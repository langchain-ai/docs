Self-hosted LangSmith Engine connects to GitHub through a GitHub App that your operator manages. This enables source-code investigation, fix branches, draft pull requests, and issue completion after a PR merge.

This guide is for the operator who configures LangSmith. A GitHub administrator follows [Create an Engine GitHub App](/langsmith/engine-github-app). Once setup is complete, workspace users [connect repositories](/langsmith/engine-github).

## Choose your GitHub environment

Configure one GitHub instance and one App per LangSmith installation. That App can have installations in multiple organizations or accounts on the instance. Each Engine project can connect multiple repositories.

| GitHub environment | Who operates GitHub | `FORGE_GITHUB_WEB_BASE_URL` | GitHub hosts that LangSmith must reach |
| --- | --- | --- | --- |
| GitHub.com, including Enterprise Cloud | GitHub | `https://github.com` | `github.com`, `api.github.com` |
| Enterprise Cloud with data residency | GitHub | `https://example.ghe.com` | `example.ghe.com`, `api.example.ghe.com` |
| GitHub Enterprise Server (GHES) | Your organization, in your cloud account or on premises | `https://git.example.com` | `git.example.com` |

Replace the example enterprise hostnames with your own. Enterprise Cloud with data residency is hosted by GitHub; it is not a GitHub appliance deployed in your cloud account. GHES hosted on AWS uses the same configuration as GHES on premises.

Use the GitHub **web origin**, with HTTPS on port 443 and a fully qualified hostname. Do not append `/api/v3`, `/api/graphql`, an organization name, or another path. LangSmith selects the API endpoints from the web origin. SSH Git URLs and custom GitHub ports are not supported.

## Before you start

You need:

- **Engine and Sandboxes**: A working [self-hosted Engine deployment](/langsmith/engine-self-hosted) and permission to update its Helm values, secrets, and workloads.
- **GitHub administration**: Permission to register an App under the chosen account and install it on the target repositories. Enterprise or organization policies may require separate approval.
- **Network access**: HTTPS connectivity for the browser, LangSmith services, and sandbox hosts, plus a webhook route reachable from GitHub. See [Allow network access](#allow-network-access).
- **GitHub integration routing**: Your ingress must serve the GitHub integration under `/api-host`, including its callback and webhook. This route and its service are required even if you do not use LangSmith Deployments.

This integration covers Engine's standard investigation and fix workflows. It does not configure GitHub for LangSmith Deployments builds or previews. Red teaming and automatic issue validation are unavailable on self-hosted Engine.

## Create the App

Follow [Create an Engine GitHub App](/langsmith/engine-github-app) on the GitHub instance you selected. That guide covers organization, personal-account, and enterprise ownership, including managed users and multi-organization installations.

Before continuing, confirm that the App has:

- **Contents** and **Pull requests** repository permissions set to read and write, plus read-only **Metadata**.
- **Request user authorization (OAuth) during installation** enabled.
- An HTTPS callback URL for your LangSmith deployment.
- An active, signed webhook with the **Pull request** event selected.

## Configure LangSmith

### Store credentials

Using your [existing secret-management workflow](/langsmith/self-host-using-an-existing-secret), create a Kubernetes Secret in the LangSmith namespace. The example below refers to a Secret named `langsmith-forge-github` with these keys:

| Secret key | Value |
| --- | --- |
| `forge_github_client_secret` | The App's OAuth Client secret. |
| `forge_github_app_pem` | The complete contents of the App's private-key PEM file, preserving newlines. |
| `forge_github_webhook_secret` | The same secret entered in the App's Webhook secret field. |
| `forge_github_state_jwt_secret` | A separate random secret of at least 32 bytes, generated by your secret manager or a cryptographically secure generator. |

The state secret protects the GitHub connection flow. GitHub does not supply it, and you do not enter it into GitHub. Do not reuse the webhook secret for this value.

Store credentials in Secrets, not in committed Helm values or command-line arguments. App IDs, Client IDs, and URLs are configuration values and can be included in Helm values.

### Set Helm values

Merge this configuration into your existing values file. Preserve any existing `commonEnv` and `extraEnv` entries. Replace the placeholders and the example URLs:

```yaml
commonEnv:
  - name: FORGE_GITHUB_WEB_BASE_URL
    value: "https://git.example.com"
  - name: FORGE_GITHUB_APP_ID
    value: "<app-id>"

hostBackend:
  enabled: true
  deployment:
    extraEnv:
      - name: FORGE_GITHUB_APP_PUBLIC_LINK
        value: "<app-page-url-copied-from-github>"
      - name: FORGE_GITHUB_CLIENT_ID
        value: "<client-id>"
      - name: ENGINE_GITHUB_OAUTH_REDIRECT_URI
        value: "https://langsmith.example.com/api-host/v1/integrations/forge/github/callback"
      - name: FORGE_GITHUB_CLIENT_SECRET
        valueFrom:
          secretKeyRef:
            name: langsmith-forge-github
            key: forge_github_client_secret
      - name: FORGE_GITHUB_APP_PEM
        valueFrom:
          secretKeyRef:
            name: langsmith-forge-github
            key: forge_github_app_pem
      - name: FORGE_GITHUB_STATE_JWT_SECRET
        valueFrom:
          secretKeyRef:
            name: langsmith-forge-github
            key: forge_github_state_jwt_secret
      - name: FORGE_GITHUB_WEBHOOK_SECRET
        valueFrom:
          secretKeyRef:
            name: langsmith-forge-github
            key: forge_github_webhook_secret
```

Keep `FORGE_GITHUB_WEB_BASE_URL` and `FORGE_GITHUB_APP_ID` in `commonEnv` so API and background workloads receive the same values. Remove duplicate definitions of these two variables from component-specific `extraEnv` sections.

Copy `FORGE_GITHUB_APP_PUBLIC_LINK` from GitHub exactly. Enterprise-owned Apps can have an enterprise namespace in their App page URL. Do not construct this value from the App name or copy the App's settings URL.

Set `ENGINE_GITHUB_OAUTH_REDIRECT_URI` to the exact callback URL saved in GitHub, including any LangSmith base path. The chart's `config.hostname`, `config.frontendHostname` if used, and `config.basePath` must also describe the URL users open in their browser.

<Warning>
Enabling `hostBackend` alone does not guarantee that your chart exposes `/api-host`. Confirm that the rendered frontend or ingress configuration routes it to the integration service. A missing route can return an HTML page or 404 instead of completing GitHub authorization.
</Warning>

Apply the complete values file through your normal deployment process, using a matching LangSmith image and chart release. For Helm upgrades, see [Upgrade a self-hosted deployment](/langsmith/self-host-upgrades).

Wait for the affected API and worker rollouts to finish before connecting repositories. Updating a Secret in place does not reload environment variables in running containers; restart affected workloads after credential changes.

## Allow network access

All GitHub connections use HTTPS. DNS resolution, routing, and certificate trust must work from the component making each connection:

| Source | Destination | Purpose |
| --- | --- | --- |
| User's browser | GitHub web host and LangSmith callback URL | Sign-in, App authorization, and installation. |
| LangSmith API and background workers | GitHub web and API hosts listed above | OAuth, repository access, branch and diff operations, and PR creation/status. |
| Engine execution workers | GitHub API host | Resolve the App's commit author. |
| Sandbox hosts | GitHub web host | Clone repositories and push fix branches. |
| GitHub | LangSmith webhook URL | Link PRs to issues and complete issues after a merge. |

GitHub.com and `ghe.com` webhooks originate outside your network. GHES webhooks originate from your GHES environment. Provide a route to the webhook handler that the relevant GitHub service can reach. A browser callback working through a user's VPN does not establish this route.

If you enforce a GitHub IP allow list, account for the outbound addresses of both LangSmith services and sandbox hosts. Use the actual addresses seen by GitHub, including any NAT gateway addresses.

Sandbox Git traffic requires a direct route from sandbox hosts to GitHub. A mandatory upstream HTTP/HTTPS forward proxy is not supported for this traffic; setting `HTTPS_PROXY` on LangSmith API pods does not configure sandbox Git access.

### GHES on a private network

For a GHES hostname that resolves to private IP addresses, configure private DNS and network routing from LangSmith and the sandbox hosts. Also set the following environment variables through the listed Helm values:

| Helm environment list | Variable | Value |
| --- | --- | --- |
| `platformBackend.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |
| `queue.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |
| `sandboxes.sandboxHost.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_EGRESS` | `"true"` |

These settings allow the respective components to reach private addresses; they do not create DNS records or network routes. They affect more than this GitHub hostname. Retain network restrictions for the destinations your deployment actually needs, and keep protections for metadata, loopback, and Kubernetes-internal addresses enabled.

### GHES with a private certificate authority

LangSmith services and sandbox hosts must trust the CA that signed your GHES certificate. Configuring trust only in your browser or inside a sandbox is insufficient.

The Helm chart's `config.customCa.secretName` and `config.customCa.secretKey` mount a CA bundle and configure `SSL_CERT_FILE`. Supply a PEM bundle that includes your private CA and any public roots needed for other outbound connections. Configure `REQUESTS_CA_BUNDLE` in `hostBackend.deployment.extraEnv` to point to the same mounted bundle, `/etc/ssl/certs/custom-ca-certificates.crt`, for GitHub clients that use Requests.

Check that the bundle reaches the GitHub integration, platform API and workers, Engine execution workers, and sandbox hosts. Keep TLS verification enabled. The sandbox proxy's own CA is separate from the CA used to verify GHES.

Validate a private-network or private-CA deployment with the complete checklist below. Successful OAuth alone does not verify cloning, pushing, or webhooks.

## Verify the integration

Use a test repository and an Engine project with representative traces:

1. Follow [Connect repositories](/langsmith/engine-github#connect-repositories). Confirm that the correct GitHub host opens, authorization returns to LangSmith, and selected repositories appear.
2. Connect a repository and choose its base branch. Run an Engine analysis and confirm it can use the repository's source code.
3. Generate a fix for an issue, inspect its diff, and open a draft PR. Check the repository, base branch, and PR link.
4. In the GitHub App's settings, open **Advanced** > **Recent deliveries**. Confirm a **pull_request** delivery reaches LangSmith successfully. The handler returns HTTP 202 when it accepts a valid signed delivery.
5. Review and merge the test PR. Confirm the corresponding Engine issue becomes complete. A successful webhook response by itself does not prove the event matched an Engine issue.
6. If users create fixes with an external coding assistant, use **Copy Fix Context**, preserve its issue reference in the PR description, and confirm the resulting PR links to the Engine issue.
7. If using several organizations, repeat repository access and a fix PR for each installation. Include repositories from different owners on the same Engine project if that is your intended configuration.

If GitHub cannot deliver webhooks, repository reads, fixes, and PR creation can still work. PR status can still be read from GitHub, but webhook-driven linking of externally created PRs and automatic issue completion after merges do not work. Restore delivery and redeliver missed events from GitHub's App settings.

## Repository policies

Engine pushes a fix branch to the connected repository and creates a draft PR. It does not use a fork-based contribution workflow or merge changes automatically.

Engine's Git commits are unsigned. Rules that require signed commits on the fix branch can reject pushes. Branch-name rules, push restrictions, and GHES pre-receive hooks can also reject a fix. For v0.17, Engine creates branches under `issues-agent/`.

Review policies that apply to these branches and the App identity. Keep your normal review and merge requirements on the target branch. A requirement on the target branch may still need to be satisfied when a person merges; configuring the App does not bypass repository policy.

## Limitations

- **One GitHub instance and App**: A LangSmith installation cannot simultaneously connect to GitHub.com, a `ghe.com` enterprise, and GHES, or use a different App per workspace.
- **Managed-user repositories**: EMU personal-account repositories cannot use this integration. Connect organization-owned repositories.
- **Git transport**: HTTPS on port 443 is required. SSH, custom GitHub ports, and GitHub installations under a URL path prefix are not supported. A LangSmith URL base path is a separate setting and is supported.
- **Repository contents**: Engine does not fetch Git LFS file contents or initialize Git submodules.
- **Repository policies**: Fix generation requires permission to push unsigned commits to an Engine branch in the connected repository. The repository must support draft PRs for Engine to open a PR.
- **App identity**: Commit attribution normally uses your App's bot identity. If GitHub's identity lookup fails, Engine can continue using a fallback author. Do not rely on commit author text as proof of which App authenticated a push.

## Change or rotate configuration

For a private-key rotation, add the new key in GitHub, update the deployment Secret, and restart affected workloads. Validate the connection before removing the old key. Follow the same overlap approach where GitHub supports multiple client secrets.

For webhook-secret rotation, coordinate the GitHub and LangSmith values. Deliveries during a mismatch fail signature verification. Review **Recent deliveries** and redeliver failed events after both sides use the new secret.

Replacing the App requires installing the replacement and reconnecting affected LangSmith workspaces. Plan for an interruption until repository access is restored. Transferring App ownership can also change where it can be installed and its App page URL; review GitHub's transfer behavior before making the change.

Do not change `FORGE_GITHUB_WEB_BASE_URL` on an existing connected deployment as a migration procedure. Changing the URL does not migrate repository connections or existing PR references. Plan a migration with LangChain support before switching GitHub instances.

## Troubleshoot setup

| Symptom | What to check |
| --- | --- |
| GitHub is not configured, or Connect GitHub fails | Confirm all App settings and Secret references are present, the App page is an HTTPS URL, and the rollout has completed. |
| GitHub authorization opens on the wrong instance | Check `FORGE_GITHUB_WEB_BASE_URL` in shared configuration and remove conflicting component overrides. |
| Installation target is missing | Check App ownership, visibility, GitHub user role, and enterprise installation policy. See [Choose who owns the App](/langsmith/engine-github-app#choose-who-owns-the-app). |
| The callback returns HTML or 404 | Check the `/api-host` route, LangSmith base path, and exact callback URL. |
| Installation finishes in GitHub but does not connect in LangSmith | Enable **Request user authorization (OAuth) during installation**, verify the Client ID/secret belong to that App, and restart the connection from LangSmith. |
| Repositories appear, but cloning or pushing fails | Check sandbox-host DNS, routing, private-IP settings, certificate trust, and GitHub IP/push policies. |
| PR creation fails after a successful push | Check **Pull requests: Read and write**, draft PR availability, and the selected base branch. |
| A merge does not complete an issue | Check **Pull request** event subscription, webhook reachability, the matching webhook secret, and **Recent deliveries**. Redeliver failed events after correcting the cause. |

When asking for help, include your LangSmith and Helm chart versions, GitHub environment and GHES version if applicable, App ownership type, and the step that fails. Do not include private keys, client secrets, webhook secrets, or access tokens.
