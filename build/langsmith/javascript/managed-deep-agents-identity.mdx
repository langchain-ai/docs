Identity controls who can invoke your managed deep agent, such as apps and SDK clients that start runs or send messages.

<ManagedDeepAgentsPublicBetaNote />

Put the identity declaration at the project root:



```text
my-agent/
  agent.ts
  identity.ts
```


For the full project layout, see [Project structure](/langsmith/javascript/managed-deep-agents-project-structure).

## Choose the identity provider

By default, `mda init` requires callers to present a LangSmith API key. Anyone who has that key can use the same deployment and may see the same threads. To give each signed-in end user private conversations, use Supabase instead:

| Goal | Use |
| --- | --- |
| Lock down the deployment for SDK clients, scripts, and services | [LangSmith API key (default)](#configure-identity-with-a-langsmith-api-key) |
| Signed-in end users with private chats | [Supabase](#configure-identity-with-supabase) |

For more information, see [Project structure](/langsmith/javascript/managed-deep-agents-project-structure).

## Configure identity with a LangSmith API key

`mda init` scaffolds this identity provider as a secure default. Callers must present a valid LangSmith workspace API key. Managed Deep Agents verifies the key with LangSmith Cloud.



```ts identity.ts
import { auth, defineIdentity } from "managed-deepagents";

export const identity = defineIdentity({
  auth: auth.langsmithApiKey(),
});
```


Clients send the key as `x-api-key`. You do not need to add verification endpoint or tenant settings to your project `.env`. LangSmith Cloud supplies those.

<Warning>
Anyone with the key can reach the deployment, so treat the key as a secret. This default does not give each end user private threads. If Alice must not see Bob's threads, use [Supabase](#configure-identity-with-supabase).
</Warning>

## Configure identity with Supabase

Use Supabase when a browser or another client calls the deployment as a signed-in entity. Each user gets private threads. Managed Deep Agents configures that ownership for you. For more information on the underlying LangSmith Deployment pattern, see [Make conversations private](/langsmith/resource-auth).

<Steps>
  <Step title="Enable auth in Supabase" id="enable-auth-in-supabase">

In the Supabase dashboard, enable the auth provider you will use (for example email/password).

  </Step>
  <Step title="Copy the project reference" id="copy-the-project-reference">

Copy the project reference: the subdomain before `.supabase.co` in your project URL.

  </Step>
  <Step title="Declare identity" id="declare-supabase-identity">

Declare identity with that project reference:



```ts identity.ts
import { auth, defineIdentity } from "managed-deepagents";

export const identity = defineIdentity({
  auth: auth.supabase({ projectRef: "your-project-ref" }),
});
```


Pass `url` instead of the project reference for a custom auth domain.

  </Step>
  <Step title="Send the access token from the client" id="send-the-access-token">

In the client app, set the Supabase project URL and publishable key (labeled `anon` in the Supabase dashboard). Sign the user in, then send the access token on every deployment request:



```ts
await fetch(`${deploymentUrl}/threads/${threadId}/runs`, {
  method: "POST",
  headers: {
    Authorization: `Bearer ${supabaseAccessToken}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify(runBody),
});
```


The publishable key (labeled `anon` in the Supabase dashboard) is only for the client to sign in with Supabase. Do not send a LangSmith API key in this mode. The Bearer token is the caller identity.

Managed Deep Agents verifies the JWT against the project's JWKS URL derived from your project reference (`https://<project-ref>.supabase.co/auth/v1/.well-known/jwks.json`).

<Note>
Adding Supabase identity to an existing deployment does not add owner metadata to existing threads. Plan and test a migration before relying on identity-based access for those threads.
</Note>

  </Step>
</Steps>

## Authenticate connection principals with OIDC

OIDC principal authentication binds an end user's verified identity to their [user-owned connections](/langsmith/javascript/managed-deep-agents-connections#choose-a-credential-owner). It lets a custom application identify callers without sending a user ID that the application chose.

Each Agent Auth request uses two independent authentication layers:

- **Service and workspace**: A LangSmith API key, LangSmith bearer token, or Agent Builder service identity authenticates the calling service and selects the workspace.
- **End user**: `X-Agent-Auth-Principal-Authorization: Bearer <token>` carries the caller's OIDC token. Agent Auth uses the verified `iss` and `sub` claims to resolve the principal in that workspace.

Agent Auth accepts the token only when its issuer has an enabled OIDC integration in the workspace. It verifies the issuer, audience, signature, expiration, and `sub` claim. A token that fails any check does not fall back to an identity supplied by the request.

Deployment identity validation and Agent Auth validation are separate trust decisions. A deployment can validate the caller before accepting a run. Agent Auth independently validates the token before resolving connection ownership. Do not use claims from an unverified JWT to authorize either operation.

### Register an OIDC integration

Register each issuer and its accepted audiences once from a trusted backend. For Google Identity Services, create an OAuth 2.0 **Web application** client ID. Add the frontend origin to **Authorized JavaScript origins**, then set that client ID as the audience. This flow does not use a Google client secret.

The following example registers Google for the current workspace:

```bash
curl --request POST \
  "$LANGSMITH_ENDPOINT/v1/agent-auth/oidc-integrations" \
  --header "x-api-key: $LANGSMITH_API_KEY" \
  --header "x-tenant-id: $LANGSMITH_WORKSPACE_ID" \
  --header "content-type: application/json" \
  --data "{
    \"slug\": \"google\",
    \"display_name\": \"Google\",
    \"issuer\": \"https://accounts.google.com\",
    \"audiences\": [\"$GOOGLE_CLIENT_ID\"]
  }"
```

Keep `LANGSMITH_API_KEY` and any LangSmith bearer token on the backend. Never expose either credential to browser code.

### Resolve the caller's principal

Send the OIDC token in the secondary authorization header. With that header present, omit `provider`, `issuer`, and `subject` from the request body. Agent Auth derives these fields from the verified token. Principal resolution therefore uses an empty JSON object:

```bash
curl --request POST \
  "$LANGSMITH_ENDPOINT/v1/agent-auth/principals" \
  --header "x-api-key: $LANGSMITH_API_KEY" \
  --header "x-tenant-id: $LANGSMITH_WORKSPACE_ID" \
  --header "X-Agent-Auth-Principal-Authorization: Bearer $GOOGLE_ID_TOKEN" \
  --header "content-type: application/json" \
  --data '{}'
```

The response returns the workspace-scoped principal. Do not log the OIDC token or copy it into application traces, error messages, or analytics.

### Create a user-owned connection

Use the same secondary header when creating a connection for that user. Set `owner_type` to `user` and omit `owner_id`; Agent Auth derives the owner from the verified token:

```bash
curl --request POST \
  "$LANGSMITH_ENDPOINT/v1/agent-auth/connections" \
  --header "x-api-key: $LANGSMITH_API_KEY" \
  --header "x-tenant-id: $LANGSMITH_WORKSPACE_ID" \
  --header "X-Agent-Auth-Principal-Authorization: Bearer $GOOGLE_ID_TOKEN" \
  --header "content-type: application/json" \
  --data "{
    \"slug\": \"user-api-key\",
    \"display_name\": \"User API key\",
    \"credential\": {
      \"kind\": \"secret\",
      \"owner_type\": \"user\",
      \"value\": \"$USER_CONNECTION_SECRET\"
    }
  }"
```

Run these requests only from a trusted backend. Avoid storing the OIDC token after the request completes. The trusted-backend flow remains equally supported. A backend that verifies identity itself can resolve a principal with explicit identity fields and omit the secondary header.

## Test and deploy

<ManagedDeepAgentsTestAndDeploy />

Authentication failures return 401. For the LangSmith API-key default, confirm that clients send `x-api-key`. For Supabase, confirm that clients send `Authorization: Bearer <access_token>`, that `project_ref` / `projectRef` matches your Supabase project, and that callers cannot access another user's threads (403).
