Role-based access control (RBAC) determines who can access your LangSmith organization and [workspaces](/langsmith/administration-overview#workspaces), and what they can do in each.

Each user has:

- One [organization role](#organization-roles) that applies across the entire organization.
- One [workspace role](#workspace-roles) in each workspace they belong to.

A user can also receive additional workspace roles through [user groups](/langsmith/user-groups). The user then holds the permissions of their assigned role and of each user group's role in that workspace.

Which roles you can assign depends on your [plan](https://langchain.com/pricing):

- **Developer**: Every user has the Organization Admin and Workspace Admin roles.
- **Plus**: All organization roles are available. Every workspace member has the Workspace Admin role.
- **Enterprise**: All organization and workspace roles are available, and you can create [custom roles](#custom-roles). To upgrade, [contact our sales team](https://www.langchain.com/contact-sales).

<Note>
To set up RBAC and assign roles, see the [User Management guide](/langsmith/user-management#set-up-access-control). Your identity provider can also assign roles automatically through [SCIM groups](/langsmith/user-management#set-up-scim-for-your-organization) or [SSO Groups Sync](/langsmith/user-management#sso-groups-sync-alternative). For the permission each operation requires, see the [Organization and workspace operations reference](/langsmith/organization-workspace-operations).
</Note>

## Organization roles

Organization roles control what a user can do across the organization, such as managing billing, members, and workspaces. They are separate from [workspace roles](#workspace-roles), which control access to resources inside a workspace. Organization roles are system-defined and cannot be modified or extended.

| Role | Description | Availability |
|------|-------------|--------------|
| [Organization Admin](#organization-admin) | Full permissions to manage organization configuration, users, billing, and workspaces | All plans |
| [Organization Operator](#organization-operator) | Management access to workspaces and users for day-to-day operations, excluding admin-level privileges | [Plus and Enterprise](https://langchain.com/pricing) |
| [Organization User](#organization-user) | Read access to organization information and ability to create personal access tokens | [Plus and Enterprise](https://langchain.com/pricing) |
| [Organization Viewer](#organization-viewer) | Read-only access to organization information | [Plus and Enterprise](https://langchain.com/pricing) |
| [Organization Restricted](#organization-restricted) | Workspace access without organization-wide read access | [Plus and Enterprise](https://langchain.com/pricing) |

### Organization Admin

The Organization Admin role has full permissions to manage all organization configuration, users, billing, and workspaces.

**Key permissions**:

| Permission | Grants |
|------------|--------|
| `organization:manage` | Legacy broad organization-management grant, retained for compatibility with older services |
| `organization:settings:manage` | Change the organization name and security contacts |
| `organization:members:manage` | Manage invitations and organization members, subject to role-assignment rules |
| `organization:access-control:manage` | Manage roles, restrictions, access policies, and role assignments |
| `organization:authentication:manage` | Manage SSO, login methods, and provisioning configuration |
| `organization:scim-tokens:manage` | Create, update, and delete SCIM provisioning tokens |
| `organization:security-policy:manage` | Manage sharing, key expiry, IP, and model-provider policies |
| `organization:billing:read` and `organization:billing:manage` | Read protected billing details and manage billing, respectively |
| `organization:workspaces:manage` | Create workspaces |
| `organization:retention:manage` | Manage organization-level retention controls |
| `organization:usage-controls:manage` | Manage usage limits, Engine spend limits, and evaluator spend defaults |
| `organization:audit-logs:read` | View audit logs |
| `organization:charts:read` and `organization:charts:manage` | Read dashboard definitions and manage organization dashboards, respectively |
| `organization:integrations:read` and `organization:integrations:manage` | Read protected integration configuration and manage organization integrations, respectively |
| `organization:infrastructure:read` and `organization:infrastructure:manage` | Read data-plane configuration and manage data planes and private networking, respectively |
| `organization:engine:read` and `organization:engine:manage` | Read organization Engine configuration and manage Engine enablement, respectively |
| `organization:gateway:manage` | Manage LLM Gateway policies |
| `organization:model-price-map:read` and `organization:model-price-map:manage` | Read and manage custom model pricing, respectively |
| `organization:installation-operations:read` and `organization:installation-operations:manage` | Read installation diagnostics and perform installation operations, subject to installation restrictions |
| `organization:installation-usage:manage` | Manage installation usage reporting, subject to installation restrictions |
| `organization:service-key:manage` | Manage service accounts and delete organization-wide service keys; key creation and role assignment have additional requirements |
| `organization:read` | Read general organization information; protected billing, audit, integration, and infrastructure details require separate permissions |
| `organization:pats:create` | Create organization-level [personal access tokens](/langsmith/administration-overview#personal-access-tokens-pats) |
| `organization:pats:read` | View every organization member's personal access tokens |
| `organization:pats:manage` | Deactivate, reactivate, or delete any organization member's personal access token |

**Key capabilities**:

- Manage [organization settings](/langsmith/set-up-hierarchy#set-up-an-organization) and branding.
- Configure [SSO and authentication methods](/langsmith/user-management#set-up-saml-sso-for-your-organization).
- Manage [billing](/langsmith/billing) and subscription plans.
- Create and delete workspaces.
- Invite and remove organization members.
- View, deactivate, reactivate, and delete any member's personal access tokens.
- Assign organization and workspace roles to members.
- Create and manage [custom roles](#custom-roles).
- Configure RBAC and [attribute-based access control (ABAC)](/langsmith/abac) policies.
- View organization [usage](/langsmith/usage-and-billing#usage-limits) and analytics.
- View [audit logs](/langsmith/audit-logs) (Enterprise).

For details on setting up and managing your organization, see the [Administration overview](/langsmith/administration-overview#organizations).

### Organization Operator

The Organization Operator role has management access for day-to-day operations, including workspace and user management, but cannot manage Organization Admins or create organization-wide service keys.

**Key permissions**:

| Permission | Grants |
|------------|--------|
| `organization:manage` | Legacy broad organization-management grant, retained for compatibility with older services |
| Action-specific administration permissions | The same granular organization administration grants as Organization Admin, subject to the restrictions below |
| `organization:read` | Read general organization information; protected billing, audit, integration, and infrastructure details require separate permissions |
| `organization:pats:create` | Create personal access tokens |
| `organization:pats:read` | View every organization member's personal access tokens |
| `organization:pats:manage` | Deactivate, reactivate, or delete any organization member's personal access token |

**Key capabilities**:

- Create and manage [workspaces](/langsmith/set-up-hierarchy#set-up-a-workspace).
- Invite organization members with any role except Organization Admin.
- Modify and remove Organization Users, Viewers, and Operators.
- View, deactivate, reactivate, and delete any member's personal access tokens.
- Assign workspace roles to members.
- Create workspace-scoped service keys and service accounts.
- Manage organization billing and subscription plans.
- Create, edit, and delete custom roles.
- Configure SSO and authentication methods.
- View organization usage and analytics.
- View audit logs (Enterprise).

**Restrictions**:

- Cannot invite, modify, or remove Organization Admins.
- Cannot assign the Organization Admin role to users.
- Cannot create organization-wide (non-workspace-specific) service keys.
- Is not automatically added to existing workspaces. An Organization Operator joins only the workspaces they create or are explicitly invited to.

### Organization User

The Organization User role has read access to organization information and can create personal access tokens.

**Key permissions**:

| Permission | Grants |
|------------|--------|
| `organization:read` | Read access to organization information |
| `organization:pats:create` | Create personal access tokens |

**Key capabilities**:

- View organization members and workspaces.
- View organization settings.
- Create personal access tokens for API access.
- Join workspaces they are invited to.

**Restrictions**:

- Cannot modify organization settings.
- Cannot manage billing or subscriptions.
- Cannot create or delete workspaces.
- Cannot invite or remove organization members.
- Cannot manage roles or permissions.

An Organization User can belong to a subset of workspaces, with a workspace role in each that sets their permissions there.

### Organization Viewer

The Organization Viewer role has read-only access to organization information.

**Key permissions**:

| Permission | Grants |
|------------|--------|
| `organization:read` | Read access to organization information |

**Key capabilities**:

- View organization members and workspaces.
- View organization settings.

**Restrictions**:

- Cannot modify anything at the organization level.
- Cannot create personal access tokens.
- Cannot manage billing, workspaces, or members.

### Organization Restricted

The Organization Restricted role grants access to assigned workspaces without organization-wide read access. Assign it to users who should work in their own workspaces without seeing other organization members or organization-level details.

**Key permissions**:

| Permission | Grants |
|------------|--------|
| `organization:read-metadata` | Read access to organization metadata, including organization roles |
| `organization:charts:read` | Read organization dashboard definitions; rendering requires access to source workspace resources |

**Key capabilities**:

- View organization metadata, role definitions, and dashboard definitions.
- Work in assigned workspaces, with permissions set by the workspace role in each.

**Restrictions**:

- Does not include `organization:read`, so cannot list organization members or service keys.
- Cannot be assigned through [just-in-time (JIT) provisioning](/langsmith/jit-invite-sso). New users created through JIT receive Organization User, and the SSO default role setting applies only to workspace roles.

Assign Organization Restricted the same way as any other organization role: through a member invite, a [SCIM group](/langsmith/user-management#group-naming-convention), or an [SSO Groups Sync](/langsmith/user-management#sso-groups-sync-alternative) group match.

Workspace-scoped [service keys](/langsmith/administration-overview#service-keys) can also hold this role. When creating or editing a service key scoped to **Specific Workspaces**, choose Organization Viewer (the default) or Organization Restricted. This choice does not change who can create or edit service keys.

## Workspace roles

Workspace roles control what users and API keys can do with resources inside a workspace.

| Role | Description |
|------|-------------|
| [Workspace Admin](#workspace-admin) | Full permissions for all resources, including workspace settings and member management |
| [Workspace Editor](#workspace-editor) | Full permissions for most resources, cannot manage workspace settings or delete certain resources |
| [Workspace Viewer](#workspace-viewer) | Read-only access to all workspace resources |
| [Fleet User](#fleet-roles) | Use and rate Fleet agents shared with them, with no access to traces |
| [Fleet Builder](#fleet-roles) | Fleet User permissions plus creating, editing, and deleting Fleet agents and skills |
| [Fleet Admin](#fleet-roles) | Fleet Builder permissions plus Fleet administration, workspace integrations and secrets, deployments, read access to traces, and workspace management |
| [Workspace Member Only](#workspace-member-only) | Workspace membership with no permissions of its own |

<Note>
LangSmith also defines workspace roles for the [keys LangSmith creates](#roles-for-keys-that-langsmith-creates). These roles appear in role lists, such as the role selector for a service key, but are not meant for users.
</Note>

### Workspace Admin

The Workspace Admin role has full permissions for all resources in the workspace and can manage the workspace itself.

**Key permissions**:

- All create, read, update, delete, and share permissions for all resource types.
- Workspace management, including all action-specific administration permissions, the broad `workspaces:manage` grant, and independent member, key, secret, and model-configuration permissions.

### Workspace Editor

The Workspace Editor role has full permissions for most resources in the workspace, but cannot manage workspace settings or delete certain critical resources.

**Restrictions**:

- Cannot delete [runs](/langsmith/observability-concepts#runs).
- Cannot manage workspace settings, such as the workspace name.
- Cannot manage workspace members (add, remove, or update member roles).

### Workspace Viewer

The Workspace Viewer role has read-only access to all resources in the workspace.

**Key permissions**:

- Read-only access to all resource types.

### Fleet roles

The Fleet roles grant access to [Fleet](/langsmith/fleet/index) without the broader access of the Workspace Editor or Workspace Admin role. Each role includes the permissions of the one above it in this table:

| Role | Permissions |
|------|-------------|
| Fleet User | `fleet-agents:read`, `fleet-agents:invoke`, `fleet-skills:read`, `mcp-servers:read`, `mcp-servers:invoke`, `deployments:read`, `prompts:read`, `workspaces:read`, `feedback:read`, `feedback:update`, and `feedback:delete`. No access to traces. |
| Fleet Builder | Fleet User permissions, plus `fleet-agents:create`, `fleet-agents:update`, `fleet-agents:delete`, `fleet-skills:create`, `fleet-skills:update`, and `fleet-skills:delete`. |
| Fleet Admin | Fleet Builder permissions, plus:<br/>• Fleet administration: `fleet:read-admin-config`, `fleet:write-admin-config`, and `workspaces:fleet-feedback:read-all`<br/>• MCP servers and integrations: `mcp-servers:create`, `mcp-servers:update`, `mcp-servers:delete`, and `workspaces:integrations:manage`<br/>• Deployments, sandboxes, and snapshots: `deployments:create`, `deployments:update`, `deployments:delete`, `sandboxes:read`, `snapshots:create`, and `snapshots:delete`<br/>• Traces: `projects:read` and `runs:read`<br/>• Workspace management: `workspaces:manage` and `workspaces:manage-secrets` |

Fleet Admin includes `workspaces:manage`, which also covers workspace settings outside Fleet. It does not include `workspaces:manage-members`. For what each Fleet permission allows, see [Fleet access and oversight](/langsmith/fleet/access-and-oversight#configure-a-fleet-role).

### Workspace Member Only

The Workspace Member Only role makes a user a member of a workspace without granting any permissions. The user's access in that workspace comes from the roles of their [user groups](/langsmith/user-groups).

### Roles for keys that LangSmith creates

These workspace roles belong to API keys that LangSmith creates for its own features, such as deployments, [Engine](/langsmith/engine), and taskset runs. Their descriptions in the LangSmith UI start with `(System)`.

| Role | Used for | Permissions |
|------|----------|-------------|
| Deployment Runtime | Keys that LangSmith creates for a deployment's runtime | Workspace Editor permissions, without `simulations:create`, `tasksets:run`, or `workspaces:tracing-keys:create`, plus `gateway:invoke`, `sandboxes:exec`, `snapshots:update`, `functions:update`, and `agent-auth-credentials:use` |
| Gateway Invoker | Keys that LangSmith creates to call the [LLM Gateway](/langsmith/llm-gateway) | `gateway:invoke` and `workspaces:read` |
| Taskset Agent | Keys that write traces for a taskset trial's Agent Server | `projects:create`, `projects:read`, `runs:create`, `prompts:read`, and `workspaces:read` |
| Issues Agent | Short-lived keys that Engine creates to analyze traces and record issues | Read access to traces, feedback, issues, prompts, rules, charts, and model prices, plus `issues:create`, `issues:update`, and `gateway:invoke` |
| Issues Agent (Replica) | Short-lived keys for Engine | Issues Agent permissions, without `gateway:invoke` |
| Issues Agent Data Tenant Reader | Short-lived keys for Engine | Read-only access to traces, feedback, issues, prompts, rules, charts, and model prices |
| Issues Agent Trace Writer | Short-lived keys that write Engine's own traces | `projects:read`, `workspaces:read`, `runs:create`, `feedback:create`, `feedback:update`, and `agent-auth-connections:read` |

Do not assign these roles to users. You can assign Gateway Invoker to a service key that only calls the LLM Gateway. For details, see [Grant permission to call the LLM gateway](/langsmith/llm-gateway-authentication#grant-permission-to-call-the-gateway).

## Custom roles

<Info>Creating custom roles is only available for organizations on the Enterprise plan.</Info>

Custom roles are workspace roles that you define. [Organization Admins](#organization-admin) and [Organization Operators](#organization-operator) can create custom roles with specific combinations of workspace-level permissions, then assign them alongside the built-in [workspace roles](#workspace-roles).

### Create a custom role

Custom roles are created at the [organization](/langsmith/administration-overview#organizations) level and can be assigned to users in any [workspace](/langsmith/administration-overview#workspaces) within that organization.

To create a custom role:

1. Navigate to Organization **Settings** > **Roles**.
2. Click **Create Role**.
3. Enter a **Role Name** and, optionally, a **Description**.
4. Under **Permissions**, select the permissions to include in the role.
5. Click **Create**.

After you create the role, [assign it to users](/langsmith/user-management#assign-a-role-to-a-user) in specific workspaces.

For details on which specific permissions are required for each operation, refer to the [Organization and workspace operations reference](/langsmith/organization-workspace-operations).

Note the following details on custom roles:

- Only Organization Admins and Organization Operators can create and manage custom roles.
- Custom roles are organization-specific (not transferable between organizations).
- Each custom role can have any combination of workspace-level permissions.
- Custom roles cannot have organization-level permissions.
- Users can have different roles (including custom roles) in different workspaces.

### Understand permission behavior

Action-specific permissions let you delegate administration without granting broad management access. Built-in Organization Admin and Operator roles include granular organization administration grants. Built-in Workspace Admin includes granular workspace administration grants.

Action-specific organization permissions are independent of `organization:manage`: the broad grant alone does not satisfy a granular check. Built-in Organization Admin and Operator roles retain the broad grant for compatibility with older services and integration setup that still requires it. General `organization:read` does not include protected billing, audit, integration, or infrastructure reads.

For workspace operations that historically required `workspaces:manage`, either the granular grant or `workspaces:manage` is accepted. Existing roles keep that historical access; you do not need to remove or replace their broad grant. This fallback does not grant unrelated permissions or bypass additional requirements.

| Workspace permission | Grants |
|----------------------|--------|
| `workspaces:settings:manage` | Change the workspace name, handle, experience, feature default models, and agent types |
| `workspaces:retention:manage` | Change workspace data-retention settings |
| `workspaces:usage-controls:manage` | Manage workspace usage limits, together with `organization:usage-controls:manage` |
| `workspaces:security-policy:manage` | Revoke public shares and manage feature model and provider restrictions |
| `workspaces:resource-tags:manage` | Manage resource tag definitions, values, and assignments |
| `workspaces:integrations:manage` | Manage workspace integration controls, OAuth providers, and integration destinations |
| `workspaces:integrations:read` | Read protected integration identity-provider metadata |
| `workspaces:sandbox-proxy-profiles:manage` | Manage sandbox proxy profiles within existing ownership limits |
| `workspaces:credentials:read-metadata` | Read protected connection, credential, and authorization-session metadata without retrieving credentials |
| `workspaces:credentials:manage` | Manage credentials, retrieve credential material, and refresh credentials |
| `workspaces:credentials:use` | Use stored credentials through Managed Tools |
| `workspaces:access-control:assign-restricted` | Assign restricted workspace roles, together with member- or key-management permission |
| `workspaces:delete` | Delete a workspace, subject to existing lifecycle restrictions |
| `workspaces:fleet-feedback:read-all` | Read all Fleet feedback in the workspace |
| `agent-auth-connections:create`, `agent-auth-connections:update`, and `agent-auth-connections:delete` | Manage agent authorization connections; revocation remains a separate permission |

Keep these independent permissions and compound requirements in mind:

- **Workspace members**: Grant `workspaces:manage-members` to add, remove, or update members. Neither `workspaces:manage` nor restricted-role assignment authority replaces it.
- **Model configurations**: Grant `workspaces:manage-model-configs` to create, edit, or delete [model configurations](/langsmith/model-configurations), including [OAuth client credentials](/langsmith/model-configurations#oauth-client-credentials). Feature default models require settings-management permission; model and provider restrictions require security-policy permission. In the UI, disabling the current default also requires permission to clear it.
- **Workspace API keys**: Grant `workspaces:manage-keys` to create or delete workspace-scoped service keys. The caller also needs authority to assign the chosen role in every target workspace. Restricted roles require `workspaces:access-control:assign-restricted`, `workspaces:manage`, or organization access-control authority. Without that authority, you can assign an unrestricted role; when you omit a role, the key defaults to your own role. Organization-wide service keys have additional organization-role requirements. See [role restriction rules](#restrict-roles).
- **Workspace secrets**: Grant `workspaces:manage-secrets` explicitly. Neither credential-management permission nor `workspaces:manage` replaces it.
- **User groups**: Grant the relevant organization or workspace `user-groups:*` permissions explicitly. Broad management grants do not include them.

The following resource permissions also remain independent:

- `bulk-exports:read` and `bulk-exports:manage` cover the bulk export endpoints (listing, creating, cancelling exports, and managing destinations). Use them in a custom role to grant least-privilege bulk export access without `workspaces:manage`. The built-in Workspace Admin role includes `bulk-exports:manage` and all read-capable roles include `bulk-exports:read` automatically.
- `projects:increase-trace-tier` and `projects:decrease-trace-tier` are independent and can be granted separately. For example, you can allow a role to decrease retention without allowing it to increase retention. If a user lacks both permissions, the retention settings UI is hidden entirely. If they have only one, the UI is partially enabled (the disallowed direction is disabled).
- `runs:read-inputs` and `runs:read-outputs` control whether a role can see run inputs and outputs, and are separate from `runs:read`. A role with `runs:read` but without one of these permissions can still list and open runs, but responses leave out the denied field and its preview. Message and trajectory views require both permissions. To hide inputs or outputs only in specific projects, use an [access policy](/langsmith/abac#control-access-to-run-inputs-and-outputs).
- `projects:update` covers only metadata updates (name, description, tags) and does **not** grant the ability to change trace retention. To allow a custom role to modify trace tier, you must explicitly grant `projects:increase-trace-tier`, `projects:decrease-trace-tier`, or both.

## Restrict roles

<Info>Role restriction is available for organizations on the [Enterprise](/langsmith/pricing-plans) plan.</Info>

[Organization Admins](#organization-admin) and [Organization Operators](#organization-operator) can mark built-in or custom roles as **restricted**. Restrictions limit which roles a delegated administrator can assign, in addition to the permissions required for the operation.

| Role scope | Requirement to assign a restricted role |
|------------|----------------------------------------|
| Organization | `organization:access-control:manage`, held by Organization Admins and Organization Operators. Only Organization Admins can assign or manage Organization Admins. |
| Workspace | `workspaces:access-control:assign-restricted` or the supported broad `workspaces:manage` grant, alongside the permission to manage members or keys. |

The built-in Workspace Admin role includes `workspaces:access-control:assign-restricted`. The `workspaces:manage-members` permission alone does not allow assigning restricted workspace roles. For workspace grants attached to an organization invitation, assigning Workspace Admin or a restricted workspace role requires `organization:access-control:manage`.

Organization Admin and Organization Operator are always restricted. You cannot remove their restrictions. Workspace roles are not restricted by default.

To restrict a role, in the [LangSmith UI](https://smith.langchain.com?utm_source=docs&utm_medium=cta&utm_campaign=langsmith-signup&utm_content=langsmith-rbac):

1. Navigate to Organization **Settings** > **Roles**.
2. Find the role in the Roles table. Check its **Scope** to distinguish organization and workspace roles.
3. Select the **Restricted** checkbox for that role.

To remove a restriction, clear the same checkbox. Restricting an organization role also protects members and service accounts that already hold it from changes by delegated member or key managers.

In member invite, member edit, and API key flows, role selectors exclude restricted roles that the caller cannot assign. The API also rejects unauthorized assignments. A caller without restricted-workspace-role assignment authority cannot use their own restricted role as an API key's default role.
