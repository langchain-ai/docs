Model fallbacks retry a request against one or more backup models when the primary model returns a configured error, such as a rate limit or provider outage. Define the fallback order once in LangSmith, then continue using the standard LLM Gateway endpoint and model ID in your application.

## How it works

A fallback chain has:

- **A primary model**: the provider and model that trigger the chain when a request fails.
- **One to five fallbacks**: an ordered list of direct provider models or saved [model configurations](/langsmith/model-configurations).
- **Triggers**: the upstream HTTP status codes that move the request to the next model, grouped by cause such as rate limits or server errors. For details, see [Set fallback triggers](#set-fallback-triggers).
- **A time to first output** (optional): how long to wait for a model to start responding before moving to the next model. For details, see [Set a time to first output](#set-a-time-to-first-output).
- **A model cooldown** (optional): skips a model on later requests after it fails repeatedly. For details, see [Skip failing models with a cooldown](#skip-failing-models-with-a-cooldown).

For each request, the gateway:

1. Calls the primary model selected by the request's provider-prefixed model ID.
1. If the request fails with a configured trigger status, times out, or fails to connect, loads the matching fallback chain.
1. Calls each fallback in order until one succeeds, returns a status that does not trigger another fallback, or the chain is exhausted.
1. Returns the final response in the API format used by the client.

Fallbacks can use a different provider and API format than the primary model. The gateway translates requests and responses between [supported API formats](/langsmith/llm-gateway-api-formats), so an Anthropic primary can fall back to an OpenAI model without client-side changes.

Each attempt is traced and counted against [spend policies](/langsmith/llm-gateway-spend-policies) separately. A request that uses two fallbacks records three model calls: the primary attempt and two fallback attempts.

## Create a fallback chain

<Warning>
Creating and managing fallback chains requires `organization:manage` permission. For the full permissions breakdown, see [Access control](/langsmith/llm-gateway-access).
</Warning>

To create a fallback chain:

1. Go to **LLM Gateway** and select the **Model Fallbacks** tab.
1. Click **Create fallback chain**.
1. Select the **Workspace** where the chain applies.
1. Select the primary provider and model. Requests to this provider-prefixed model ID use the chain when the primary attempt fails.
1. Under **Fallbacks**, add one to five backup models in the order the gateway should try them. Choose a provider and model directly, select an existing model configuration, or create a custom model configuration.
1. Under **Fallback triggers**, review which errors move a request to the next model. The rate limit, server error, and request timeout groups are selected by default. For details, see [Set fallback triggers](#set-fallback-triggers).
1. (Optional) Set **Time to first output** to limit how long each model can take to start responding.
1. (Optional) Set **Model cooldown** to skip a model that keeps failing.
1. Click **Create chain**.

A provider and model can have one fallback chain in each workspace. To change its behavior, edit the existing chain.

## Set fallback triggers

Fallback triggers are the provider errors that send a request to the next model in the chain. A fallback also happens when the gateway cannot connect to a provider, regardless of the selected triggers.

Status codes are grouped by why another model can help:

- **Rate limits and overload**: `429`, `503`, and `529`. The provider is busy, rate limited, or temporarily unavailable. Selected by default.
- **Server errors**: `500`, `502`, `504`, `507`, `508`, `510`, and `511`. The provider failed while handling the request. Selected by default.
- **Request timeouts**: `408` and `425`. The provider took too long to accept the request. Selected by default.
- **Model or request rejected**: `400`, `403`, and `404`. A different model can succeed when one refuses the request, for example because the prompt is too long for it. Not selected by default.
- **Other status codes**: any other code from `300` to `599`. Click **Add codes** to enter one.

To remove a single code from a group, click the code. Click it again to add it back. A chain can use up to 20 status codes.

## Set a time to first output

A time to first output limits how long the gateway waits for each model to start responding. When a model does not respond in time, the gateway cancels that attempt and moves to the next model. Use it to recover quickly from a provider that hangs instead of returning an error.

- For streaming requests, the timer runs until the model sends its first output.
- For non-streaming requests, the timer runs until the provider returns response headers, which usually arrive when the full response is ready. Set a limit long enough for your longest expected completion.

Each model in the chain gets a fresh timer. Leave **Time to first output** blank to wait without a limit. The value must be between 1 and 300 seconds.

## Skip failing models with a cooldown

A model cooldown skips a model on later requests after it fails repeatedly, so requests go straight to the next model instead of waiting for the same failure again. For example, with a time to first output of 30 seconds, a provider outage costs every request 30 seconds until the provider recovers. With a cooldown, only the first few requests wait.

To set a cooldown, enter the cooldown period in seconds and the number of failures under **Model cooldown**. For example, **Skip for 60 seconds after 3 failures** means that when a model fails 3 times within 60 seconds, later requests skip it for the next 60 seconds. The cooldown period must be between 1 and 3600 seconds, and the number of failures between 1 and 10. Leave both fields blank to turn off the cooldown.

A cooldown follows these rules:

- **What counts as a failure**: a selected trigger status code from the provider, a time to first output that elapses, or a failure to connect to the provider. Errors inside the gateway, and requests the client cancels, do not count.
- **How failures are counted**: failures count within the cooldown period, starting from the first failure. A successful response does not reset the count.
- **Which models can be skipped**: the primary model and every fallback except the last. The gateway always tries the last model in the chain, so a request is never left without a model to try.
- **Scope**: each fallback chain counts its own failures. A model in cooldown for one chain is still tried by other chains that use it.

A skipped model is not called, so it adds no latency and no cost. The [gateway response metadata](#inspect-fallback-attempts) records the skip with the trigger `cooldown`.

To set a cooldown through the API, add an `ejection` block to the fallback chain's configuration:

```json
"ejection": {"failure_threshold": 3, "cooldown_seconds": 60}
```

### Rate limit cooldowns

When a chain's triggers include `429`, the gateway also skips models that recently returned a rate limit, without any cooldown setting. After a provider returns `429` for a model, requests skip that model until the retry delay the provider requested has passed, up to 5 minutes. If the provider sends no retry delay, the model is skipped for 5 seconds. When the error indicates an exhausted quota or spend limit, the model is skipped for 5 minutes.

Unlike a model cooldown, a rate limit cooldown is shared by every fallback chain in the workspace that uses the same provider and model and falls back on `429`, because the rate limit belongs to the provider account rather than to one chain.

The LLM Gateway home page simulator does not apply cooldowns, so use real requests to check cooldown behavior.

## Make a call

Call the standard LLM Gateway endpoint with the primary provider-prefixed model ID. You do not need a route-specific URL or additional request fields:

<CodeGroup>

```bash Cloud
curl https://gateway.smith.langchain.com/v1/chat/completions \
    -H "Authorization: Bearer $LANGSMITH_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"model":"anthropic/claude-opus-5","messages":[{"role":"user","content":"Hello!"}]}'
```

```bash BYOC
curl https://<data_plane_host>/gateway/v1/chat/completions \
    -H "Authorization: Bearer $LANGSMITH_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{"model":"anthropic/claude-opus-5","messages":[{"role":"user","content":"Hello!"}]}'
```

</CodeGroup>

The gateway applies the fallback chain configured for `anthropic/claude-opus-5` in the API key's workspace. If no chain matches, the gateway returns the primary model's response without attempting a fallback.

## Inspect fallback attempts

Every gateway response includes an `X-LangSmith-Gateway-Metadata` header with a JSON summary of how the gateway routed the request. To see it, add `-i` to a `curl` request.

For a fallback chain, the summary lists each model the gateway tried or skipped:

```json
{
  "selected_candidate": 2,
  "selected_model": "gpt-5.4-mini",
  "fallback_used": true,
  "attempt_details": [
    {"candidate": 1, "model": "claude-opus-5", "fallback_trigger": "cooldown"},
    {"candidate": 2, "model": "gpt-5.4-mini", "status_code": 200}
  ]
}
```

The `fallback_trigger` field explains why the gateway moved past a model:

- **`status_code`**: the model returned a selected trigger status code.
- **`transport_error`**: the gateway could not connect to the model's provider.
- **`timeout`**: the time to first output elapsed.
- **`cooldown`**: the model was skipped without being called because it is in a cooldown.

## Set fallbacks for a prompt

To give a prompt its own fallback chain, route it through a saved model configuration. The prompt references the configuration by name, while the gateway manages its fallback chain.

Creating the configuration requires workspace admin permissions. Creating the fallback chain requires `organization:manage` permission.

To configure fallbacks for a prompt:

1. [Create a model configuration](/langsmith/model-configurations#create-a-configuration) pointing to the provider and model you want the prompt to use.
1. [Create a fallback chain](#create-a-fallback-chain) in the same workspace. Select your saved configuration as the primary model, rather than selecting its underlying provider and model directly. Add the backup models, configure the triggers, and save the chain.
1. [Create a prompt](/langsmith/create-a-prompt) in the Playground. Open **Model Configuration**, select **LangSmith Gateway** as the **Provider**, and enter `custom/<my_config_name>` in the **Model** field. Replace `<my_config_name>` with the saved configuration's name, without angle brackets. You can type the value even if it is not listed. Click **Apply**.

    <img
      src="/images/llm-gateway-prompt-model-configuration.png"
      alt="Model Configuration dialog with LangSmith Gateway selected as the provider and custom/<my_config_name> entered in the Model field."
    />

1. **Save** the prompt, then [pull it with its model](/langsmith/manage-prompts-programmatically#pull-a-prompt). In Python, set `include_model=True` when calling `client.pull_prompt` so the saved Gateway model configuration is included.

Invoke the pulled prompt with its saved model to send requests through the gateway and apply the configuration's fallback chain. Pulling only the prompt template does not include the model configuration.

The fallback chain belongs to the model configuration, not the prompt itself. Prompts that reference the same configuration share its fallbacks. Use a separate configuration for each prompt that needs different fallback behavior.

## Choose fallback candidates

You can add two types of fallback candidates:

- **Direct provider model**: select a supported gateway provider and model. This option uses the workspace's secret for that provider, or Gateway Credits for eligible hosted models.
- **Model configuration**: select a saved [model configuration](/langsmith/llm-gateway-model-configurations). Use this option for a custom OpenAI-compatible or Anthropic endpoint, a custom model name, or configuration-specific parameters.

A fallback chain can use model configurations from its selected workspace or organization. If both scopes contain a configuration with the same name, LLM Gateway uses the workspace-scoped configuration, including for the primary model.

For example, configure `anthropic/claude-opus-5` as the primary model, `openai/gpt-5.4-mini` as the first fallback, and a saved OpenAI-compatible model configuration as the second fallback. The application continues to request `anthropic/claude-opus-5`; the gateway selects and translates fallback calls when needed.
