Logging traces to an agent names the [agent](/langsmith/agents) and the [environment](/langsmith/agent-environments) a trace belongs to. Your application sends both with every run, and LangSmith records them when the trace arrives. A trace goes either to an agent or to a [project](/langsmith/log-traces-to-project), never both.

<Note>
Sending traces to an agent applies to agent-based workspaces, which are in [beta](/langsmith/release-stages). The [arguments that take an agent](#agent-arguments) can change without notice. It is supported in:

- The Python SDK from `langsmith>=0.14.5`
- The TypeScript SDK from `langsmith>=0.10.9`

For tracing setup that does not depend on the beta, see [Log traces to a specific project](/langsmith/log-traces-to-project).
</Note>

## Agent variables

Two environment variables name the agent and the environment:

- **`LANGSMITH_AGENT_ID`**: The agent to send traces to. The value is the agent's identifier, which the browser address bar carries and the **ID** field on the agent's Overview copies. It is sent with every run.
- **`LANGSMITH_AGENT_ENVIRONMENT`**: The environment the run belongs to. Required alongside the agent, and one of `local`, `development`, `staging`, or `production`. Use the lowercase form, which maps to the Local, Development, Staging, and Production labels in the UI. There is no default, because neither the agent nor the environment names a destination alone. If only one of the two variables is set, the SDK logs a warning and leaves the call untraced instead of picking an environment for you, so nothing reaches LangSmith.

`LANGSMITH_AGENT_ID` takes the identifier, not the display name. A [display name is a separate, editable value](/langsmith/agents#identifiers-and-display-names) that does not have to match the identifier, so read the identifier from the agent rather than deriving it from what the agent is called.

## Agent arguments

Supply the agent and the environment together, in code or as both [environment variables](#agent-variables). In code, pass an `AgentAddress` object: `ls.AgentAddress("checkout", "production")` in Python or `new AgentAddress("checkout", "production")` in TypeScript.

In Python, @[`@traceable`] and @[`tracing_context`][tracing_context] each take the agent in an `address` argument. In TypeScript, [`traceable`](https://reference.langchain.com/javascript/langsmith/traceable) takes the agent as `address` in its config. An agent in code takes precedence over the variables. The SDK reads the variables only when nothing in code names a destination, and then it needs both.

## Send your first trace to an agent

<Steps>
  <Step title="Confirm your workspace is enabled">
    If your workspace is agent-based, sending traces to an agent is already on. LangChain turns it on, and you have no setting to change. In a workspace that LangChain [converted](/langsmith/migrate-to-agent-based-workspaces#how-a-workspace-moves), an admin can switch the UI between the new and the classic experience. That switch changes only what the UI shows. It does not turn on sending traces to an agent.

    To tell which kind of workspace you have, look at the control at the top left. In an agent-based workspace it names your workspace. In a project-based workspace it shows the LangSmith logo, and sending traces to an agent is off. To ask about access, [contact our sales team](https://www.langchain.com/contact-sales).

    If your workspace is not enabled, LangSmith ingestion rejects runs sent to an agent and records nothing.
  </Step>
  <Step title="Install the SDK">
    Sending traces to an agent needs `langsmith>=0.14.5` in Python or `langsmith@>=0.10.9` in TypeScript:

    <CodeGroup>

    ```bash uv
    uv add "langsmith>=0.14.5"
    ```

    ```bash pip
    pip install -U "langsmith>=0.14.5"
    ```

    ```bash npm
    npm install "langsmith@>=0.10.9"
    ```

    </CodeGroup>
  </Step>
  <Step title="Choose an identifier">
    Copy the identifier from the **ID** field on an existing agent's Overview, or pick a new one. If no agent in the workspace uses the identifier you pick, LangSmith creates that agent the first time you send a trace to it. You do not have to create the agent in advance. For the rules an identifier must follow, see [Identifier rules](/langsmith/create-an-agent#identifier-rules).
  </Step>
  <Step title="Configure the agent">
    Set both [agent variables](#agent-variables), or pass an [`AgentAddress`](#agent-arguments) in code. If only one variable is set, the SDK logs a warning and sends nothing.

    ```bash
    export LANGSMITH_TRACING=true
    export LANGSMITH_API_KEY=<your-api-key>
    export LANGSMITH_AGENT_ID=checkout
    export LANGSMITH_AGENT_ENVIRONMENT=production
    ```

    The first two are the usual tracing prerequisites rather than part of naming the agent. Use an [API key](/langsmith/create-account-api-key) from the workspace you confirmed in step 1.
  </Step>
  <Step title="Run your application">
    Run your application so it sends at least one trace. Producing traces needs `@traceable` or `tracing_context` in Python, or `traceable` in TypeScript, as in [Examples](#examples).
  </Step>
  <Step title="Find the trace">
    In LangSmith, select the agent in the top bar, go to **Tracing**, and set the environment control to the one you sent the trace to. The trace appears there.
  </Step>
</Steps>

## Query an agent's traces

To query the traces of an agent, first [resolve the agent to its project ID](/langsmith/resolve-an-agent), then use the endpoints as before, passing that ID.

## An agent and a project are mutually exclusive

Sending traces to an agent and to a project do not combine. What happens depends on where each is set:

- **An agent and a project together**: Not allowed. If you set the agent variables and also `LANGSMITH_PROJECT`, `LANGCHAIN_PROJECT`, or `LANGCHAIN_SESSION`, the trace has two destinations, and the SDK does not pick one. It logs a warning when the client starts, and it does not trace a call unless code names the destination. If you pass both `address` and `project_name` to `@traceable` or `tracing_context()` in one call, the SDK raises `LangSmithUserError` and sends nothing. If a run that names both an agent and a project reaches LangSmith, LangSmith rejects it.
- **A project named in code**: Overrides the agent variables. Passing `project_name` to `@traceable` or `tracing_context()` traces the run to that project and ignores the agent variables, without an error. This is what lets an [evaluation](/langsmith/evaluation) set its own project while the agent variables stay set for the rest of the process.

## Send traces to an agent that does not exist

If an identifier does not match an agent in the workspace, LangSmith creates that agent.

For the rules the value must follow, see [Identifier rules](/langsmith/create-an-agent#identifier-rules).

An agent created this way shows no Deployments section on its [Overview](/langsmith/navigate-agents#read-the-agent-overview).

## When runs stop being accepted

A workspace that accepted runs sent to an agent can stop accepting them. First check that your API key still belongs to the agent-based workspace, because LangSmith rejects runs sent to an agent with a key from a project-based workspace. If the key is not the problem, contact support via [support.langchain.com](https://support.langchain.com).
