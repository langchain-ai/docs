Run priority decides which waiting run starts next when every worker slot on a deployment is busy. You set each thread's priority in a Python function that runs on the server, so urgent work, such as interactive chat, starts ahead of background work, such as scheduled jobs.

<Note>
Run priority is in beta. It requires Agent Server 0.18.0 or later and `langgraph-sdk>=0.4.12`, and the image must be built with `langgraph-cli>=0.4.38`. The priority function is Python only.
</Note>

## How run priority works

- **Priority**: An integer from -5 to 5. -5 starts first, 5 starts last, and 0 is the default.
- **Set once per thread**: Your priority function sets a thread's priority at the thread's first run. Every later run on the thread uses the same priority, and priority does not change how runs execute on a thread: a thread still runs one run at a time, oldest first, and no running run is stopped.
- **Order of waiting runs**: When a worker slot frees up, the waiting run with the most urgent priority starts. Runs with the same priority start in the order they became due.
- **Busy deployments only**: Priority matters only when every worker slot is busy. When a slot is free, a run starts right away, whatever its priority.
- **No function, no change**: Without a priority function, every run has priority 0 and runs start in the same order as before.

## Configure run priority

### Step 1. Write a priority function

Create `priority.py` next to your `langgraph.json`, and decorate an async function with `@priority.assign` on a @[Priority] instance:

```python
from langgraph_sdk import Priority

priority = Priority()


@priority.assign
async def assign(ctx: Priority.types.PriorityContext):
    if ctx.cron_id is not None:
        return {"priority": 3}  # Scheduled jobs wait behind other runs
    if ctx.assistant_metadata.get("workload") == "chat":
        return {"priority": -3}  # Interactive chat starts first
    return None  # Every other run uses the default priority, 0
```

The function receives a @[PriorityContext] with these fields:

- **`user` and `permissions`**: The authenticated user and their permissions. For a run that a cron starts, the cron's owner.
- **`thread_id` and `thread_metadata`**: The thread and its metadata, including metadata that the run adds. `thread_id` is `None` for a run without a thread.
- **`assistant_id`, `graph_id`, and `assistant_metadata`**: The assistant, its graph, and the assistant's metadata.
- **`run_metadata`**: The run's metadata.
- **`cron_id`**: The ID of the cron that started the run, or `None`.

The function returns a @[PrioritySettings] dictionary, or `None` to use the defaults:

- **`priority`**: An integer from -5 to 5. Defaults to 0.
- **`fairness_group`**: A string of at most 256 characters. Defaults to `"default"`. The server stores it on the thread unencrypted, even with custom encryption, so use an opaque ID rather than personal data. It does not affect run order yet.

Any other key causes the run to fail, except `fairness_weight`, which earlier SDK versions list and the server ignores with a warning.

Keep the function async and fast. It runs on the API server before a thread's first run is created, so a blocking call, such as a synchronous HTTP request, stalls every request on that server.

### Step 2. Add the function to `langgraph.json`

Add a `priority` section whose `path` points at the `Priority` instance, and set `api_version` to 0.18.0 or later:

```json
{
  "dependencies": ["."],
  "graphs": {
    "agent": "./agent.py:graph"
  },
  "api_version": "0.18.0",
  "priority": {
    "path": "./priority.py:priority"
  }
}
```

Server versions earlier than 0.18.0 ignore the `priority` section. For all configuration keys, see the [configuration file reference](/langsmith/cli#configuration-file).

### Step 3. Build and deploy the image

Run priority applies to images that you build with `langgraph build`, such as images for self-hosted deployments:

```bash
langgraph build -t <registry>/<agent>:<tag>
docker push <registry>/<agent>:<tag>
```

Then update your deployment to the new image. On self-hosted LangSmith, `langgraph deploy --push-to <registry>/<agent>` builds the image, pushes it, and updates the deployment in one step. For more information, see [Deploy with the control plane](/langsmith/deploy-with-control-plane).

<Note>
Deployments that LangSmith Cloud builds from your repository do not apply the `priority` section yet.
</Note>

## Verify that run priority is on

- **Server logs**: At startup, the server logs `Loaded priority callback from path ...`. If the server cannot load the function, it does not start, so a wrong path shows up at deploy time rather than on every run.
- **Threads**: After a thread's first run, reading the thread returns `run_priority` and `fairness_group`.
- **Metrics**: Queue metrics carry a `priority` label from -5 to 5, for example `lg_api_num_due_pending_runs`. These series appear only while a priority function is configured.

<Note>
`langgraph dev` calls your priority function and stores the result, but starts runs in arrival order. To see runs start in priority order, test on a deployment.
</Note>

## Understand how priority behaves

- **Client requests**: No API field sets a run's priority. If your function reads metadata that callers send, callers can influence the result, so prefer the authenticated user or assistant metadata that you control.
- **Existing threads**: A thread that already exists receives a priority at its next run after you deploy the function.
- **Changes to the function**: A thread's priority does not change. A new version of the function applies to threads that have not run yet.
- **Errors**: If the function raises an exception, the server does not create the run and returns a 500 error. To refuse a run with your own status code, raise @[HTTPException]. In both cases nothing is stored, so the thread's next run calls the function again.
- **Long waits**: Under sustained load at more urgent priorities, runs at less urgent priorities can wait indefinitely, because priorities do not age. The per-priority wait metrics show how long runs wait.
- **Scheduled runs**: A run scheduled for later competes at its priority from its due time.

## Turn off run priority

Remove the `priority` section from `langgraph.json`, rebuild the image, and redeploy. Every new run then has priority 0. Runs that were already waiting keep the priority they were created with. Threads keep their stored priority, which applies again if you add the function back.
