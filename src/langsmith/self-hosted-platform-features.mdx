This page describes the platform features that apply only to [self-hosted](/langsmith/self-hosted) deployments.

## Custom PostgreSQL

A custom PostgreSQL instance can be used instead of the [one automatically created by the control plane](/langsmith/cloud-platform-features#database-provisioning). Specify the [`POSTGRES_URI_CUSTOM`](/langsmith/env-var-self-hosted) environment variable to use a custom PostgreSQL instance. To authenticate with a cloud workload identity instead of a static password, see [Configure IAM authentication for data stores](/langsmith/configure-iam-auth).

Multiple deployments can share the same PostgreSQL instance. For example, for `Deployment A`, `POSTGRES_URI_CUSTOM` can be set to `postgres://<user>:<password>@/<database_name_1>?host=<hostname_1>` and for `Deployment B`, `POSTGRES_URI_CUSTOM` can be set to `postgres://<user>:<password>@/<database_name_2>?host=<hostname_1>`. `<database_name_1>` and `<database_name_2>` are different databases within the same instance, but `<hostname_1>` is shared. **The same database cannot be used for separate deployments**.

## Custom Redis

A custom Redis instance can be used instead of the one automatically created by the control plane. Specify the [`REDIS_URI_CUSTOM`](/langsmith/env-var-self-hosted) environment variable to use a custom Redis instance. To authenticate with a cloud workload identity instead of a static password, see [Configure IAM authentication for data stores](/langsmith/configure-iam-auth).

Multiple deployments can share the same Redis instance. For example, for `Deployment A`, `REDIS_URI_CUSTOM` can be set to `redis://<hostname_1>:<port>/1` and for `Deployment B`, `REDIS_URI_CUSTOM` can be set to `redis://<hostname_1>:<port>/2`. `1` and `2` are different database numbers within the same instance, but `<hostname_1>` is shared. **The same database number cannot be used for separate deployments**.

Redis Cluster supports only database `0`, so deployments cannot share a Redis Cluster by database number. To share one Redis server across deployments, use a standalone Redis instance with a separate database number for each deployment.

## Listeners

A listener is an instance of a [listener application](/langsmith/data-plane#listener-application). A listener contains metadata about the application (such as its version) and metadata about the compute infrastructure where it can deploy to (such as Kubernetes namespaces).

The listener data model only applies to self-hosted deployments. The control plane and listener coordinate to provision and reconcile deployments running on your own infrastructure.

### Listener version requirements

Keep the listener current before you change a deployment's `resource_spec`. The control plane validates a `PATCH` against the rules of its own version. The listener then validates the stored `resource_spec` again against the rules of its own version when it applies the revision. If the listener is older than the control plane, a `PATCH` can return `200` and the revision then fails with `DEPLOY_FAILED`.

The rejected value stays in the stored `resource_spec`, so every later revision of that deployment also fails, including image-only deploys, until you `PATCH` the deployment with a value the listener accepts.

The following `resource_spec` fields depend on the listener version:

| Field | Minimum listener version |
| :--- | :--- |
| Fractional `cpu` and `queue_cpu` values (for example, `0.5`) | Later than 0.12.x. Listener 0.12.x rejects fractional values. |
| `redis_cpu` and `redis_cpu_limit` | 0.13.22 or later. Earlier listeners ignore these fields. |
| `redis_memory_mb` below `2048` | 0.13.27 or later. Earlier listeners require at least `2048`. |
| `volumes` and `volume_mounts` | 0.11.30 or later. |

Upgrading the listener does not restart existing deployments. After you upgrade, `PATCH` each deployment with its full `resource_spec` to apply the new values. For the accepted ranges and `PATCH` behavior, see [Resource spec](/langsmith/api-ref-control-plane#resource-spec).

## Resource customization

You set resources for each self-hosted deployment, including its Redis and PostgreSQL instances, through the deployment's `resource_spec`. Unlike Cloud, which exposes fixed Serverless and Dedicated [deployment types](/langsmith/cloud-platform-features#deployment-types), self-hosted deployments size CPU, memory, replicas, and storage according to your infrastructure configuration. Some fields, such as Redis CPU, require a minimum listener version. See [Listener version requirements](#listener-version-requirements).

The `db_*` fields size the PostgreSQL instance that the control plane creates, and the `redis_*` fields size the Redis instance. If a deployment uses [custom PostgreSQL](#custom-postgresql) or [custom Redis](#custom-redis), the matching fields have no effect.

There are no organization or workspace defaults for deployment resources. Fields you do not set fall back to the defaults for the deployment type, so send a full `resource_spec` when you create each deployment. See [Configure Agent Server for scale](/langsmith/agent-server-scale) for tuning guidance.

## Volumes

You can mount Kubernetes volumes, such as a PersistentVolumeClaim backed by Amazon EFS, NFS, or another CSI driver, into a deployment's pods. This lets your agent read and write files that persist across restarts or that several replicas share. The operator adds the volumes to both the API server and the queue worker pods.

Set volumes in one of two places:

- **One deployment**: Set `volumes` and `volume_mounts` in the deployment's `resource_spec` through the [control plane API](/langsmith/api-ref-control-plane). The LangSmith UI does not expose these fields.
- **Every deployment**: Add `volumes` and `volumeMounts` to the operator's base deployment template in your Helm values (`operator.templates.deployment`). For an example of editing that template, see [Configure authentication for private registries](/langsmith/enable-self-hosted-deployment#configure-authentication-for-private-registries).

If both set a volume or volume mount with the same `name`, the deployment's `resource_spec` takes precedence.

To mount a volume on one deployment:

1. Create the PersistentVolumeClaim in the Kubernetes namespace where the deployment runs. For Amazon EFS, install the [Amazon EFS CSI driver](https://docs.aws.amazon.com/eks/latest/userguide/efs-csi.html) and use an EFS StorageClass with the `ReadWriteMany` access mode, so that every replica can mount the volume.
1. Call `PATCH /v2/deployments/{deployment_id}` with the volume and its mount in `resource_spec`. Each `volumes` entry takes a `name` and exactly one volume source: `persistentVolumeClaim`, `csi`, `nfs`, `configMap`, `secret`, `emptyDir`, `projected`, or `downwardAPI`. The control plane passes the source object to Kubernetes unchanged, so write its keys in Kubernetes camelCase, for example `claimName`:

    ```json
    {
      "resource_spec": {
        "min_scale": 1,
        "max_scale": 3,
        "cpu": 1,
        "memory_mb": 2048,
        "volumes": [
          {
            "name": "shared-files",
            "persistentVolumeClaim": { "claimName": "efs-claim" }
          }
        ],
        "volume_mounts": [
          { "name": "shared-files", "mountPath": "/mnt/shared" }
        ]
      }
    }
    ```

    A `PATCH` that includes `resource_spec` replaces the whole object, so include your existing CPU, memory, and replica values. For more information, see [Resource spec](/langsmith/api-ref-control-plane#resource-spec).
1. Poll the new revision until its `status` is `DEPLOYED`, then confirm that the files are visible at `mountPath` in the API server and queue worker pods.

## PodDisruptionBudgets

Starting in operator 0.1.60 (`langgraph-dataplane` chart 0.2.24), the operator creates a PodDisruptionBudget with `minAvailable: 1` for a deployment's API server and queue worker Deployments when their minimum replica count is 2 or more. You cannot turn these PodDisruptionBudgets off.

Before you upgrade to operator 0.1.60 or later, remove any PodDisruptionBudgets of your own that select the same pods. When two PodDisruptionBudgets select the same pod, Kubernetes cannot evict it, so node drains and other evictions fail.
