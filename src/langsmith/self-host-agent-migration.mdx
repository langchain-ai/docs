Self-hosted LangSmith v0.18 organizes every workspace by [agent](/langsmith/agent-registry#agent) instead of by tracing project. Each agent divides its traces across [environments](/langsmith/agent-environments) drawn from a fixed set of four. When you upgrade an existing installation, LangSmith migrates your tracing projects to agents automatically, so no action is required from you.

This page is for administrators of a self-hosted installation. It covers how the migration runs, how your existing tracing projects map to agents, and what changes in each workspace afterward. For the upgrade itself, see [Upgrade an installation](/langsmith/self-host-upgrades). Upgrades move one minor version at a time, so an installation on 0.16 upgrades to the latest 0.17 chart before moving to 0.18.

## Before you upgrade

- **The migration cannot be undone.** Once it has run, do not downgrade to a LangSmith version from before the migration. Writes from the older version can be lost.
- **LangSmith does not migrate installations without authentication.** If your installation sets `authType: none`, its workspace keeps the tracing-project experience after the upgrade.

## How the migration runs

The migration starts on its own after the upgrade. The Helm chart value `config.agentMigration.enabled` controls it and defaults to `true`. It runs on the existing queue workers, so it needs no extra infrastructure or permissions.

1. About 10 minutes after the upgraded services start, LangSmith begins migrating workspaces. Restarts do not reset this delay.
1. LangSmith migrates and verifies each workspace on its own. A workspace switches to agents as soon as its own migration is verified, without waiting for the rest of the installation.
1. While the migration is active, LangSmith checks migrated workspaces for tracing projects created after their migration and migrates those too.
1. After 24 hours with no new work, and a clean scan of the installation, the migration stops for good. Later upgrades do not run it again.

To pause the migration, set `config.agentMigration.enabled` to `false` and apply the Helm change. LangSmith reads the setting at startup, so the change takes effect once the affected pods restart. To resume, set it back to `true`. The migration continues from where it stopped.

## How tracing projects map to agents

LangSmith does not re-ingest, move, or rename your traces. Each tracing project keeps its ID, name, and history:

- **Each tracing project becomes its own agent**, with a Production environment. That environment is the original tracing project. The migration does not create Staging, Development, or Local environments.
- **Projects are not merged by name.** Tracing projects named `checkout`, `checkout-prod`, and `checkout-staging` become three separate agents, not one agent with three environments.
- **The agent identifier comes from the project name**, converted to lowercase letters, digits, and hyphens. When a deployment owns the tracing project, the identifier and display name come from the deployment's name instead. If the identifier is already taken, LangSmith adds a suffix.
- **Some projects stay as they are.** LangSmith does not convert experiments, internal projects, or tracing projects that belong to preview deployments to agents.

A new environment that you add later gets a tracing project named after the agent identifier, a hyphen, and the environment. For example, an agent whose identifier is `checkout` has its staging traces in `checkout-staging`.

## What changes

The organizing container changes, and everything scoped to it follows:

- **Traces** group under an agent and one of its environments instead of under a tracing project you named.
- **Prebuilt dashboards** cover an environment rather than a named project. See [Monitor agent environments with dashboards](/langsmith/dashboards).
- **Alerts** are scoped to an environment of an agent. See [Alerts](/langsmith/alerts).
- **Evaluators** attach to an environment. See [Manage evaluators](/langsmith/evaluators).
- **Datasets** attach to one or more agents rather than to a project, and to no environment, so one dataset can serve several agents. See [Create and manage datasets in the UI](/langsmith/manage-datasets-in-application).
- **Navigation** gains an agent picker in the top bar, which moves between the agent list and a single agent's Overview. See [Navigate agents](/langsmith/navigate-agents).
- **The top-left control** becomes a workspace switcher that names your workspace and opens a list of the workspaces in your organization. Where Fleet is enabled, the workspace list ends with a link to Fleet.

Agents and environments record what a tracing project cannot: which agent produced a trace, and in which environment. LangSmith can then act on that context rather than asking you to filter for it, so an alert can watch production and stay quiet about local runs, and a prebuilt dashboard covers each environment without you naming a project for it.

What does not change: your traces, datasets, prompts, and experiments are the same records, and existing tracing configuration keeps working. See [Configure legacy integrations](/langsmith/create-an-agent#use-an-environment-project).
