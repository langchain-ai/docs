These are estimates, not a quote. Rates are AWS public on-demand prices for `us-east-1` Linux, retrieved on 22 September 2026. AWS changes them without notice. Your bill depends on region, usage, and any discount agreement with AWS, such as an Enterprise Discount Program or a Savings Plan.

The ClickHouse tab is a monthly run-rate for a whole default data plane. The SmithDB tab is only what SmithDB adds when it replaces ClickHouse as the trace store: a local-SSD node pool, a small general-compute pool, and a PostgreSQL 18 metastore. It does not include the EKS control plane, system nodes, Redis, application pods, or networking. SmithDB S3 is priced on its own, because it depends on how much trace data you keep.

<Warning>
Scaling capacity for any resource can be lowered when required, as long as the deployment remains within safe operating limits. For cost-conscious or pre-production deployments, Multi-AZ can be turned off. That lowers monthly cost and reduces fault tolerance.
</Warning>

  <Tab title="SmithDB">
    Prices use the tested tiers in [Configure SmithDB for scale](/langsmith/self-host-smithdb-scale). Each line includes the instances, one 100 GiB gp3 boot volume per node, and the metastore with 50 GB of storage. Hours per year are 8,760. S3 is excluded.

    Pod sizes follow the tier: requests equal limits, so each pod is placed whole on one node. `compaction` and `cluster-manager` run on general compute (2.25 vCPU at Small, 4.25 vCPU at Medium). If your existing nodes already have that room, drop the general-compute line. The metastore is a dedicated PostgreSQL 18 database. Do not use a burstable `db.t3` or `db.t4g` class for it.

    In `us-east-1` the local-NVMe pool is priced on `m6id`. Any family with enough local NVMe works. A single Small `m6id.4xlarge` has 16 vCPU and no room for node daemons, so the smallest single node is `m6id.8xlarge`.

    | Layout | What a node loss does |
    | --- | --- |
    | A. One node | SSD workloads stop until a replacement node starts, then the cache rebuilds from S3. Data in S3 and the metastore is kept. |
    | B. Two nodes, half-size replicas | Each SSD workload keeps one replica at half the tier CPU and memory. This split is not one of the three load-tested profiles. |
    | B+. Two nodes, documented pod sizes | Pods on the surviving node keep running. The lost pods wait for a replacement. |
    | C. Two full nodes | Documented pod sizes continue at two replicas each. |

    Medium Option B runs `query` as two pods of 14 vCPU and 24 GiB, and `ingestion` and `compaction-worker` as two pods of 8 vCPU and 16 GiB each. Prices assume one `compaction-worker` replica at the documented size. Two replicas need 76 vCPU at Medium, which does not fit a single 64 vCPU node.

    One Small environment on layout A plus two Medium environments on layout B is $110,218 per year. The same shape with Medium on B+ is $143,478. Layout C for all three is $203,641. Large is a tested tier and is not priced here.

    A 1-year Standard Reserved Instance, all upfront, for that one-Small-plus-two-Medium shape is about $64,718 on layout B and $64,338 if every environment uses layout A. Reserve a family only after the tier is confirmed, and pin the node pool to that family.

    ### S3

    SmithDB object storage is not in the totals. Standard storage is $0.023 per GB-month for the first 50 TB. Do not add lifecycle rules that expire objects. SmithDB deletes its own segments, and an external rule can delete live data.

    | Data retained | Per year |
    | --- | --- |
    | 1 TB | $283 |
    | 10 TB | $2,826 |
    | 50 TB | $14,131 |

    A ClickHouse backfill needs an extra `m6id.4xlarge` for the migration job (8 vCPU, 32 GiB, 100 GiB ephemeral) at about $693 per month. That node is only for the backfill.

    See [Prepare SmithDB supporting infrastructure](/langsmith/self-host-smithdb-infrastructure) for the metastore, bucket, and cache disk.
