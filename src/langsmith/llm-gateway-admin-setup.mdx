One-time setup to enable the LLM Gateway for your LangSmith [organization](/langsmith/administration-overview#organizations). [Organization admins](/langsmith/rbac#organization-admin) should complete this before individual users can route calls through the gateway.

## Prerequisites

You need [`organization:manage` permission](/langsmith/organization-workspace-operations) in LangSmith. [Step 2 Option A](/langsmith/llm-gateway-admin-setup#option-a-create-a-custom-workspace-role-recommended) also requires a plan that includes [RBAC](/langsmith/rbac) (custom roles).

On self-hosted LangSmith, [enable the gateway in the Helm chart](/langsmith/llm-gateway-self-hosted) before you complete these steps.

## 1. Add Provider Secrets

Skip this step for LangChain-hosted models: they use your LangSmith API key, not provider secrets. See [Gateway Credits](/langsmith/llm-gateway-credits) for paid chat models. Continue with step 2 to grant gateway access.

The gateway resolves provider credentials from your workspace's Provider Secrets. This lets it proxy calls to upstream providers without individual users needing local copies of provider credentials.

Go to **Settings > Integrations > Provider Secrets** and add the keys for the providers you want to proxy through the gateway:

| Secret name | Provider |
| --- | --- |
| `ANTHROPIC_API_KEY` | Anthropic |
| `AWS_BEARER_TOKEN_BEDROCK` | AWS Bedrock |
| `AZURE_FOUNDRY_API_KEY` | Azure Foundry (API key authentication only) |
| `AZURE_FOUNDRY_RESOURCE_NAME` | Azure Foundry (required for both authentication methods) |
| `AZURE_TENANT_ID` | Azure Foundry (Entra ID authentication only) |
| `AZURE_CLIENT_ID` | Azure Foundry (Entra ID authentication only) |
| `AZURE_CLIENT_SECRET` | Azure Foundry (Entra ID authentication only) |
| `BASETEN_API_KEY` | Baseten |
| `FIREWORKS_API_KEY` | Fireworks |
| `GOOGLE_API_KEY` | Google Gemini |
| `OPENAI_API_KEY` | OpenAI |
| `SCALEDOWN_API_KEY` | ScaleDown |
| `VERTEX_SERVICE_ACCOUNT_JSON` | Gemini Enterprise Agent Platform |

Add only the providers your organization uses. The gateway returns an error if a user calls a provider whose credentials have not been added.

### Configure Azure Foundry authentication

Azure Foundry supports either an API key or a Microsoft Entra ID service principal. Service principal authentication lets you use resources that disable API key authentication (`disableLocalAuth`).

Both methods require `AZURE_FOUNDRY_RESOURCE_NAME`. Set it to the Azure resource name, not a URL or deployment name. The gateway sends requests to `<resource-name>.openai.azure.com` in the Azure public cloud.

For API key authentication, add `AZURE_FOUNDRY_API_KEY` and `AZURE_FOUNDRY_RESOURCE_NAME` through the Azure Foundry provider form.

To use an Entra ID service principal instead:

1. Create a Foundry resource and deploy a chat model, or use an existing resource and deployment. Record the resource name and deployment name separately. Use the deployment name as the `model` value in requests.
1. In the Azure portal, go to **Microsoft Entra ID > App registrations > New registration**, or select an existing app registration. No redirect URI is needed. From the app's overview, record the directory (tenant) ID and application (client) ID.
1. Go to **Certificates & secrets > New client secret** for the app registration. Copy the secret **value**, not the secret ID, before leaving the page. The value is shown only once.
1. Open the **Foundry resource**, not a project inside it. Go to **Access control (IAM) > Add > Add role assignment**. Assign the app's service principal the `Cognitive Services OpenAI User` role at the resource scope.

   A role assigned on a project does not grant access to the parent resource. The generic `Contributor`, `Owner`, and `Reader` roles do not grant permission to call models. Allow 5–10 minutes for a new role assignment to take effect.

1. In LangSmith, select the workspace that routes Azure requests. Go to **Settings > Integrations > Provider Secrets** and add each of the following as a custom secret:

   | Secret name | Value |
   | --- | --- |
   | `AZURE_FOUNDRY_RESOURCE_NAME` | Azure resource name. |
   | `AZURE_TENANT_ID` | Directory (tenant) ID. |
   | `AZURE_CLIENT_ID` | Application (client) ID. |
   | `AZURE_CLIENT_SECRET` | Client secret value. |

   Select **Custom** in the provider selector to enter each secret's name and value. The Azure Foundry provider form only exposes API key authentication.

1. Remove `AZURE_FOUNDRY_API_KEY` from the workspace if it is set. An API key takes precedence over service principal credentials, even when the resource disables API key authentication.

All three Entra ID secrets are required. If any are missing, the gateway returns a `400` error identifying the missing secrets. The gateway obtains and refreshes Azure access tokens automatically. Users continue to authenticate to the gateway with their LangSmith API key, not the Azure credentials.

This method uses a client secret. It does not use managed identity or workload identity federation.

#### Verify Azure access

Before testing through the gateway, verify that the service principal can call Azure directly. Use the Azure CLI to sign in as the service principal and obtain an access token for `https://cognitiveservices.azure.com`. Send that token as `Authorization: Bearer <token>` to your resource's `/openai/v1/chat/completions` endpoint, with the deployment name as `model`.

After completing the gateway access steps below, send the same chat request through the gateway at `/azure/v1/chat/completions`. Authenticate with your LangSmith API key instead of the Azure token. A successful response confirms that the workspace secrets and Azure permissions work together.

The gateway also supports `/azure/v1/responses` and `/azure/v1/messages`. The messages endpoint requires a compatible model deployment. Do not use the older `/openai/deployments/<name>/chat/completions?api-version=...` URL format as a gateway path.

#### Troubleshoot Azure authentication

- **Missing model permissions:** If Azure reports a missing `Microsoft.CognitiveServices/accounts/OpenAI/deployments/chat/completions/action` permission, check the role assignment on the Foundry resource. An assignment on a project is not sufficient.
- **New role assignment:** If Azure reports `Principal does not have access to API/Operation.`, allow 5–10 minutes for permissions to propagate, then retry the direct Azure call.
- **Direct Azure call succeeds, but gateway call fails:** Check the secrets in the workspace associated with your LangSmith API key. Confirm the resource name is not a URL and `AZURE_FOUNDRY_API_KEY` is absent.
- **Deployment listing returns 404:** For `/azure/deployments`, use `api-version=2023-03-15-preview`. Newer API versions can omit this endpoint.

## 2. Configure gateway access for users

The built-in roles `WORKSPACE_USER` and `WORKSPACE_VIEWER` do not include the `gateway:invoke` permission and cannot be edited. You have two options for granting gateway access:

### Option A: Create a custom workspace role (recommended)

Requires an RBAC-enabled plan.

1. Go to **Settings > Members/Roles**.
1. Create a new workspace role.
1. Grant it at minimum `gateway:invoke` and `workspaces:read`.
1. Assign users who need gateway access to this role.

Use this when you want to grant gateway access to specific users without giving them full workspace-admin privileges. This gives you the most control over who can use the gateway.

### Option B: Use the workspace admin role

No plan requirement.

The `WORKSPACE_ADMIN` role already includes both `gateway:invoke` and `workspaces:read` by default. Assign users who need gateway access to this role.

Use this if you don't need fine-grained access control, or if you don't have RBAC enabled.

## 3. Configure policies (optional)

Gateway policy management requires `organization:manage` permission.

Go to **LLM Gateway** to create governance policies. You can configure:

- **Spend limits:** hard caps at the organization, workspace, API key, or user level. Refer to [Spend policies](/langsmith/llm-gateway-spend-policies).
- **Data policy:** detect and redact PII and secrets before they reach the model, and control whether request and response bodies are traced. Refer to [Data policy](/langsmith/llm-gateway-data-policy).

Policies are optional during initial setup. The gateway will freely allow invocations until you have configured policies.

## 4. Distribute API keys to users

Create workspace-scoped [Service Keys](/langsmith/administration-overview#service-keys) for users who need gateway access. Each key should be attached to a role that includes `gateway:invoke` and `workspaces:read`.

Use workspace-scoped keys, not organization-scoped keys. See [API key scoping](/langsmith/llm-gateway-access#api-key-scoping) for details.

Share the key and the gateway endpoint with each user, or distribute them via MDM (mobile device management) for company-wide coding agent rollouts. For per-agent configuration instructions, refer to [Set up coding agents](/langsmith/llm-gateway-coding-agents).

## Verification

For bring-your-own-key providers, ask a user to run the [verification cURL from the quickstart](/langsmith/llm-gateway-quickstart#send-a-request). A `200` response confirms the gateway, the API key, provider secrets, and role permissions are all configured correctly. The call will appear as a trace in the **gateway** tracing project in the workspace.
