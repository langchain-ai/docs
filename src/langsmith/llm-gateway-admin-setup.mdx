[Organization admins](/langsmith/rbac#organization-admin) should follow this one-time setup guide to connect providers and grant gateway access to users in their [organization](/langsmith/administration-overview#organizations). Once complete, users can route calls through the gateway.

## Prerequisites

You need the [Organization Admin](/langsmith/rbac#organization-admin) role in LangSmith.

On self-hosted LangSmith, [enable the gateway in the Helm chart](/langsmith/llm-gateway-self-hosted) before you complete these steps.

## 1. Add provider secrets

Skip this step if your users call only [Gateway Credits](/langsmith/llm-gateway-credits) models: LangChain owns the upstream credential, so no provider secret is required. Continue with step 2 to grant gateway access.

The gateway resolves provider credentials from your workspace's provider secrets. This lets it proxy calls to upstream providers without individual users needing local copies of provider credentials.

Go to **Settings > Integrations > Provider secrets**, and add the keys for the providers you want to proxy through the gateway:

| Secret name | Provider |
| --- | --- |
| `ANTHROPIC_API_KEY` | Anthropic |
| `AWS_BEARER_TOKEN_BEDROCK` | AWS Bedrock |
| `AZURE_FOUNDRY_API_KEY` | Azure Foundry |
| `AZURE_FOUNDRY_RESOURCE_NAME` | Azure Foundry |
| `BASETEN_API_KEY` | Baseten |
| `FIREWORKS_API_KEY` | Fireworks |
| `GOOGLE_API_KEY` | Google Gemini |
| `OPENAI_API_KEY` | OpenAI |
| `SCALEDOWN_API_KEY` | ScaleDown |
| `TYPESAFE_API_KEY` | TypeSafe |
| `VERTEX_SERVICE_ACCOUNT_JSON` | Gemini Enterprise Agent Platform |
| `XAI_API_KEY` | xAI |

<Tip>
Azure Foundry also supports Microsoft Entra ID service principal authentication, for resources that disable API keys. For setup steps, see [Provider authentication](/langsmith/llm-gateway-provider-authentication#configure-azure-foundry).
</Tip>

## 2. Configure gateway access for users

The built-in roles `WORKSPACE_USER` and `WORKSPACE_VIEWER` do not include the `gateway:invoke` permission and cannot be edited. You have two options for granting gateway access:

### Option A: Create a custom role (recommended)

This option requires a plan that includes [custom roles](/langsmith/rbac#custom-roles).

1. Go to **Settings > Roles** and create a custom role.
1. Grant it at minimum `gateway:invoke` and `workspaces:read`.
1. Go to **Settings > Members** and assign the role to users who need gateway access.

Use this when you want to grant gateway access to specific users without giving them full workspace-admin privileges. This gives you the most control over who can use the gateway.

### Option B: Use the workspace admin role

This option works on any plan.

The `WORKSPACE_ADMIN` role already includes both `gateway:invoke` and `workspaces:read` by default. Assign users who need gateway access to this role.

Use this if you do not need fine-grained access control, or if your plan does not include custom roles.

## 3. Configure governance policies (optional)

Creating policies requires `organization:gateway:manage` permission, which Organization Admins and Organization Operators have by default. On self-hosted LangSmith earlier than application version 0.18.9, it requires `organization:manage` instead.

Until you configure a policy, the gateway allows every invocation. Use the horizontal tabs on the **LLM Gateway** page to create any of the following types of governance policies:

- **[Spend limits](/langsmith/llm-gateway-spend-policies)**: Hard caps at the organization, workspace, API key, or user level.
- **[Rate limits](/langsmith/llm-gateway-rate-limit-policies)**: Request or token limits in a rolling time window.
- **[Model access](/langsmith/llm-gateway-model-access-policies)**: Which models users can call.
- **[Per-customer policies](/langsmith/llm-gateway-header-policies)**: Spend caps and rate limits split by a custom request header, so each end customer gets its own limit.
- **[Data policy](/langsmith/llm-gateway-data-policy)**: Detect and redact PII and secrets before they reach the model, and control whether request and response bodies are traced.

<Tip>
On the Enterprise plan, creating, updating, and deleting policies is recorded in [audit logs](/langsmith/audit-logs).
</Tip>

## 4. Distribute API keys to users

Each user needs a workspace-scoped [LangSmith API key](/langsmith/create-account-api-key) whose permissions include `gateway:invoke` and `workspaces:read`. Organization-scoped keys are not supported. For details, see [Use a workspace-scoped key](/langsmith/llm-gateway-authentication#use-a-workspace-scoped-key).

A [personal access token](/langsmith/administration-overview#personal-access-tokens-pats) has the same permissions as the user who created it, so it carries the role you assigned in step 2. A [service key](/langsmith/administration-overview#service-keys) does not inherit a user's role.

Share the key and the gateway endpoint with each user, or distribute them via MDM (mobile device management) for company-wide coding agent rollouts. For per-agent configuration instructions, see [Set up coding agents](/langsmith/llm-gateway-coding-agents).

## Verification

For bring-your-own-key providers, ask a user to run the [verification cURL](/langsmith/llm-gateway-first-request#send-a-request-from-your-code). A `200` response confirms the gateway, the API key, provider secrets, and role permissions are all configured correctly. The call appears as a trace in the **gateway** tracing project in the workspace.
