Fleet gives you the control layer for scaling agents across your organization: tiered permissions, credential management, human-in-the-loop oversight, and an audit trail for agent actions.

## Permissions and sharing

Fleet combines workspace role permissions with agent sharing. Your role determines which actions you can perform. Agent ownership and sharing determine which agents you can access.

<Note>
The Fleet roles and custom roles are part of the Enterprise [RBAC](/langsmith/rbac) feature. Self-hosted v0.17 does not include the Fleet roles, and Fleet on v0.17 checks a different set of permissions. For v0.17, see [Enable Fleet RBAC on self-hosted v0.17](#enable-fleet-rbac-on-self-hosted-v0-17).
</Note>

### Configure a Fleet role

LangSmith includes three built-in workspace roles for Fleet. Each role includes every permission of the role before it:

- **Fleet User**: View, run, and rate shared agents, browse workspace skills, and use tools from MCP servers and integrations.
- **Fleet Builder**: Everything in Fleet User, plus create, edit, clone, share, and delete agents and skills, and manage agent connections.
- **Fleet Admin**: Everything in Fleet Builder, plus Fleet usage and limits, workspace MCP servers and integrations, integration access, Fleet webhooks, OAuth providers, workspace secrets, and snapshots.

Assign one of these roles to each Fleet user, and use a [custom role](#create-a-custom-fleet-role) only when none of them fits. To assign a role, see [Assign a role to a user](/langsmith/user-management#assign-a-role-to-a-user).

| Role | Permissions |
| --- | --- |
| Fleet User | <span style={{ whiteSpace: "nowrap" }}>`workspaces:read`<br />`fleet-agents:read`<br />`fleet-agents:invoke`<br />`fleet-skills:read`<br />`mcp-servers:read`<br />`mcp-servers:invoke`<br />`feedback:read`<br />`feedback:update`<br />`feedback:delete`<br />`prompts:read`<br />`deployments:read`</span> |
| Fleet Builder | Fleet User permissions, plus:<br /><span style={{ whiteSpace: "nowrap" }}>`fleet-agents:create`<br />`fleet-agents:update`<br />`fleet-agents:delete`<br />`fleet-skills:create`<br />`fleet-skills:update`<br />`fleet-skills:delete`</span> |
| Fleet Admin | Fleet Builder permissions, plus:<br /><span style={{ whiteSpace: "nowrap" }}>`fleet:read-admin-config`<br />`fleet:write-admin-config`<br />`mcp-servers:create`<br />`mcp-servers:update`<br />`mcp-servers:delete`<br />`workspaces:integrations:manage`<br />`workspaces:manage-secrets`<br />`workspaces:fleet-feedback:read-all`<br />`workspaces:manage`<br />`runs:read`<br />`projects:read`<br />`sandboxes:read`<br />`snapshots:create`<br />`snapshots:delete`<br />`deployments:create`<br />`deployments:update`<br />`deployments:delete`</span> |

Fleet User and Fleet Builder have no access to traces. A Fleet User cannot clone an agent, even one shared at the **Clone** level, because cloning requires `fleet-agents:create`.

<Warning>
Fleet Admin can read every trace in the workspace. It also holds `workspaces:manage`, which lets it change workspace settings, retention, and security policy, and delete the workspace. Fleet Admin cannot manage workspace members or API keys, which require `workspaces:manage-members` and `workspaces:manage-keys`.
</Warning>

#### Understand the LangSmith permissions in Fleet roles

Fleet roles include LangSmith permissions that Fleet pages and API routes check. These permissions apply to the whole workspace, not only to Fleet. For example, the `deployments:*` permissions also grant access to deployment resources outside Fleet.

All Fleet roles include these LangSmith permissions:

| Permission | Needed for |
| --- | --- |
| `workspaces:read` | Access the workspace. |
| <span style={{ whiteSpace: "nowrap" }}>`feedback:read`<br />`feedback:update`<br />`feedback:delete`</span> | Rate agent responses. Fleet shows the rating controls only to roles with all three permissions. Also allows reading, updating, and deleting any feedback in the workspace through the API. |
| `prompts:read` | Read the workspace's [model configurations](/langsmith/model-configurations), which Fleet uses to show which models are available and which API keys they need. Also allows reading, liking, and commenting on prompts in the workspace. |
| `deployments:read` | List the OAuth providers set up in the workspace. Also allows reading every deployment in the workspace. |

Fleet Admin also includes these LangSmith permissions:

| Permission | Needed for |
| --- | --- |
| `workspaces:fleet-feedback:read-all` | List every user's agent ratings in the workspace through the API. Also requires `feedback:read`. |
| `workspaces:manage-secrets` | Add, update, and delete [workspace secrets](/langsmith/fleet/workspace-admin#workspace-secrets), such as model provider and tool API keys. |
| `workspaces:integrations:manage` | Turn built-in integrations on or off in the [workspace integration policy](#workspace-integration-policy), and add, edit, and delete [Fleet webhooks](/langsmith/fleet/webhooks). |
| `workspaces:manage` | List every agent in the workspace, including private agents, and lock or unlock agents through the API. Also allows changing workspace settings, retention, and security policy, and deleting the workspace. |
| <span style={{ whiteSpace: "nowrap" }}>`projects:read`<br />`runs:read`</span> | Show total threads, total runs, and spend on the **Usage** page, which Fleet reads from its tracing projects. Also allows reading every trace in the workspace. |
| `sandboxes:read` | List snapshots, so you can choose a **Snapshot** for an agent's [computer](/langsmith/fleet/computer-use). Also allows reading every sandbox, snapshot, and registry in the workspace. |
| <span style={{ whiteSpace: "nowrap" }}>`snapshots:create`<br />`snapshots:delete`</span> | Build, capture, and delete custom [snapshots](/langsmith/sandbox-snapshots). |
| <span style={{ whiteSpace: "nowrap" }}>`deployments:create`<br />`deployments:update`<br />`deployments:delete`</span> | Set up, edit, and remove OAuth providers. Also allows creating, updating, and deleting any deployment in the workspace. |

### Create a custom Fleet role

To give users a different set of Fleet permissions, create a [custom role](/langsmith/rbac#custom-roles) that starts from the permissions of the closest [Fleet role](#configure-a-fleet-role), then add or remove permissions. Grant each permission explicitly. Create, update, delete, and invoke permissions do not include read permission. Existing agent and skill ownership and sharing checks still apply.

Common additions to a role based on Fleet Builder:

- **View Fleet usage and limits**: Add `fleet:read-admin-config` to view usage reports and usage limits. To show total threads, total runs, and spend on the **Usage** page, also add `projects:read` and `runs:read`, which allow reading every trace in the workspace.
- **Manage Fleet limits**: Add `fleet:write-admin-config` to create, update, and delete usage limits. Grant both Fleet admin permissions to view and manage limits.
- **Choose snapshots for agent computers**: Add `sandboxes:read`.
- **Manage workspace secrets**: Add `workspaces:manage-secrets`.
- **Manage integration access and Fleet webhooks**: Add `workspaces:integrations:manage`.
- **Set up OAuth providers**: Add `deployments:create`, `deployments:update`, and `deployments:delete`.

Custom roles cannot use the names Fleet User, Fleet Builder, or Fleet Admin. A custom role that already has one of these exact names keeps working, but saving any change to it fails with a `409` error unless the change also renames the role.

For more information, see [Workspace administration](/langsmith/fleet/workspace-admin).

### Share agents

Fleet provides granular control over every agent in two dimensions: **who gets access** and **what they can do**.

- **Who**: Share with individual users or your entire workspace.
- **What**: Three permission levels:
  - **Clone**: copy and customize the agent
  - **Run**: use without modifying
  - **Edit**: full access to change instructions, tools, and settings

You can layer these permissions. Give a core team edit access, share run-only with the broader organization, and revoke at any time.

For setup instructions, see [Change access to the agent](/langsmith/fleet/manage-agent-settings#change-access-to-the-agent).

### Enable Fleet RBAC on self-hosted

Fully self-hosted LangSmith v0.18 or later always enforces Fleet role-based access control (RBAC). There is no deployment flag to set.

When you upgrade to v0.18, LangSmith adds the built-in [Fleet roles](#configure-a-fleet-role) and adds Fleet agent and skill permissions to existing custom roles, based on the Prompts permissions each role already holds:

| Existing permission | Added permissions |
| --- | --- |
| `prompts:read` | `fleet-agents:read`, `fleet-agents:invoke`, `fleet-skills:read` |
| `prompts:create` | `fleet-agents:create`, `fleet-skills:create` |
| `prompts:update` | `fleet-agents:update`, `fleet-skills:update` |
| `prompts:delete` | `fleet-agents:delete`, `fleet-skills:delete` |

The built-in Workspace Admin and Workspace Editor roles include every Fleet agent and skill permission, and Workspace Viewer includes `fleet-agents:read`, `fleet-agents:invoke`, and `fleet-skills:read`.

The upgrade does not add any other permissions to custom roles. Fleet denies requests from users whose roles lack the permissions it checks. Before you upgrade, compare the custom roles that Fleet users hold with [Configure a Fleet role](#configure-a-fleet-role), or plan to assign the Fleet roles instead.

If your Helm values set `FLEET_RBAC_PERMISSIONS_ENABLED`, remove it. LangSmith v0.18 does not read it.

#### Enable Fleet RBAC on self-hosted v0.17

Fully self-hosted LangSmith v0.17 installations enable Fleet RBAC with a deployment flag. Cloud and hybrid (BYOC) deployments do not need this step.

<Note>
Fleet RBAC on self-hosted v0.17 requires LangSmith 0.17.44 or a later v0.17 patch.
</Note>

On v0.17, to let users use and manage Fleet, create a [custom workspace role](/langsmith/rbac#custom-roles) with these permissions:

| Area | Permissions | Needed for |
| --- | --- | --- |
| Workspace | <span style={{ whiteSpace: "nowrap" }}>`workspaces:read`</span> | Access the workspace. |
| Agents | <span style={{ whiteSpace: "nowrap" }}>`fleet-agents:read`<br />`fleet-agents:invoke`<br />`fleet-agents:create`<br />`fleet-agents:update`<br />`fleet-agents:delete`</span> | View, run, create, edit, clone, and delete agents. Manage agent connections. |
| Skills | <span style={{ whiteSpace: "nowrap" }}>`fleet-skills:read`<br />`fleet-skills:create`<br />`fleet-skills:update`<br />`fleet-skills:delete`</span> | Browse, create, edit, and delete workspace skills. |
| MCP servers | <span style={{ whiteSpace: "nowrap" }}>`mcp-servers:read`<br />`mcp-servers:invoke`<br />`mcp-servers:create`<br />`mcp-servers:update`<br />`mcp-servers:delete`</span> | Use tools and install, update, or remove workspace integrations. |
| Deployments | <span style={{ whiteSpace: "nowrap" }}>`deployments:read`<br />`deployments:create`<br />`deployments:update`<br />`deployments:delete`</span> | Configure OAuth providers and manage connected accounts through the current Fleet UI. |

Grant each permission explicitly. Create, update, delete, and invoke permissions do not include read permission. Existing agent and skill ownership and sharing checks still apply.

The `deployments:*` permissions also grant access to deployment resources outside Fleet.

To administer Fleet on v0.17, also add:

- **View Fleet usage and limits**: Add `fleet:read-admin-config` to view usage reports and usage limits.
- **Manage Fleet limits**: Add `fleet:write-admin-config` to create, update, and delete usage limits. Grant both Fleet admin permissions to view and manage limits.
- **Manage workspace settings**: Add `workspaces:manage` for workspace settings, integration access controls, and OAuth provider management in **Settings**.

To enable Fleet RBAC:

1. Upgrade all services to the required LangSmith version.
2. Create or update custom roles with the permissions above, and assign them to users. The upgrade does not add Fleet permissions to existing roles.
3. Add the flag to your Helm values, preserving existing `extraEnv` entries:

    ```yaml
    platformBackend:
      deployment:
        extraEnv:
          - name: FLEET_RBAC_PERMISSIONS_ENABLED
            value: "true"
    ```

    The flag defaults to `false`. Setting it to `true` enables Fleet RBAC across all workspaces in the deployment.
4. Apply the values through your normal Helm upgrade process.
5. Call `GET /v1/fleet/config` with your API key and workspace ID. Confirm that the response contains `"rbac_permissions_enabled": true`.

## Agent identity and credentials

Fleet offers two credential models that control how agents authenticate with external tools:

- **Fixed credentials ("Claws")**: The agent uses a single set of credentials regardless of who runs it. Use for shared-resource agents like a team Slack bot where everyone interacts through the same account.
- **User credentials ("Assistants")**: The agent acts on behalf of the individual user who invokes it. Each user authenticates with their own account via OAuth. Use for tools where users have different access levels, like a personal email assistant.

This is configurable per agent, so you can choose the right model for each use case.

For setup instructions, see [Agent identity](/langsmith/fleet/agent-identity).

## Tool access control

Fleet provides layered access control for tools, covering both **custom MCP servers** (user-added, workspace-scoped) and **built-in integrations** (platform-provided, such as Gmail, Slack, and GitHub):

- **[Role-based access control (RBAC)](#role-based-permissions)**: Controls access at the role level.
- **[Attribute-based access control (ABAC)](#attribute-based-access-control)**: Adds per-resource granularity on top of RBAC.
- **[Workspace integration policy](#workspace-integration-policy)**: Provides an admin-controlled enable/disable gate for built-in integrations.

<Note>
Tool access control is an Enterprise feature. If you are interested in this feature, [contact our sales team](https://www.langchain.com/contact-sales).
</Note>

### Role-based permissions

Role-based access control (RBAC) grants or denies access to all MCP servers and integrations in a workspace based on a user's role. Configure roles in **Settings > Roles**.

The following permissions are available for MCP servers and integrations:

| Permission | Description |
|------------|-------------|
| `mcp-servers:read` | Discover and list MCP servers and integrations |
| `mcp-servers:invoke` | Execute tools from MCP servers and integrations |
| `mcp-servers:create` | Create new MCP server configurations |
| `mcp-servers:update` | Modify MCP server configurations |
| `mcp-servers:delete` | Remove MCP server configurations |

<Note>
A role with `mcp-servers:read` and `mcp-servers:invoke` can see and use all MCP servers and integrations in the workspace.
</Note>

For more on RBAC, see [Role-based access control](/langsmith/rbac).

#### Create a role with tool permissions

<Steps>
  <Step title="Open role settings">
    Navigate to **Settings > Roles** and click **Create role**.
  </Step>
  <Step title="Configure MCP Servers permissions">
    Expand the **MCP Servers** section and select the permissions to include. For example, grant `Read` and `Invoke` for users who need to use tools but not manage server configurations.
  </Step>
  <Step title="Assign the role">
    Assign the role to users in the workspace in **Settings > Members**.
  </Step>
</Steps>

### Attribute-based access control

Attribute-based access control (ABAC) adds resource-level granularity on top of RBAC. Admins can tag individual MCP servers or integrations and create policies that grant or restrict access based on those tags.

ABAC operates on two resource types for tools:

| Resource type | Applies to |
|---------------|-----------|
| `mcp_server` | Custom MCP servers added to the workspace |
| `fleet_integration` | Built-in integrations (Gmail, Slack, GitHub, etc.) |

<Note>
A role with no `mcp-servers:*` RBAC permissions can still be granted access to specific tagged resources (e.g. only Notion and Gmail) via an ABAC allow policy. Conversely, a role with broad RBAC access can be restricted from specific resources via an ABAC deny policy.
</Note>

For details on policy structure, operators, and managing policies via the API, see [Attribute-based access control](/langsmith/abac).

### Workspace integration policy

Built-in integrations have an additional control layer: a workspace-level enable/disable toggle managed from **Settings > Integrations > Access control**. This acts as an admin-controlled baseline that runs before per-user RBAC and ABAC.

If an integration is disabled at the workspace level, no user can access it regardless of their role or ABAC policies.

<Note>
The Access control page is only visible to users with the `workspaces:integrations:manage` or `workspaces:manage` permission.
</Note>

### Policy evaluation order

The three layers evaluate in sequence. The evaluation order differs slightly between custom MCP servers and built-in integrations:

**Custom MCP servers:**

```
ABAC deny → RBAC → ABAC allow
```

**Built-in integrations:**

```
Workspace policy gate → ABAC deny → RBAC → ABAC allow
```

At each step:
1. **Workspace policy gate** (integrations only): If the integration is disabled, access is denied. No further evaluation.
2. **ABAC deny**: If a deny policy matches, access is denied. Deny always wins.
3. **RBAC**: If the user's role grants the required permission, access is allowed (unless step 4 is needed).
4. **ABAC allow**: If RBAC does not grant access, an allow policy can still grant it for specific tagged resources.

## Observability and audit trail

Agent actions in Fleet are captured in a structured [LangSmith trace](/langsmith/observability), including tool calls, decisions, and outputs. You can inspect, search, and export traces.

Combined with agent identity and permissions, tracing tells you which agent acted, on whose behalf, with what credentials, and what it did at each step.

## Human-in-the-loop oversight

Fleet provides a [central inbox](https://smith.langchain.com/agents/inbox) for reviewing agent actions across all your agents. You can configure agents to pause and request approval before taking specific actions, then review, approve, edit, or reject from one place.

For setup instructions, see [Human-in-the-loop](/langsmith/fleet/essentials#human-in-the-loop).
