Give a managed deep agent a browser to act on websites without a public API, such as booking a restaurant reservation, or to test an app through its UI after changing its code. The agent can navigate, click, fill forms, and inspect the result. Managed Deep Agents manages the browser and its tools.

Use a direct API when one supports the task. For browser choices and open source setup, see [Browser use with Deep Agents](/oss/deepagents/browser-use).

<Note>
Browser support was added in Managed Deep Agents SDK 0.10. Your workspace also needs access to the LangSmith browser beta.
</Note>

## Declare a browser

Export a named `browser` at the [project root](/langsmith/managed-deep-agents-project-structure):

:::python
```python browser.py
from managed_deepagents import define_browser

browser = define_browser(
    scope="thread",
    idle_ttl_seconds=600,
)
```
:::

:::js
```ts browser.ts
import { defineBrowser } from "managed-deepagents";

export const browser = defineBrowser({
  scope: "thread",
  idleTtlSeconds: 600,
});
```
:::

The CLI discovers this root file. Do not put the declaration inside `browser/` or `sandbox/`: those locations do not enable browser support.

| Option | Default | Description |
| --- | --- | --- |
| `scope` | `"thread"` | Share a browser within one thread or across a signed-in user's threads |
:::python
| `idle_ttl_seconds` | `600` | Seconds of inactivity before the browser stops; accepts `60` through `86400` |
:::
:::js
| `idleTtlSeconds` | `600` | Seconds of inactivity before the browser stops; accepts integers from `60` through `86400` |
:::

## Choose a scope

| Scope | Browser state | Use it for |
| --- | --- | --- |
| `"thread"` (default) | One browser per conversation; authorized participants share it across turns | Multiplayer collaboration, a reservation workflow, or an independent app test |
| `"user"` | One browser per authenticated person, with a separate window for each thread and shared cookies and logins | Reusing a website login across conversations |

Thread scope starts each new conversation without another thread's cookies or logins. Later runs in the same thread reuse its saved state. Starting another thread does not delete the previous browser.

For user scope, change the declaration:

:::python
```python browser.py
from managed_deepagents import define_browser

browser = define_browser(scope="user", idle_ttl_seconds=600)
```
:::

:::js
```ts browser.ts
import { defineBrowser } from "managed-deepagents";

export const browser = defineBrowser({ scope: "user", idleTtlSeconds: 600 });
```
:::

For example, sign in to a booking site in one conversation, then request another reservation in a new thread. The same user's new window can reuse the login. Other authenticated people get different browsers. User scope follows [verified caller identity](/langsmith/managed-deep-agents-identity), not a name in a prompt; non-person principals use thread scope.

Shared login state is not account isolation: logging out or switching accounts can affect the person's other threads. Coordinate purchases and bookings across conversations. Finishing a run releases the client, not the login; the idle timeout stops the browser rather than logging out. Website expiry or browser replacement can still invalidate saved state.

## Browser tools

Managed Deep Agents includes these tools automatically:

| Tool | What it does |
| --- | --- |
| `browser_snapshot` | Reads the active page's accessibility tree and assigns element IDs for interactions |
| `browser_run` | Navigates and interacts through JavaScript or batches of actions against snapshot IDs |
| `browser_screenshot` | Captures the page; an optional absolute `path` saves the image to the agent's sandbox |
| `browser_handoff` | Gives a person control of the window for login, CAPTCHA, or two-factor authentication |

Take a new snapshot after navigation or when element IDs become stale. Browsing does not require an agent [sandbox](/langsmith/managed-deep-agents-sandboxes); saving screenshot files does.

## Hand off the browser

Human handoff lets you sign in or handle a page the agent cannot complete on its own. The agent calls `browser_handoff(reason)` to give you control of its thread's browser window.

Custom clients must render the handoff artifact to provide the embedded browser or browser link.

To complete a login and return control:

1. Ask the agent to perform the website task. If login, CAPTCHA, or two-factor authentication requires your input, the agent requests a handoff and explains why.
2. Use the embedded browser or open the browser link supplied by your client. The proposed Studio interface shows a **The agent needs you in the browser** card with an **Open in new tab** option. Enter credentials directly on the website, not in chat, and complete any required authentication steps.
3. Click **Hand back** in the browser window when you are finished.
4. A separate watcher run detects that you handed the browser back and queues a notification run on the original conversation. The agent inspects the current page and continues from the resulting state, rather than assuming login succeeded.

<Note>
Studio screenshot placeholder: show the handoff request, website login, and **Hand back** control.
</Note>

While you control the window, the agent's browser tools cannot act on it. Handoff returns immediately, so the agent can perform other work. The link expires after 15 minutes; expiry ends the handoff but does not prove that the website task is complete.

The watcher runs as its own graph on a separate thread, rather than as a background task tied to the agent's process. It does not wake a conversation paused on a separate approval or credential interrupt; complete that interrupt through its normal interface. A newer handoff supersedes the previous one. If the watcher cannot start, you can still use the browser and hand it back, then send a new message in the original conversation to continue.

<Warning>
Keep handoff links private: anyone with a valid link can control the browser. Do not store passwords in prompts, chat messages, or agent-written files. Sign in directly during handoff, and avoid exposing secrets in page content that the agent can later inspect. Browser scope controls session reuse; it is not a password vault.
</Warning>

## Configure a graph factory

Set `browser` explicitly in a [graph factory](/langsmith/managed-deep-agents-agent-definition#select-configuration-per-run) to choose the scope and idle timeout for a run:

:::python
```python agent.py
from managed_deepagents import ManagedServerRuntime, define_browser, define_deep_agent


def agent(runtime: ManagedServerRuntime):
    return define_deep_agent(
        name="browsing",
        browser=define_browser(scope="user", idle_ttl_seconds=900),
    )
```
:::

:::js
```ts agent.ts
import { defineBrowser, defineDeepAgent, type ManagedServerRuntime } from "managed-deepagents";

export function agent(runtime: ManagedServerRuntime) {
  return defineDeepAgent({
    name: "browsing",
    browser: defineBrowser({ scope: "user", idleTtlSeconds: 900 }),
  });
}
```
:::

Keep the root browser declaration even when the factory selects a different configuration. It enables browser support and installs the deployment's browser dependencies. A factory cannot add a browser without that file.

To disable browser tools for a run, pass `browser=None` in Python or `browser: null` in TypeScript. Pass a browser definition, not a middleware instance. Static agent definitions configure browser support in the declaration file instead.
