## Components and pods

Use this table to find each component in your cluster. Run `kubectl get deploy,sts,jobs -n <namespace>` and compare the names.

| Component | Kubernetes object | Description |
|---|---|---|
| Frontend | `langsmith-frontend` | Serves the LangSmith UI. |
| Backend | `langsmith-backend` | Serves most of the LangSmith API. |
| Platform backend | `langsmith-platform-backend` | Receives runs and feedback from clients and queues them for writing. Sends trace queries to SmithDB. |
| Queue | `langsmith-queue` | Runs automation rules, including online evaluations. |
| Ingest queue | `langsmith-ingest-queue` | Writes queued runs, feedback, and deletes to SmithDB. |
| SmithDB cluster manager | `langsmith-smithdb-cluster-manager` | Decides which SmithDB pod handles which tenant and project, so that related requests go to the same pod. |
| SmithDB query | `langsmith-smithdb-query`<br />`langsmith-smithdb-stats-query`<br />`langsmith-smithdb-run-rules`<br />`langsmith-smithdb-mutations` | Answers queries, and applies feedback and deletes. The optional pools keep heavy load away from UI and API reads. |
| SmithDB ingestion | `langsmith-smithdb-ingestion` | Stores new runs, and serves the newest runs to queries. |
| SmithDB compaction scheduler | `langsmith-smithdb-compaction` | Plans compaction work, and runs garbage collection and retention. Runs as a single instance. |
| SmithDB compaction worker | `langsmith-smithdb-compaction-worker` | Does the compaction work: merges and rewrites stored data. |
| SmithDB metastore migration | `langsmith-smithdb-metastore-migration` | Prepares the metastore during install and upgrade. |
| SmithDB migration | `langsmith-smithdb-migration` | Copies historical data from ClickHouse. Optional. |
| Redis, PostgreSQL, ClickHouse | `langsmith-redis`<br />`langsmith-postgres`<br />`langsmith-clickhouse` | LangSmith datastores. They run in the cluster only if you do not use external services. |

Names come from the chart templates (`<release>-smithdb-<component>`). Confirm them against your deployment.

## Write path

<img
  className="block dark:hidden"
  src="/images/langsmith/smithdb/write-path.svg"
  alt="The platform backend adds a task to Redis. An ingest queue worker writes the runs to SmithDB ingestion, which writes segments to object storage and segment rows to the metastore, then acknowledges the write."
/>

<img
  className="hidden dark:block"
  src="/images/langsmith/smithdb/write-path-dark.svg"
  alt="The platform backend adds a task to Redis. An ingest queue worker writes the runs to SmithDB ingestion, which writes segments to object storage and segment rows to the metastore, then acknowledges the write."
/>

The platform backend receives runs from the SDK and adds a **task** (a batch of runs) to the ingestion queue in Redis (1). An ingest queue worker takes the task (2) and sends its runs to SmithDB ingestion (3). Ingestion keeps the rows in memory for a short time. Then it writes them to object storage as an **L0 segment** (4). A segment is a data file that SmithDB never changes after it writes it. Ingestion also records each segment in the **metastore**, a PostgreSQL database (5). When the segment is in object storage and in the metastore, the data is durable. Ingestion then sends an **ack** to the worker (6), and the worker removes the task from Redis. If the write fails, the task stays in Redis, and the worker tries it again later. Thus, a slow write is first visible as a larger queue in Redis. Later, ingestion merges the small L0 segments into a larger **L1 segment** and gives it to compaction. Until then, ingestion keeps copies of the L0 segments on its **disk cache**. The disk cache never holds the only copy of the data.

## Read path

<img
  className="block dark:hidden"
  src="/images/langsmith/smithdb/read-path.svg"
  alt="The platform backend queries SmithDB query, which reads the segment list from the metastore and segments from its disk cache, object storage, or the ingestion pod that wrote them."
/>

<img
  className="hidden dark:block"
  src="/images/langsmith/smithdb/read-path-dark.svg"
  alt="The platform backend queries SmithDB query, which reads the segment list from the metastore and segments from its disk cache, object storage, or the ingestion pod that wrote them."
/>

The platform backend sends a query to SmithDB query (1). The backend does not query SmithDB itself. It sends trace reads through the platform backend. In large installations, LangSmith sends run statistics, automation rules, and feedback and deletes to the optional query pools. The read path is the same for each pool. Query first asks the metastore which segments contain data for the tenant, the project, and the time range (2). Then it reads these segments. If a segment is on its **disk cache**, query reads it from there (3). If not, query reads it from object storage (4) and keeps a copy on its disk cache for the next query. Query reads the newest data from the ingestion pod that wrote it, instead of from object storage (5). If that pod is not available, query reads the data from object storage. Query then merges all segments into one result, removes deleted and expired rows, and sends the result to the platform backend (6). The more segments a query must read, the slower it is. **Compaction** merges small segments into larger segments to keep this number low. If compaction is late, queries become slower, and query rejects queries that must read too many segments.

## Feedback path

<img
  className="block dark:hidden"
  src="/images/langsmith/smithdb/feedback-path.svg"
  alt="The platform backend adds feedback to the Redis feedback queue. An ingest queue worker sends it to the SmithDB mutations pool, which stores it in the metastore. Compaction later writes it to object storage."
/>

<img
  className="hidden dark:block"
  src="/images/langsmith/smithdb/feedback-path-dark.svg"
  alt="The platform backend adds feedback to the Redis feedback queue. An ingest queue worker sends it to the SmithDB mutations pool, which stores it in the metastore. Compaction later writes it to object storage."
/>

Feedback has its own path, because SmithDB stores feedback apart from runs. The platform backend receives feedback from the SDK and the UI, directly or through the backend. It adds a task to the **feedback queue** in Redis (1). This queue is not the ingestion queue. An ingest queue worker takes the task (2) and sends the feedback to the SmithDB **mutations** pool (3). If the mutations pool is not enabled, the query pool gets the feedback. SmithDB stores each feedback as a row in the metastore (4). Then it sends the ack (5), and the worker removes the task from Redis. Queries read new feedback directly from the metastore, thus feedback is visible immediately. Later, a **feedback compaction** job reads the new rows (6) and writes the feedback into files next to the run segments in object storage (7). This occurs after approximately 60 seconds, or when 5,000 new feedback rows wait. Thus, a large quantity of feedback adds load to the metastore first.

## Terms

| Term | Meaning |
|---|---|
| Run | One step of a trace, for example an LLM call or a tool call. |
| Feedback | A score or a comment on a run, from a user, an evaluator, or an automation rule. |
| Task | One unit of work in a Redis queue, for example a batch of runs or of feedback. Each worker pod processes several tasks at the same time. |
| Ingestion queue, feedback queue | The two Redis queues on the trace path. The ingestion queue holds runs. The feedback queue holds feedback. The ingest queue workers process both. |
| Segment | One data file in object storage, plus its row in the metastore. SmithDB never changes a segment after it writes it. |
| Partition | The runs of one tenant, one project, and one day. Ingestion writes each partition to its own segments. |
| L0 segment | A small segment. Ingestion writes one for each partition every 500 ms or every 5,000 rows. |
| L1 segment | A larger segment. Ingestion merges the L0 segments of one partition into it. |
| Ack | The message from SmithDB to the worker that the data is durable. The worker removes the task from Redis only after the ack. |
| Metastore | The PostgreSQL database of SmithDB. It keeps a record of each segment, and stores new feedback. |
| Disk cache | The local disk of a SmithDB pod. It holds copies of data only, never the only copy. |
| Query pool | A group of SmithDB query pods for one type of request: query, stats-query, run-rules, or mutations. |
| Delete | SmithDB never changes a segment. Thus, a delete does not remove rows immediately. The query service finds the rows and records them in the metastore as a deletion vector. Queries then hide these rows. Later, compaction rewrites the segment without them. |
| Compaction | Background work that merges small segments into larger segments, writes feedback into files, and removes expired and deleted data. |
| Slice | A range of the key space that the cluster manager gives to a SmithDB pod. For ingestion, the key is the tenant and the project. For queries, the key is the tenant. |
