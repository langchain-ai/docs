LangSmith for Coding Agents gives IT and engineering leaders a single view of what their coding agent budget is buying across the whole organization. It connects every session to the pull request it opened, so you can see cost per merged PR across harnesses and model providers and hold teams accountable for how the budget is spent.

<Note>
LangSmith for Coding Agents is in public beta on LangSmith Cloud. Coding agent traces count toward your regular LangSmith tracing usage.
</Note>

## Key concepts

### Outcomes

An outcome links a [thread](/langsmith/threads) to a GitHub pull request or GitLab merge request. One thread can open several PRs, and several threads can contribute to the same PR. LangSmith groups spend by PR state: open, closed, or merged. Spend that never led to a PR appears alongside those groups rather than being dropped.

Cost per merged PR gives engineering and finance a shared unit of measure to start from. A merge does not prove the code is good, and useful agent work does not always become a PR, so the coding agent overview shows comprehensive spend including sessions without a PR outcome.

### Coding agents dashboard

The coding agent overview page aggregates cost across every coding agent you trace and ties it to the pull requests your agents worked on. At the top, a set of high-level metrics reads like an executive summary, and you can click in to see how each one changes over time.

Additional charts break down cost by:

- Model
- GitHub user
- PR status (open, closed, or merged)

Ready-made views highlight your 20 most expensive attributed PRs and cost by thread length. Every outlier links back to the threads and sessions behind it, so you can open the exact conversation and inspect what the agent did.

## Roll out to your organization

The recommended path for IT managers is to deploy the LangSmith plugin via MDM software, connect GitHub once at the organization level, and then use the coding agent overview to monitor cost across every team.

### Step 1: Deploy the plugin with MDM

Each coding agent has its own plugin. Install it on every machine using your existing MDM tool (such as Jamf or Microsoft Intune) so engineers do not have to opt in individually.

|---|---|
| Claude Code | [Deploy to your organization](/langsmith/trace-claude-code#deploy-to-your-organization) |
| OpenAI Codex | [Deploy to your organization](/langsmith/trace-with-codex#deploy-to-your-organization) |
| Cursor | [Deploy to your organization](/langsmith/trace-with-cursor#deploy-to-your-organization) |
| GitHub Copilot | [Configure tracing](/langsmith/trace-with-vscode-copilot#configure-tracing) |
| Deep Agents | [Trace Deep Agents](/langsmith/trace-deep-agents) |

Each guide covers the MDM-deployable managed settings file at `~/.langsmith-plugins/managed.json`. This file is read by the Claude Code, Cursor, and Codex plugins. Settings in it override users' own config files and environment variables. Admins can lock the LangSmith workspace, the agent ID, and [strict auth](/langsmith/trace-claude-code#require-a-working-sign-in) from one place. See [Lock settings](/langsmith/trace-claude-code#lock-settings) for the format and security requirements.

<Tip>
Start with one agent and one repository. Spend appears broken out by pull request as soon as the first threads come in.
</Tip>

### Step 2: Connect GitHub

Connect your GitHub account in LangSmith settings so that LangSmith can link pull requests to traces. LangSmith reads PR state (open, closed, or merged) and attributes cost to the threads that opened each PR.

### Step 3: Open the coding agent overview

Navigate to the coding agent overview page in LangSmith. The dashboard aggregates data across every harness and model provider you have connected.

## What to monitor

### Find outlier spend

Sort by attributed cost to see which pull requests were the most expensive to produce. Each one traces back to its threads, the models involved, and the GitHub user behind it. This is how you catch usage that falls outside expected patterns—for example, a single session that cost as much as a week's normal spend.

### Set a thread policy and verify it

Spend concentrates in long threads, since every new turn carries the conversation so far along with it. Starting a fresh thread avoids paying for that context again. Set a turn-limit policy in a custom plugin or at your model gateway, then use the cost-by-thread-length view to confirm that behavior changed after the policy went into effect.

### Measure a model change

When you move engineers from one model to another, compare usage and cost before and after the switch. Outcomes are in the same view, so you can also check whether the new model still gets work merged.

### Keep skills current

Skill calls are traced too. You can see which skills your team's agents rely on most and which ones have gone stale and need an update.
