A dynamic agent selects its configuration at the start of each run from the run's context. One deployment can serve several audiences, tasks, or repositories without a separate agent for each variation.

<ManagedDeepAgentsPublicBetaNote />

For example, using dynamic context, a support agent can give internal staff a stronger model and an internal case tool, while customers get a smaller model and a help center search tool. A coding agent can pick instructions, skills, and sandbox settings based on the repository a task targets. Each run resolves its own configuration, so concurrent runs don't affect each other.

## Define a dynamic agent

:::python
Decorate a resolver with `@dynamic` and assign it to the module-level `agent`. The resolver receives the run context and returns `define_deep_agent(...)`:

```python agent.py
from managed_deepagents import DeepAgentDefinition, ManagedRunContext, define_deep_agent, dynamic
from tools.support import customer_lookup, inspect_internal_case


@dynamic
def build_agent(ctx: ManagedRunContext) -> DeepAgentDefinition:
    internal = isinstance(ctx, dict) and ctx.get("role") == "internal"
    return define_deep_agent(
        name="support",
        model="openai:gpt-5.5" if internal else "openai:gpt-5-mini",
        tools=[inspect_internal_case] if internal else [customer_lookup],
        instructions="Help support staff." if internal else "Help customers.",
        skills=["./skills/internal-support" if internal else "./skills/customer-support"],
    )


agent = build_agent
```

The resolver can be synchronous or `async`.
:::

:::js
Wrap a resolver in `dynamic(...)` and export it as `agent`. The resolver receives the run context and returns `defineDeepAgent(...)`:

```ts agent.ts
import { defineDeepAgent, dynamic } from "managed-deepagents";
import { customerLookup, inspectInternalCase } from "./tools/support";

export const agent = dynamic((ctx) => {
  const internal = "role" in ctx && ctx.role === "internal";

  return defineDeepAgent({
    name: "support",
    model: internal ? "openai:gpt-5.5" : "openai:gpt-5-mini",
    tools: internal ? [inspectInternalCase] : [customerLookup],
    instructions: internal ? "Help support staff." : "Help customers.",
    skills: [internal ? "./skills/internal-support" : "./skills/customer-support"],
  });
});
```

The resolver can be synchronous or `async`.
:::

The `name` must be an inline string literal in the returned definition. `mda build` reads it without calling the resolver and uses it as the graph ID and default deployment name. See [Build and deploy](#build-and-deploy).

## Pass run context

Clients pass application data in the `context` field of the Agent Server run request:

:::python
```python
await client.runs.create(
    thread_id,
    assistant_id,
    input={"messages": [{"role": "user", "content": "Where is my order?"}]},
    context={"role": "customer"},
)
```
:::

:::js
```ts
await client.runs.create(threadId, assistantId, {
  input: { messages: [{ role: "user", content: "Where is my order?" }] },
  context: { role: "customer" },
});
```
:::

:::python
The resolver's context type is `ManagedRunContext`. Direct API runs receive the application context the client sent. Runs from a managed [channel](/langsmith/managed-deep-agents-channels), such as Slack, receive MDA's channel context instead. Check the shape before reading application fields, as `isinstance(ctx, dict)` does in the earlier example.
:::

:::js
The resolver's context type is `ManagedRunContext`. Direct API runs receive the application context the client sent. Runs from a managed [channel](/langsmith/managed-deep-agents-channels), such as Slack, receive `{ channel: … }` instead. Check for a field before reading it, as `"role" in ctx` does in the earlier example.
:::

<Warning>
Run context is application data, not verified identity. A client can send any value. Derive security-sensitive roles from authenticated server state, and have [tools](/langsmith/managed-deep-agents-tools) check authorization when they are called.
</Warning>

## What a resolver can select

A dynamic agent can select `model`, `tools`, `subagents`, `middleware`, `instructions`, `skills`, `mcp`, and `sandbox`. Standard agent fields behave as described in [Agent definition](/langsmith/managed-deep-agents-agent-definition#parameters).

The managed fields fall back to the project's discovered resources when omitted:

:::python
| Field | Omitted | Empty | Set |
|---|---|---|---|
| `instructions=` | Uses [`instructions.md`](/langsmith/managed-deep-agents-instructions). | `""` clears authored instructions. | Replaces `instructions.md` for the run. |
| `skills=` | Exposes every discovered project skill. | `[]` exposes no skills. | Exposes only the selected skills. See [Select skills](#select-skills). |
| `mcp=` | Uses the discovered MCP declaration. | `[]` exposes no MCP tools. | Replaces the discovered MCP declaration. See [Select MCP servers](#select-mcp-servers). |
| `sandbox=` | Uses the discovered sandbox. | `None` disables the sandbox for the run. | Replaces the discovered sandbox options. See [Select sandbox options](#select-sandbox-options). |
:::

:::js
| Field | Omitted | Empty | Set |
|---|---|---|---|
| `instructions` | Uses [`instructions.md`](/langsmith/managed-deep-agents-instructions). | `""` clears authored instructions. | Replaces `instructions.md` for the run. |
| `skills` | Exposes every discovered project skill. | `[]` exposes no skills. | Exposes only the selected skills. See [Select skills](#select-skills). |
| `mcp` | Uses the discovered MCP declaration. | `[]` exposes no MCP tools. | Replaces the discovered MCP declaration. See [Select MCP servers](#select-mcp-servers). |
| `sandbox` | Uses the discovered sandbox. | `null` disables the sandbox for the run. | Replaces the discovered sandbox options. See [Select sandbox options](#select-sandbox-options). |
:::

These managed fields are available only in a dynamic agent. A static agent continues to configure them through project files. See [Project structure](/langsmith/managed-deep-agents-project-structure).

[Memory](/langsmith/managed-deep-agents-memory) is not selectable. Declare it in the root memory file. Its `allow(context)` policies already decide access for each run.

### Select skills

Each entry in the skills list is either the path of an authored skill directory under `skills/` or a generated skill definition. After the resolver returns, MDA validates the selection, copies the selected skill files into a read-only view, and mounts that view at `/skills` for the run.

:::python
Pass authored skill paths as strings relative to the project root, such as `"./skills/refunds"`. Convert `Path` values with `str()`.

```python
define_deep_agent(
    name="support",
    skills=["./skills/refunds", "./skills/escalations"],
)
```
:::

:::js
```ts
defineDeepAgent({
  name: "support",
  skills: ["./skills/refunds", "./skills/escalations"],
});
```
:::

A path must point to a skill directory that exists in the project. A generated skill cannot reuse the name of an authored skill. To write skills, see [Skills](/langsmith/managed-deep-agents-skills).

### Select MCP servers

:::python
Pass a list of definitions returned by `define_mcp(...)`. A non-empty list replaces the project's discovered MCP declaration for the run. Other connectors stay active, and the selected servers go through the same tool loading and credential checks.
:::

:::js
Pass an array of definitions returned by `defineMcp(...)`. A non-empty array replaces the project's discovered MCP declaration for the run. Other connectors stay active, and the selected servers go through the same tool loading and credential checks.
:::

Build the definition in a helper that takes the run context. This example gives every run the LangChain docs and Notion servers, and adds Linear for the engineering team:

:::python
```python config/mcp.py
from managed_deepagents import ManagedRunContext, connections, define_mcp


def get_dynamic_mcp(ctx: ManagedRunContext):
    servers = {
        "langchainDocs": {
            "transport": "http",
            "url": "https://docs.langchain.com/mcp",
            # Select by raw MCP tool name; MDA adds the server-name prefix at runtime.
            "include_tools": ["search_docs_by_lang_chain"],
        },
        "notion": {
            "transport": "http",
            "url": "https://mcp.notion.com/mcp",
            "connection": connections.get("notion", {"type": "user"}),
        },
    }

    if isinstance(ctx, dict) and ctx.get("team") == "engineering":
        servers["linear"] = {
            "transport": "http",
            "url": "https://mcp.linear.app/mcp",
            "connection": connections.get("linear", {"type": "user"}),
        }

    return define_mcp(servers=servers)
```
:::

:::js
```ts config/mcp.ts
import { connections, defineMcp, type ManagedRunContext } from "managed-deepagents";

export function getDynamicMcp(ctx: ManagedRunContext) {
  const engineering = "team" in ctx && ctx.team === "engineering";

  return defineMcp({
    servers: {
      langchainDocs: {
        transport: "http",
        url: "https://docs.langchain.com/mcp",
        // Select by raw MCP tool name; MDA adds the server-name prefix at runtime.
        includeTools: ["search_docs_by_lang_chain"],
      },
      notion: {
        transport: "http",
        url: "https://mcp.notion.com/mcp",
        connection: connections.get("notion", { type: "user" }),
      },
      ...(engineering
        ? {
            linear: {
              transport: "http",
              url: "https://mcp.linear.app/mcp",
              connection: connections.get("linear", { type: "user" }),
            },
          }
        : {}),
    },
  });
}
```
:::

<Note>
Keep these helpers out of `tools/mcp.*`. That file is the static MCP declaration, and `mda build` requires it to export `mcp`.
</Note>

For server options such as tool allowlists and credentials, see [MCP connectors](/langsmith/managed-deep-agents-mcp-connectors) and [Manage connections](/langsmith/managed-deep-agents-connections).

### Select sandbox options

:::python
Return a definition from `define_sandbox(...)` to replace the discovered sandbox options for the run, or `None` to disable the sandbox. This helper gives build tasks longer timeouts and turns the sandbox off for runs that only answer questions:

```python config/sandbox.py
from managed_deepagents import ManagedRunContext, define_sandbox


def get_dynamic_sandbox(ctx: ManagedRunContext):
    task = ctx.get("task") if isinstance(ctx, dict) else None

    if task == "question":
        return None
    if task == "build":
        return define_sandbox(idle_ttl_seconds=1800, default_timeout=1200)
    return define_sandbox(idle_ttl_seconds=600, default_timeout=600)
```
:::

:::js
Return a definition from `defineSandbox(...)` to replace the discovered sandbox options for the run, or `null` to disable the sandbox. This helper gives build tasks longer timeouts and turns the sandbox off for runs that only answer questions:

```ts config/sandbox.ts
import { defineSandbox, type ManagedRunContext } from "managed-deepagents";

export function getDynamicSandbox(ctx: ManagedRunContext) {
  const task = "task" in ctx ? ctx.task : undefined;

  if (task === "question") {
    return null;
  }
  if (task === "build") {
    return defineSandbox({ idleTtlSeconds: 1800, defaultTimeout: 1200 });
  }
  return defineSandbox({ idleTtlSeconds: 600, defaultTimeout: 600 });
}
```
:::

Sandbox setup and image baking stay in the `sandbox/` directory. For sandbox options, see [Sandboxes](/langsmith/managed-deep-agents-sandboxes).

### Use the helpers in the resolver

Call both helpers from the resolver with the same context:

:::python
```python agent.py
from config.mcp import get_dynamic_mcp
from config.sandbox import get_dynamic_sandbox
from managed_deepagents import DeepAgentDefinition, ManagedRunContext, define_deep_agent, dynamic


@dynamic
def build_agent(ctx: ManagedRunContext) -> DeepAgentDefinition:
    return define_deep_agent(
        name="support",
        mcp=[get_dynamic_mcp(ctx)],
        sandbox=get_dynamic_sandbox(ctx),
    )


agent = build_agent
```
:::

:::js
```ts agent.ts
import { defineDeepAgent, dynamic } from "managed-deepagents";
import { getDynamicMcp } from "./config/mcp";
import { getDynamicSandbox } from "./config/sandbox";

export const agent = dynamic((ctx) =>
  defineDeepAgent({
    name: "support",
    mcp: [getDynamicMcp(ctx)],
    sandbox: getDynamicSandbox(ctx),
  })
);
```
:::

## Build and deploy

`mda build` detects a dynamic agent without calling the resolver, because run context exists only at runtime. As a result:

- **The name must be static.** The build reads the inline string-literal `name` from the returned definition and uses it as the graph ID and default deployment name. If the name is computed or the resolver has several possible return statements, the build falls back to `agent`. `mda deploy --name` changes the deployment name, not the graph ID.
- **Model dependencies are not detected.** Add the integration package for every model the resolver can return to the project's dependencies.

:::python
List those packages in `pyproject.toml`.
:::

:::js
List those packages in `package.json`.
:::

## Write a resolver

- **Keep the resolver repeatable and free of side effects.** MDA can call the resolver again for retries and resumes. Do not create records, call external APIs, or mutate state in the resolver.
- **Handle an empty context.** Agent Server sometimes loads the graph for inspection, such as schema requests, without a run. In that case MDA calls the resolver with `{}`. A real run resolves again with the actual context.
- **Keep interrupting middleware stable.** Do not select middleware that can interrupt a run based on context. A resumed run rebuilds the graph, and the middleware that raised the interrupt must still be present.
- **Use middleware for changes within a run.** The resolver runs once per run. To change behavior between model steps in the same run, use [custom middleware](/langsmith/managed-deep-agents-middleware).
