A private BYOC data plane exposes its load balancer inside your data plane VPC. Applications in a different AWS account cannot reach it without an explicit cross-account network path. Two approaches work: **AWS PrivateLink** (recommended) and **VPC peering or transit gateway** (when CIDR ranges do not overlap).

<Note>
LangChain provisions a PrivateLink endpoint for the EKS control plane only. There is no LangChain-managed endpoint service for application traffic. You create and manage the endpoint service for your own use.
</Note>

The steps below apply to a [customer-owned VPC (BYOVPC)](/langsmith/byoc-byovpc-aws). Whether the same approach holds when LangChain creates the VPC is pending confirmation from the LangChain infrastructure team.

## AWS PrivateLink (recommended)

PrivateLink creates a private endpoint in each consumer VPC without routing between CIDR ranges, so it works even when IP ranges overlap.

### In the data plane account

1. Identify the Network Load Balancer (NLB) for the data plane ingress. Find it in the AWS console or by describing load balancers with the tag `langsmith-data-plane=<data-plane-name>`.
2. Create a **VPC endpoint service** backed by that NLB. Set acceptance mode to **auto** or **manual** depending on your security policy.
3. Add each consumer AWS account as a **principal** allowed to create an interface endpoint for the service.
4. Note the endpoint service name (for example, `com.amazonaws.vpce.us-east-1.vpce-svc-xxxxxxxxxxxxxxxxx`).

<Warning>
Do not modify the NLB itself. LangSmith reconciles the data plane on a regular cadence and reverts manual changes to managed resources. If the ingress mode or subnets change, LangChain coordinates any NLB updates with you.
</Warning>

### In each consumer account

1. Create a **VPC interface endpoint** for the endpoint service name from the previous step, in the VPC where your application runs.
2. Create a **private Route 53 hosted zone** for the data plane hostname (for example, `<data-plane-name>.aws.smith.langchain.com`), associated with the consumer VPC.
3. Add an alias or CNAME record in that hosted zone pointing the data plane hostname to the interface endpoint's DNS name.

Routing the hostname through Route 53 ensures that the TLS certificate served by the data plane still matches the hostname and that certificate validation succeeds.

Your applications then use the standard data plane API URL from **Settings > Data Planes** without any change. DNS resolves it to the interface endpoint in the consumer VPC.

## VPC peering or transit gateway

VPC peering and transit gateways work when CIDR ranges do not overlap between the data plane VPC and the consumer VPCs.

**VPC peering:**

1. In the data plane account, create a peering connection request from the data plane VPC to the consumer VPC.
2. In the consumer account, accept the request.
3. Add routes in both VPCs so traffic to each other's CIDR range traverses the peering connection.
4. Update any network ACLs or security groups that need to allow the peered ranges.

**Transit gateway:**

Attach both VPCs to a shared transit gateway and configure route tables so each VPC can reach the other. This scales to many consumer VPCs without a full mesh of peering connections.

With either approach, your applications reach the data plane at its API URL directly, with no Route 53 change required. DNS resolves the hostname to the private load balancer IP address within the data plane VPC, and routing carries the traffic across the peering or gateway connection.
