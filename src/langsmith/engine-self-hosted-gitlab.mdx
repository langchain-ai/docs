[LangSmith Engine](/langsmith/engine) reads GitLab projects and opens merge requests with an access token that a workspace admin saves in the LangSmith UI. GitLab needs no App registration, Helm values, or Kubernetes Secrets: workspace admins [connect GitLab](/langsmith/engine-repositories#connect-gitlab) the same way as on LangSmith Cloud. This page covers the network access and certificate trust that the connection depends on.

- **BYOC**: No data plane configuration is needed. See [Connect GitLab on BYOC](#connect-gitlab-on-byoc).
- **Self-hosted**: An operator confirms network access and, for a GitLab instance on a private network, allows private addresses and trusts its certificate authority. See [Configure GitLab on self-hosted](#configure-gitlab-on-self-hosted).

## Connect GitLab on BYOC

On a [BYOC](/langsmith/byoc) data plane, the data plane serves GitLab connection, project, and webhook requests, and stores each workspace's GitLab connection. You do not set environment variables or Helm values.

The data plane and your GitLab instance must be able to reach each other:

- **Data plane to GitLab**: The GitLab instance must be reachable from the data plane over HTTPS on port 443.
- **GitLab to data plane**: GitLab delivers merge request webhooks to the data plane's API hostname. After a workspace admin connects GitLab, the exact URL appears as **Webhook URL** under **Connection health** in **Settings** > **Integrations** > **GitLab**.

A GitLab instance that resolves to private IP addresses requires data plane settings that LangChain manages. Contact your LangChain account team.

Then, a workspace admin [connects GitLab](/langsmith/engine-repositories#connect-gitlab), and workspace users [add GitLab projects](/langsmith/engine-repositories#add-gitlab-projects).

## Configure GitLab on self-hosted

On self-hosted LangSmith, an operator confirms that LangSmith and GitLab can reach each other before a workspace admin connects GitLab.

### Before you start

You need:

- **Engine and Sandboxes**: A working [self-hosted Engine deployment](/langsmith/engine-self-hosted) and permission to update its Helm values and workloads.
- **GitLab**: GitLab.com, or a self-managed instance running GitLab 16.10 or later. The instance must be served over HTTPS on port 443, without a relative URL root such as `/gitlab`.
- **Network access**: Connections from LangSmith to GitLab, and from GitLab to LangSmith's webhook URL. See [Allow network access](#allow-network-access).

### Allow network access

All connections use HTTPS. Configure DNS, routing, and certificate trust for each source:

| Source | Destination | Purpose |
| --- | --- | --- |
| Platform backend (`platformBackend`) | GitLab instance | Check the token, list projects, read branches and diffs, open merge requests, and register webhooks. |
| Ingest queue workers (`ingestQueue`) | GitLab instance | Renew access tokens and keep merge request webhooks registered. |
| Sandbox hosts | GitLab instance | Clone projects and push fix branches. |
| GitLab instance | LangSmith webhook URL | Report merged and closed merge requests. |

Engine's sandboxes allow the workspace's GitLab host on port 443 for runs that track GitLab projects. You do not configure sandbox egress for GitLab.

LangSmith builds the webhook URL from `config.hostname` and `config.basePath`, in the form `https://langsmith.example.com/api/v1/platform/gitlab/webhooks/<workspace-id>/<connection-id>`. A deployment with a base path includes it, for example `https://langsmith.example.com/langsmith/api/v1/platform/gitlab/webhooks/...`. After a workspace admin connects GitLab, the exact URL appears as **Webhook URL** under **Connection health**.

The webhook URL must be reachable from GitLab. GitLab.com sends webhooks from the internet. A self-managed instance blocks webhooks to private addresses by default. If your LangSmith hostname resolves to a private address, a GitLab administrator allows it under **Admin** > **Settings** > **Network** > **Outbound requests**, either by adding the LangSmith hostname to **Local IP addresses and domain names that hooks and integrations can access** or by selecting **Allow requests to the local network from webhooks and integrations**. See GitLab's [webhook security settings](https://docs.gitlab.com/security/webhooks/).

If GitLab cannot deliver webhooks, Engine can still read code, generate fixes, and open merge requests. Merged merge requests do not complete their issues until delivery works.

### GitLab on a private network

For a GitLab hostname that resolves to private IP addresses, configure private DNS and network routing from LangSmith and the sandbox hosts. Also set the following environment variable through the listed Helm values:

| Helm environment list | Variable | Value |
| --- | --- | --- |
| `platformBackend.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |
| `ingestQueue.deployment.extraEnv` | `SSRF_ALLOW_PRIVATE_IPS_ENGINE` | `"true"` |

This setting allows these components to reach private addresses for all of Engine's outbound requests, not only GitLab. It does not create DNS records or network routes, and loopback addresses stay blocked. These are the same settings that [GHES on a private network](/langsmith/engine-self-hosted-github#ghes-on-a-private-network) uses for these components.

Sandbox hosts need no extra setting. On self-hosted LangSmith, a sandbox can reach a private address that its allow list names, and Engine's sandboxes name the GitLab host.

### GitLab with a private certificate authority

The platform backend, ingest queue workers, and sandbox hosts must trust the certificate authority (CA) that signed your GitLab certificate. Configuring trust only in your browser or inside a sandbox is insufficient.

Follow [Mount internal CAs for TLS](/langsmith/self-host-custom-tls-certificates#mount-internal-cas-for-tls) to configure `config.customCa.secretName` and `config.customCa.secretKey`. Include your private CA and any public roots needed for other outbound connections in the bundle. Keep TLS verification enabled.

GitLab requests do not pass through `hostBackend`, so GitLab does not need the `REQUESTS_CA_BUNDLE` setting that [GHES with a private certificate authority](/langsmith/engine-self-hosted-github#ghes-with-a-private-certificate-authority) requires.

### Apply the configuration

Apply the complete values file through your normal deployment process. For Helm upgrades, see [Upgrade a self-hosted deployment](/langsmith/self-host-upgrades). Wait for the platform backend, ingest queue, and sandbox host rollouts to finish before a workspace admin connects GitLab.

### Verify webhook delivery

After the rollout, ask a workspace admin to [connect GitLab and verify the connection](/langsmith/engine-repositories#verify-the-gitlab-connection) with a test project. While they create and merge the test merge request, check the project's webhook:

1. In GitLab, open the test project's **Settings** > **Webhooks**. Confirm that a webhook for the LangSmith **Webhook URL** exists with merge request events enabled.
2. Edit the webhook and review **Recent events**. Confirm that merge request deliveries reach LangSmith successfully. LangSmith returns HTTP 202 when it accepts a delivery.

A successful webhook response alone does not prove the event matched an Engine issue. Confirm that merging the test merge request completes its issue.

### Troubleshoot setup

| Symptom | What to check |
| --- | --- |
| **GitLab** does not appear under **Settings** > **Integrations** | Confirm that your Helm chart version supports GitLab and that Engine is enabled. |
| Connecting fails with "Could not reach GitLab" | Check DNS and routing from `platformBackend` to GitLab, `SSRF_ALLOW_PRIVATE_IPS_ENGINE` for private addresses, and CA trust. |
| **Token renewal failed** shows a network or TLS error | Apply the same checks to `ingestQueue`, which renews tokens. |
| Projects are listed, but cloning or pushing fails | Check sandbox host DNS, routing, and CA trust. |
| A project row shows **Merges in \<project\> won't resolve issues** with "GitLab didn't accept the webhook" | Check GitLab's outbound request settings and the route from GitLab to your LangSmith ingress. See [Allow network access](#allow-network-access). |
| Webhook deliveries fail in **Recent events** | For connection or TLS errors, check the route from GitLab and the certificate that LangSmith's ingress presents. A 404 response means the webhook belongs to an earlier connection or the workspace is disconnected. A 401 response means the webhook's secret does not match the connection. Connecting GitLab or adding a project repairs the webhook. |

When asking for help, include your LangSmith and Helm chart versions, your GitLab version, and the step that fails. Do not include access tokens.
