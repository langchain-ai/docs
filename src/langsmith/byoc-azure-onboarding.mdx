<Note>
BYOC on Azure is in **[beta](/langsmith/release-stages)**. To get started, [contact our sales team](https://www.langchain.com/contact-sales).
</Note>

This page describes how to create a LangSmith BYOC data plane in your Azure subscription. For how the data plane is built and secured, see [BYOC architecture on Azure](/langsmith/byoc-azure-architecture). For the AWS guide, see [BYOC onboarding](/langsmith/byoc-onboarding).

Each data plane runs in its own resource group in your subscription. You create the resource group and a Key Vault in it, and give the LangSmith BYOC application roles on that resource group only. LangChain then creates and operates the data plane resources in the resource group.

## Before you start

You need the following:

- **A LangSmith organization on Azure**: Use the LangSmith control plane on Azure at [azure.smith.langchain.com](https://azure.smith.langchain.com). Send your organization ID to the LangChain team to enable BYOC.
- **An Azure subscription**: LangChain recommends a subscription dedicated to LangSmith BYOC, but it is not required.
- **Azure permissions**: A role on the subscription that can create resource groups, Key Vaults, and role assignments, such as `Owner`. You also need a Microsoft Entra role that can add the service principal of a multi-tenant application to your tenant, such as `Cloud Application Administrator`.
- **An organization admin in LangSmith**: Creating, changing, and deleting a data plane requires the organization admin role.
- **vCPU quota**: The AKS system node pool uses three `Standard_D2s_v6` VMs. LangSmith checks at create time that the region has at least 6 free vCPUs in both the **Total Regional vCPUs** quota and the Dsv6 VM family quota. Application nodes use D, E, and F series VMs of version 5 or later, so also plan quota for those families. See [Node pools](/langsmith/byoc-azure-architecture#compute).
- **A region**: BYOC on Azure can run in any Azure region. If you need a region that is not yet enabled, contact the LangChain team, who can add it.

## Create a data plane

<Steps>

<Step title="Copy the external ID">
LangChain assigns your organization an external ID. Navigate to **Settings > Data Planes** in LangSmith and use the copy button next to the **Data Planes** header to copy it. Do not create your own value.

LangSmith uses the external ID to confirm that the role assignments in your subscription belong to your organization.
</Step>

<Step title="Grant LangSmith access to a resource group">
For each data plane, create the following in your Azure subscription:

- **The LangSmith BYOC service principal**: Add the service principal of the LangSmith BYOC multi-tenant application to your Microsoft Entra tenant. Its application (client) ID is `5b0a74cb-9f37-4797-b557-c15d7be80d3b`. You add it once per tenant. The application requests no Microsoft Graph permissions.
- **A dedicated resource group**: Each resource group holds one data plane. Do not put other workloads in it.
- **One Key Vault in the resource group**: The vault must use Azure RBAC authorization, not access policies. The resource group must contain exactly one Key Vault. LangSmith writes the data plane's bootstrap secret to this vault, and the data plane reads it through a private endpoint, so you can disable public network access on the vault.
- **Two role assignments for the service principal on the resource group**: `Contributor` and `User Access Administrator`. Set the description of both role assignments to your external ID.

The following Terraform configuration creates these resources for one data plane:

```hcl
terraform {
  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = ">= 4.42.0, < 5.0.0"
    }
    azuread = {
      source  = "hashicorp/azuread"
      version = "~> 3.0"
    }
  }
}

provider "azurerm" {
  subscription_id = "<subscription-id>"
  features {}

  # The data plane needs these resource providers. LangSmith cannot
  # register them, because its roles stop at the resource group.
  resource_providers_to_register = [
    "Microsoft.Cache",
    "Microsoft.Compute",
    "Microsoft.ContainerService",
    "Microsoft.DBforPostgreSQL",
    "Microsoft.KeyVault",
    "Microsoft.ManagedIdentity",
    "Microsoft.Network",
    "Microsoft.Storage",
  ]
}

provider "azuread" {}

variable "external_id" {
  description = "The external ID from Settings > Data Planes in LangSmith."
  type        = string
}

data "azurerm_client_config" "current" {}

# The LangSmith BYOC application in your tenant.
resource "azuread_service_principal" "langsmith" {
  client_id    = "5b0a74cb-9f37-4797-b557-c15d7be80d3b"
  use_existing = true
}

resource "azurerm_resource_group" "data_plane" {
  name     = "langsmith-byoc-prod"
  location = "eastus"
}

resource "azurerm_key_vault" "data_plane" {
  # Key Vault names are global: 3 to 24 letters, digits, and hyphens.
  name                = "ls-byoc-prod-a1b2c3"
  location            = azurerm_resource_group.data_plane.location
  resource_group_name = azurerm_resource_group.data_plane.name
  tenant_id           = data.azurerm_client_config.current.tenant_id
  sku_name            = "standard"

  rbac_authorization_enabled    = true
  public_network_access_enabled = false

  network_acls {
    default_action = "Deny"
    bypass         = "None"
  }
}

resource "azurerm_role_assignment" "langsmith" {
  for_each = toset(["Contributor", "User Access Administrator"])

  scope                = azurerm_resource_group.data_plane.id
  role_definition_name = each.value
  principal_id         = azuread_service_principal.langsmith.object_id
  principal_type       = "ServicePrincipal"
  description          = var.external_id
}

output "azure_entra_tenant_id" {
  value = data.azurerm_client_config.current.tenant_id
}

output "resource_group_id" {
  value = azurerm_resource_group.data_plane.id
}
```

Replace the subscription ID, the region, and the Key Vault name, which must be unique across Azure. Then apply the configuration with your external ID, for example `terraform apply -var 'external_id=<external-id>'`. Note the `azure_entra_tenant_id` and `resource_group_id` outputs for the next step.

For what each role allows, see [Access and permissions](/langsmith/byoc-azure-architecture#access-and-permissions).
</Step>

<Step title="Create the data plane">
The **Settings > Data Planes** form in the LangSmith UI does not support Azure yet. Create the data plane with the [Create a new data plane](/langsmith/smith-api/data_planes/create-a-new-data-plane) API instead. Authenticate with an API key of an organization admin, and set your organization ID in the `X-Organization-Id` header:

```bash
curl -X POST 'https://azure.api.smith.langchain.com/orgs/current/data-planes' \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <api-key>' \
  -H 'X-Organization-Id: <organization-id>' \
  -d '{
    "name": "prod",
    "region": "eastus",
    "azure_entra_tenant_id": "<tenant-id>",
    "resource_group_id": "/subscriptions/<subscription-id>/resourceGroups/langsmith-byoc-prod",
    "vpc_cidr": "10.80.0.0/16",
    "public_load_balancer": false
  }'
```

| Field | Description |
|-------|-------------|
| `name` | Up to 24 lowercase letters, digits, and hyphens. Starts and ends with a letter or digit, and does not start with `internal`. |
| `region` | The Azure region of the data plane, such as `eastus`. Use the region of the resource group. |
| `azure_entra_tenant_id` | Your Microsoft Entra tenant ID, in `8-4-4-4-12` UUID form. |
| `resource_group_id` | The resource group, in the form `/subscriptions/<subscription-id>/resourceGroups/<name>`. Each resource group serves one data plane. |
| `vpc_cidr` | The address range of the VNet that LangSmith creates for the data plane. A private RFC 1918 range from `/16` to `/18`. To connect the data plane to your network later, pick a range that does not overlap your other networks. |
| `public_load_balancer` | `true` for an internet-facing endpoint. `false`, the default, for an internal load balancer that is reachable only from the data plane VNet and networks connected to it. |

Before LangSmith accepts the request, it checks that:

- The role assignments of the LangSmith service principal on the resource group have your external ID as their description.
- The service principal has the permissions it needs on the resource group.
- The resource group contains exactly one Key Vault, and the vault uses Azure RBAC.
- Your subscription can create the AKS system node size and the PostgreSQL size in the region, and has enough vCPU quota for the system node pool.

If a check fails, the API returns an error code and a remedy. See [Troubleshoot data plane creation](#troubleshoot-data-plane-creation).
</Step>

<Step title="Wait for provisioning">
LangChain provisions the data plane resources in your resource group. The data plane moves from `requested` to `provisioning` to `active`. Track its state in **Settings > Data Planes**.

If the data plane does not become active within 3 hours, it moves to `provisioning_failed`. If that happens, contact the LangChain team.
</Step>

<Step title="Connect to the data plane">
The data plane URL has the form `https://<data_plane_id>.azure.langchain-byoc.com`. Find it under **Settings > Data Planes**.

- **Internal load balancer** (`public_load_balancer: false`): Users and applications reach the data plane only from its VNet. Connect your network to that VNet, for example with VNet peering or a VPN gateway.
- **Public load balancer** (`public_load_balancer: true`): Users and applications reach the data plane over the internet.

If the LangSmith UI cannot reach your data plane, it prompts you to switch to a workspace on a data plane that is reachable.
</Step>

<Step title="Create workspaces">
A workspace named `dp-<data_plane_name>` is created automatically in the new data plane. It is not accessible until the data plane is reachable.

You can create more workspaces in the data plane. Select the target data plane when you create each one: a workspace belongs to exactly one data plane, and a data plane can hold many workspaces.

<Warning>
A workspace cannot be moved to another data plane after creation.
</Warning>
</Step>

<Step title="(Optional) Migrate existing data">
If you are moving from LangSmith Cloud or a [self-hosted](/langsmith/self-hosted) instance, contact the LangChain team to arrange a migration. Trace migration is supported on AWS only.

For more information, see [Migrate to BYOC](/langsmith/byoc-migration).
</Step>

</Steps>

To send traces and API requests to the data plane, see [BYOC usage](/langsmith/byoc-usage).

## Troubleshoot data plane creation

| Code | HTTP status | Cause | Fix |
|------|-------------|-------|-----|
| `azure_external_id_mismatch` | 403 | A role assignment of the LangSmith service principal on the resource group does not have your organization's external ID as its description. | Set the description of both role assignments to the external ID from **Settings > Data Planes**, then retry. |
| `azure_permissions` | 403 | The LangSmith service principal cannot access the resource group, or lacks a required permission. The remedy lists the missing actions. | Check that the resource group exists and that both role assignments are in place, then retry. |
| `azure_policy_denied` | 403 | An Azure Policy assignment in your subscription denied a request. | Exempt the data plane resource group from the policy, then retry. |
| `azure_resource_group_invalid` | 400 | The resource group does not exist, does not contain exactly one Key Vault, or its vault does not use Azure RBAC. | Fix the resource group, then retry. |
| `azure_region_unavailable` | 400 | Your subscription cannot use the region, or cannot create the AKS system node size or the PostgreSQL size in it. | Choose another region, or ask Azure support to enable the VM size or PostgreSQL for your subscription in the region. |
| `insufficient_azure_quota` | 422 | The region does not have enough free vCPU quota for the AKS system node pool. | Request a quota increase, or choose another region. |
| `azure_resource_group_in_use` | 409 | Another data plane uses the resource group. | Create a new resource group for the data plane. |
| `data_plane_name_taken` | 409 | Your organization already has a data plane with this name. | Choose another name. |
| `azure_throttled` | 429 | Azure is rate limiting requests for your subscription. | Wait a minute, then retry. |
| `azure_unavailable` | 502 or 503 | Azure returned a server error, or did not report the vCPU quota. | Wait a minute, then retry. |

Invalid field values return HTTP 400 with the field name and the rule that the value breaks.

## Change data plane settings

The settings form in the LangSmith UI supports AWS maintenance windows only. To change the maintenance window of an Azure data plane, use the [Update data plane settings](/langsmith/smith-api/data_planes/update-data-plane-settings) API:

```bash
curl -X PATCH 'https://azure.api.smith.langchain.com/orgs/current/data-planes/<data-plane-id>' \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: <api-key>' \
  -H 'X-Organization-Id: <organization-id>' \
  -d '{"maintenance_window": "sun:07:00-sun:11:00"}'
```

You can change the following settings of an Azure data plane while it is `provisioning` or `active`:

| Setting | Field | Azure |
|---------|-------|-------|
| Maintenance window | `maintenance_window` | A weekly UTC window of exactly 4 hours that starts on the hour, in the form `ddd:HH:00-ddd:HH:00`. The default is `sun:07:00-sun:11:00`. AKS upgrades and PostgreSQL maintenance happen in this window. |
| Trace payload retention | `ttl` | Supported. By default, `short_days` is 14 and `long_days` is 400. |
| Network firewall | `firewall` | Not available on Azure. |
| Fleet OIDC | `fleet_oidc` | Not available on Azure. |

## Delete a data plane

Delete the data plane in **Settings > Data Planes**, or with the `DELETE /orgs/current/data-planes/<data-plane-id>` API. You can delete an Azure data plane while it is `provisioning`, `active`, or `provisioning_failed`. LangSmith first checks that it can still access your resource group, so keep both role assignments in place until the deletion completes.

LangSmith deletes the AKS cluster, PostgreSQL, Redis, the network, and the private DNS zones. It keeps the following in your resource group:

- The resource group and the Key Vault.
- The Blob storage accounts that hold your trace data and SmithDB data.

Azure keeps the backups of a deleted PostgreSQL server for a limited time, during which you can restore it. See [Restore a dropped Azure Database for PostgreSQL flexible server](https://learn.microsoft.com/azure/postgresql/flexible-server/how-to-restore-dropped-server).

After the deletion completes, delete the resource group yourself when you no longer need the retained data. If you create a new data plane with the same name in the same resource group, it reuses the Key Vault and the retained Blob storage accounts.

## Remove LangSmith access

To stop LangSmith from changing or deleting the data plane, delete the two role assignments of the LangSmith service principal on the resource group. The data plane resources stay in your subscription, and LangChain can no longer upgrade or repair them. Delete the data plane first if you want LangSmith to clean up its resources.
