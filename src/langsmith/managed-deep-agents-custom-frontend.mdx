A custom frontend is any application you write that calls a deployment directly instead of reaching the agent through a [channel](/langsmith/managed-deep-agents-channels) or [LangSmith Studio](/langsmith/managed-deep-agents-local-development#start-local-studio). Use one when the agent belongs inside a product surface you control, such as a support console, an internal dashboard, or a customer-facing chat page.

Managed Deep Agents deployments run on [LangSmith Agent Server](/langsmith/agent-server-overview). A frontend talks to the same threads, runs, and streaming endpoints that every Agent Server client uses.

<ManagedDeepAgentsPublicBetaNote />

## Choose an identity provider

Every request to a deployment names a caller, and the frontend supplies that name. Which [identity provider](/langsmith/managed-deep-agents-identity) fits depends on where the frontend code runs, not on the language it is written in.

| Where the frontend calls the deployment from | Identity provider |
| --- | --- |
| The user's browser | An external auth provider. The browser sends an access token and the deployment verifies it. See [Supabase](/langsmith/managed-deep-agents-identity#configure-identity-with-supabase). |
| Your own server, which already authenticates the user | [Your own backend](/langsmith/managed-deep-agents-identity#configure-identity-with-your-own-backend). Your server asserts the user ID behind a shared ingress secret. |
| Your own server, with no end-user accounts of its own | The [LangSmith API key](/langsmith/managed-deep-agents-identity#configure-identity-with-a-langsmith-api-key) default. The key itself is the caller. |

Either server row fits a server-rendered application in any language. Streamlit, Gradio, and Dash run their code on the server, as do a Next.js route handler and an Express proxy. A frontend pointed at [`mda dev`](/langsmith/managed-deep-agents-local-development#understand-local-behavior) works before you configure a provider, because the local server supplies a test user.

<Warning>
A LangSmith API key reaches every resource in the workspace, not only this deployment, so it must never ship in browser JavaScript. Use an external auth provider when the browser calls the deployment directly, and backend identity when your own server calls it on the user's behalf.
</Warning>

## Connect to the deployment

A frontend needs two values.

**Deployment API URL.** `mda deploy` prints the LangSmith deployment dashboard URL, not the API URL. Open that dashboard, then copy the **API URL** from the deployment details view. The local server started by [`mda dev`](/langsmith/managed-deep-agents-local-development) serves the same routes at the URL the CLI prints.

**Assistant ID.** Clients pass the agent's `name` from the [agent definition](/langsmith/managed-deep-agents-agent-definition#parameters). Managed Deep Agents also uses that name as the graph ID:

:::python
```python agent.py
from managed_deepagents import define_deep_agent

agent = define_deep_agent(
    name="research-assistant",  # [!code highlight]
    model="openai:gpt-5.5",
)
```
:::

:::js
```ts agent.ts
import { defineDeepAgent } from "managed-deepagents";

export const agent = defineDeepAgent({
  name: "research-assistant", // [!code highlight]
  model: "openai:gpt-5.5",
});
```
:::

Clients address an agent named `research-assistant` with that same string. Renaming the agent changes the value clients send, so treat the name as part of the deployment's public interface.

## Build a web frontend

The [LangChain frontend SDKs](/oss/langchain/frontend/overview) connect a browser application to an Agent Server deployment. `useStream` exposes messages, tool calls, interrupts, and thread state as reactive values:

| Framework | Package | Entry point |
| --- | --- | --- |
| React | `@langchain/react` | `useStream` |
| Vue | `@langchain/vue` | `useStream` |
| Svelte | `@langchain/svelte` | `useStream` |
| Angular | `@langchain/angular` | `injectStream` |

The frontend runs in the browser, so these examples are TypeScript even when the agent is written in Python.

Under an external auth provider, the browser sends the access token from the signed-in session. That token rotates, so re-read it whenever the session changes rather than capturing it once at mount:

```ts useAuthHeaders.ts
import { useEffect, useState } from "react";

import { supabase } from "./supabase";

export function useAuthHeaders() {
  const [headers, setHeaders] = useState<Record<string, string>>();

  useEffect(() => {
    const refresh = async () => {
      const { data } = await supabase.auth.getSession();
      const token = data.session?.access_token;
      setHeaders(token ? { Authorization: `Bearer ${token}` } : undefined);
    };

    void refresh();
    const { data } = supabase.auth.onAuthStateChange(() => void refresh()); // [!code highlight]
    return () => data.subscription.unsubscribe();
  }, []);

  return headers;
}
```

The highlighted subscription fires on sign-in, sign-out, and token refresh. Without it the hook holds the token captured at mount, and requests start failing with 401 once that token expires.

Point the stream at the deployment API URL, the agent name, and those headers:

```tsx Chat.tsx
import { useStream } from "@langchain/react";
import { useState } from "react";

import { useAuthHeaders } from "./useAuthHeaders";

export function Chat() {
  const [input, setInput] = useState("");
  const headers = useAuthHeaders();
  const stream = useStream({
    apiUrl: import.meta.env.VITE_DEPLOYMENT_API_URL,
    assistantId: "research-assistant",
    defaultHeaders: headers,
  });

  return (
    <main>
      {stream.messages.map((message) => (
        <p key={message.id}>{message.text}</p>
      ))}

      <form
        onSubmit={(event) => {
          event.preventDefault();
          stream.submit({ messages: [{ type: "human", content: input }] });
          setInput("");
        }}
      >
        <input value={input} onChange={(event) => setInput(event.target.value)} />
        <button type="submit" disabled={stream.isLoading}>
          Send
        </button>
      </form>
    </main>
  );
}
```

Under backend identity the browser never reaches the deployment. Point `apiUrl` at your own server and forward the Agent Server routes from there, stamping `x-mda-ingress-secret` and the user ID your auth layer resolved on each upstream request. For the headers and the shared secret, see [Configure identity with your own backend](/langsmith/managed-deep-agents-identity#configure-identity-with-your-own-backend).

The same frontend patterns work against a Managed Deep Agents deployment. See [tool-call rendering](/oss/langchain/frontend/tool-calling), [generative UI](/oss/langchain/frontend/generative-ui-overview), [human-in-the-loop approval](/oss/langchain/frontend/human-in-the-loop), [queued submissions](/oss/langchain/frontend/message-queues), and [durable rejoin](/oss/langchain/frontend/join-rejoin).

### Handle authorization interrupts

When the agent needs a [user-owned connection](/langsmith/managed-deep-agents-connections) the caller has not granted, the run pauses and `stream.interrupt` carries a credential gate payload. A browser frontend renders the consent links and resumes with `stream.respond`. For the payload shape and a worked example, see [Handle the authorization interrupt](/langsmith/managed-deep-agents-connections#handle-the-authorization-interrupt).

## Build a Python frontend

Streamlit, Gradio, and Dash render on the server, so no credential reaches the browser and the API-key default works without extra setup. All three use the same [LangGraph SDK](https://reference.langchain.com/python/langgraph-sdk) client, so the connection code below applies to any of them.

Install the SDK alongside your application framework:

```bash
uv add langgraph-sdk streamlit
```

Create a client, then stream a run against a thread:

```python
from langgraph_sdk import get_sync_client

client = get_sync_client(
    url=DEPLOYMENT_API_URL,
    api_key=LANGSMITH_API_KEY,
)

thread = client.threads.create()

for chunk in client.runs.stream(
    thread["thread_id"],
    "research-assistant",
    input={"messages": [{"role": "user", "content": "Summarize this week's incidents."}]},
    stream_mode="messages",
):
    ...
```

Three details govern how that loop behaves:

- **`api_key`**: Sets the `x-api-key` header. Passing `headers={"x-api-key": ...}` instead raises `ValueError: Cannot set reserved header 'x-api-key'`.
- **Environment fallback**: When `api_key` is omitted, the client tries `LANGGRAPH_API_KEY`, then `LANGSMITH_API_KEY`, then `LANGCHAIN_API_KEY`. For Supabase or backend identity, pass `api_key=None` explicitly and put the token in `headers`. Otherwise a stray environment variable attaches a second credential.
- **`messages/partial`**: Carries the whole message so far, not a delta. Replace the rendered text on each event rather than appending, or the output repeats itself.

### Stream into a Streamlit chat

This application keeps one thread per browser session and rewrites the assistant bubble as each event arrives:

```python app.py
import os

import streamlit as st
from langgraph_sdk import get_sync_client

ASSISTANT_ID = "research-assistant"


@st.cache_resource
def get_agent_client():
    return get_sync_client(
        url=os.environ["DEPLOYMENT_API_URL"],
        api_key=os.environ["LANGSMITH_API_KEY"],
    )


def text_of(message):
    return "".join(
        block.get("text", "")
        for block in message.get("content", [])
        if block.get("type") == "text"
    )


client = get_agent_client()

if "thread_id" not in st.session_state:
    st.session_state.thread_id = client.threads.create()["thread_id"]
    st.session_state.history = []

for role, text in st.session_state.history:
    st.chat_message(role).markdown(text)

if prompt := st.chat_input("Message the agent"):
    st.session_state.history.append(("user", prompt))
    st.chat_message("user").markdown(prompt)

    with st.chat_message("assistant"):
        placeholder = st.empty()
        answer = ""
        for chunk in client.runs.stream(
            st.session_state.thread_id,
            ASSISTANT_ID,
            input={"messages": [{"role": "user", "content": prompt}]},
            stream_mode="messages",
        ):
            if chunk.event != "messages/partial":
                continue
            for message in chunk.data:
                if message.get("type") == "ai":
                    answer = text_of(message)
                    placeholder.markdown(answer)  # [!code highlight]

    st.session_state.history.append(("assistant", answer))
```

The highlighted line replaces the bubble contents on every event. Appending there produces duplicated text, because each event repeats the message from the beginning.

`text_of` reads content blocks rather than a plain string. Agent messages arrive as a list of typed blocks, so a frontend that expects `message["content"]` to be text renders nothing. The web SDKs deserialize each event into a message object that exposes a `text` accessor, which is why the React example above reads `message.text`. The LangGraph SDK yields plain dictionaries, so a Python frontend extracts the text itself.

Gradio and Dash use the same client and the same loop. Substitute their streaming primitive for the Streamlit placeholder: a generator function for `gr.ChatInterface`, or a `dcc.Interval` callback for Dash.
:::

## Copy or branch a conversation

Agent Server supports copying a thread's checkpoint history and branching from an earlier checkpoint. Use these capabilities to continue a conversation separately or explore an alternative within it.

[Identity](/langsmith/managed-deep-agents-identity) still governs access. Studio can read and search every deployment thread, but mutations remain owner-scoped. Read access alone does not guarantee permission to copy or branch. Managed channel threads belong to the source conversation, not an individual participant.

Choose the operation for your goal:

- **Separate conversation ID**: [Copy the thread](/langsmith/use-threads#copy-thread) with the SDK's `threads.copy` method or `POST /threads/{thread_id}/copy`. Send subsequent runs to the returned thread's `thread_id`, not the original ID.
- **Edit or retry an earlier step**: Keep the same thread ID and select a past checkpoint. Optionally update its state, then resume from that checkpoint. See [time travel using the server API](/langsmith/human-in-the-loop-time-travel) and [branching chat](/oss/langchain/frontend/branching-chat) for frontend controls. Nodes after the checkpoint execute again, including tool calls and their side effects.
- **Pass context to a subagent**: Use [forked subagents](/oss/deepagents/subagents#forked-subagents) with `mode: "fork"`. The subagent inherits parent context for a delegated task. It does not copy a durable conversation into a new thread.

Checkpoint history is not a copy of the execution environment:

- **Sandbox**: The runtime selects a [sandbox](/langsmith/managed-deep-agents-sandboxes) by thread ID. Copying checkpoints does not clone the original thread's live sandbox or files. Branching within the same thread does not rewind its sandbox.
- **Memory**: [Durable memory](/langsmith/managed-deep-agents-memory#control-access-to-a-layer) remains deployment-shared or caller-scoped, not an independent copy for each thread or branch. Availability depends on the current caller, delivery context, and memory policy. Moving from a Slack DM to a direct API run can change which memory is available.
- **Channel destination**: Copying a thread does not create a new Slack conversation or establish a new reply destination. [Channel routing](/langsmith/managed-deep-agents-channels) uses the source conversation and verified delivery, not the copied checkpoint history.
