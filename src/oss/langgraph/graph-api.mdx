The Graph API defines agent workflows as a graph of [state](#state), [nodes](#nodes), and [edges](#edges). [`Send`](#send) and [`Command`](#command) control how the graph runs work: `Send` dynamically invokes nodes for fan-out, and `Command` updates state while routing to the next node (including resume after an interrupt). Use the Graph API when you want explicit shared state and a visual control flow.

For step-by-step decisions while building, see the [Build checklist for the Graph API](/oss/langgraph/use-graph-api). For a guided walkthrough, see [Thinking in the Graph API](/oss/langgraph/thinking-in-graph-api). To choose between this and the Functional API, see [Choosing between Graph and Functional APIs](/oss/langgraph/choosing-apis).

## Graphs

LangGraph models agent workflows as graphs built from three parts:

1. [`State`](#state): A shared snapshot of the application. Usually a typed schema.
2. [`Nodes`](#nodes): Functions that read state, do work, and return updates.
3. [`Edges`](#edges): Fixed or conditional transitions that determine the next node.

Compose nodes and edges to build sequences, branches, and loops. Nodes and edges are ordinary functions. They can call an LLM or run other code.

In short: nodes do the work; edges decide what runs next.

### Super-steps

LangGraph runs graphs with [message passing](https://en.wikipedia.org/wiki/Message_passing), in the style of Google's [Pregel](https://research.google/pubs/pregel-a-system-for-large-scale-graph-processing/) system. Execution advances in discrete **super-steps**:

- Nodes that run in parallel share one super-step.
- Nodes that run in sequence use separate super-steps.
- A node becomes active when it receives input on an incoming edge.
- After a super-step, nodes with no pending messages become inactive.
- The run ends when every node is inactive and no messages remain in transit.

## State

State is the shared data that nodes read and update. LangGraph stores that data in **channels**: named slots in the state schema (the keys of your state object). Each channel holds a value and defines how updates merge into it. Most channels use last-write-wins. Channels with a [reducer](#reducers) combine values instead, for example by appending to a list.

State has two parts:

- A [schema](#schema) that declares the channels in the graph
- Optional [reducers](#reducers) that control how updates merge into each channel

Nodes return partial updates. LangGraph applies those updates through each channel's reducer.

:::python
Define state with a [`TypedDict`](https://docs.python.org/3/library/typing.html#typing.TypedDict), a [`dataclass`](https://docs.python.org/3/library/dataclasses.html) (for defaults), or a Pydantic [`BaseModel`](/oss/langgraph/graph-api-state#use-pydantic-models-for-graph-state) when you need validation. Prefer `TypedDict` or `dataclass` for performance.

<Info>
[`create_agent`](/oss/langchain/agents) state schemas must be `TypedDict`. Pydantic models are not supported.
</Info>
:::

:::js

- A **standard schema** (last-value channel; overwrites on update)
- A **`ReducedValue`** (custom reducer, often for parallel updates)
- A **`MessagesValue`** (message list with a message-aware reducer)
- An **`UntrackedValue`** (transient; not checkpointed)

### Schema

By default, the graph input and output schemas match the full state. You can narrow them when some keys are internal only. See [Define input and output schemas](/oss/langgraph/graph-api-state#define-input-and-output-schemas).

#### Multiple schemas

Most graphs share one state schema. Use multiple schemas when you need either of the following:

- Private channels that internal nodes share, but that are not part of graph input or output
- Explicit input and output schemas that are subsets of the full internal state

A node can write to any channel in the graph state, including channels outside its declared input schema. Nodes can also introduce private channels when those schemas are defined. Input and output schemas constrain what `invoke` accepts and returns. They do not hide channels from [streaming](/oss/langgraph/streaming) by default. See [Private channels and streaming](/oss/langgraph/graph-api-state#private-channels-and-streaming).

For examples, see [Define input and output schemas](/oss/langgraph/graph-api-state#define-input-and-output-schemas) and [Pass private state between nodes](/oss/langgraph/graph-api-state#pass-private-state-between-nodes).

### Reducers

Reducers control how node updates merge into state. Each key has its own reducer. With no reducer, updates overwrite the previous value.

#### Reducer arguments

- **Left**: The current value in state for that key

#### Default reducer

The default reducer replaces the left value with the right. Nodes return partial updates, not the full state.

### Re-execution and idempotency

With a [checkpointer](/oss/langgraph/persistence), LangGraph saves checkpoints at [super-step](#super-steps) boundaries, not mid-function inside a node. After an [interrupt](/oss/langgraph/interrupts) or [retry](/oss/langgraph/fault-tolerance#retries), the affected node runs again from the start of its function. Side effects before the pause run again.

Design node logic so re-execution is safe. Prefer idempotency keys, upserts, or read-before-write checks. For effects around `interrupt()`, see [Side effects called before `interrupt` must be idempotent](/oss/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent).

You can add or remove nodes and edges without breaking resume for existing threads. Resumed runs use saved state and the graph you compile now.

If a node calls [tasks](/oss/langgraph/functional-api#task) or @[`interrupt`], stricter [determinism](/oss/langgraph/functional-api#determinism) rules apply on resume. Completed task results are restored from the checkpointer. Changing task or interrupt order before the resume point can mismatch cached values. See [Idempotency](/oss/langgraph/functional-api#idempotency).

### Using tasks in nodes

When one node runs several operations that should checkpoint independently, wrap each operation in a [task](/oss/langgraph/functional-api#task) instead of splitting the work across nodes. With a checkpointer, completed task results are saved, so a resumed thread can skip finished work inside the node. For patterns and examples, see [Tasks](/oss/langgraph/functional-api-tasks) and [Common pitfalls](/oss/langgraph/functional-api#common-pitfalls).

## Edges

Edges decide where control goes next:

- **Normal edges**: Always go from one node to the next
- **Conditional edges**: Call a function to determine the next node(s)
- **Entry point**: First node after user input (`START` → node)
- **Conditional entry point**: Route from `START` with a function

A node can have multiple outgoing edges. Destinations on those edges run in parallel in the next super-step.

<Warning>
For each node, use either static edges or dynamic routing ([conditional edges](#conditional-edges) / @[`Command`]), not both. Mixing them can run both paths.
</Warning>

## `Send`

Use @[`Send`] when you need to run the same node once per item, each with its own input, and the number of items is only known at runtime. That shape is often called map-reduce or orchestrator-worker: one node produces a list, workers process each item in parallel, then a later node reads the combined results.

Normal edges cannot do this. They choose which nodes run next, but every chosen node still receives the shared graph state, and the topology is fixed when you build the graph.

Return one or more `Send` objects from a conditional edge. Each `Send` names a target node and passes a custom argument as that invocation's input. LangGraph runs those invocations in parallel. When workers write to shared state keys, [reducers](#reducers) merge their updates, for example by concatenating lists.

The first argument to `Send` is the target node name. The second is the state (or partial state) for that invocation.

## `Command`

Use @[`Command`] when a single step must both update state and choose what runs next. Normally those jobs are separate: a node returns state updates, and [edges](#edges) (or [conditional edges](#conditional-edges)) decide the next node. Return `Command` from a node when the next hop depends on work you just did in that same function.

`Command` also covers two other cases that plain returns and edges do not: resume a run after an [interrupt](/oss/langgraph/interrupts), and update or route from inside a [tool](#return-from-tools).

For routing alone, prefer conditional edges. Reach for `Command` when you need the update and the route together (or one of the interrupt / tool cases above).

`Command` accepts:

- **`update`**: State updates (like a normal node return)
- **`goto`**: Next node(s) (like a conditional edge)
- **`graph`**: Parent graph target when navigating from a [subgraph](/oss/langgraph/use-subgraphs)
- **`resume`**: Value used to resume after an [interrupt](/oss/langgraph/interrupts)

Use `Command` in three places:

- **[Return from nodes](#return-from-nodes)**: `update`, `goto`, and `graph`
- **[Input to `invoke` or `stream`](#input-to-invoke-or-stream)**: `resume` after an interrupt
- **[Return from tools](#return-from-tools)**: Updates and routing from inside a tool

### Input to `invoke` or `stream`

:::python
<Warning>
`Command(resume=...)` is the only `Command` pattern meant as input to `invoke()` / `stream()` (optionally with `update=...` while resuming). Do not pass `Command(update=...)` alone to continue a conversation. Any `Command` as input resumes from the latest checkpoint, not from `START`, so a finished thread can look stuck. Pass a plain dict to start a new turn:

```python
# Wrong: resumes from the latest checkpoint
graph.invoke(Command(update={  # [!code --]
    "messages": [{"role": "user", "content": "follow up"}]  # [!code --]
}), config)  # [!code --]

# Correct: plain dict restarts from START
graph.invoke({  # [!code ++]
    "messages": [{"role": "user", "content": "follow up"}]  # [!code ++]
}, config)  # [!code ++]
```
</Warning>
:::

Return @[`Command`] from tools to update state and route after the tool finishes. `goto` from a tool adds a dynamic edge. Static edges on the calling node still run, so do not mix both.

See [Use inside tools](/oss/langgraph/graph-api-send-command#use-inside-tools).

## Graph migrations

You can change a graph's nodes, edges, and state schema even when a [checkpointer](/oss/langgraph/persistence) already stores thread state. What is safe depends on whether the thread has finished or is paused.

**Topology (nodes and edges)**

- Finished threads (not interrupted): you can add, remove, or rename nodes and edges freely.
- Interrupted threads: you can change edges and add nodes. Do not rename or remove a node the thread is about to enter. On resume, LangGraph looks up that node by name, and a missing name fails the run.

**State schema**

- Adding or removing keys is backwards and forwards compatible.
- Renaming a key drops the saved value for that key in existing threads.
- Incompatible type changes on an existing key (for example, narrowing or requiring a field that old checkpoints omit) can break older thread state.

For logic changes that stay schema-compatible (for example, a new tool set), see [Business compatibility](/oss/langgraph/backward-compatibility#business-compatibility).

### Recursion limit

The recursion limit caps how many [super-steps](#super-steps) one run may execute. When the limit is exceeded, LangGraph raises `GraphRecursionError`.

The default is 10007 super-steps. Override it with the `LANGGRAPH_DEFAULT_RECURSION_LIMIT` environment variable, or pass `recursion_limit` as a top-level config key (not under `configurable`).
