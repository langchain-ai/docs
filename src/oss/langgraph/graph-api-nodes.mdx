[Nodes](/oss/langgraph/graph-api#nodes) are the steps of a Graph API graph. This page covers how to attach runtime configuration, retries, timeouts, error handlers, defaults, and caching when you add a node. For wiring nodes into sequences, branches, and loops, see [Control flow](/oss/langgraph/graph-api-control-flow). For the full retry, timeout, and error lifecycle, see [Fault tolerance](/oss/langgraph/fault-tolerance).

## Add runtime configuration

Pass values into a run (for example, which LLM or system prompt to use) without putting those values in graph state.

To add runtime configuration:

1. Specify a schema for your configuration
2. Add the configuration to the function signature for nodes or conditional edges
3. Pass the configuration into the graph

## Add retry policies

Attach a retry policy when a node calls an API, database, or LLM that can fail transiently.

:::python
Pass `retry_policy` to @[`add_node`]. The value is a `RetryPolicy` named tuple. This example uses the defaults:

<LanggraphGraphApiNodesRetryDefaultPy />

By default, `retry_on` uses `default_retry_on`, which retries any exception except:

* `ValueError`
* `TypeError`
* `ArithmeticError`
* `ImportError`
* `LookupError`
* `NameError`
* `SyntaxError`
* `RuntimeError`
* `ReferenceError`
* `StopIteration`
* `StopAsyncIteration`
* `OSError`

For exceptions from popular HTTP libraries such as `requests` and `httpx`, it only retries on 5xx status codes. See [Fault tolerance](/oss/langgraph/fault-tolerance#retries) for the full default list and parameters.
:::

:::js
Pass `retryPolicy` to [`addNode`](https://reference.langchain.com/javascript/classes/_langchain_langgraph.index.Graph.html#addnode). An empty object uses the built-in defaults:

<LanggraphGraphApiNodesRetryDefaultJs />

Retries are opt-in: without a `retryPolicy`, the first failure ends the attempt. If the policy omits `retryOn`, LangGraph retries thrown errors except:

* Abort and cancellation errors (`error.name === "AbortError"`, or `error.message` starts with `"Cancel"` or `"AbortError"`)
* `GraphValueError`, matched by `error.name`
* Aborted connections (`error.code === "ECONNABORTED"`)
* HTTP client errors with status 400, 401, 402, 403, 404, 405, 406, 407, or 409
* OpenAI-style quota errors (`error.error?.code === "insufficient_quota"`)

See [Fault tolerance](/oss/langgraph/fault-tolerance#retries) for the full default list and parameters.
:::

## Set node timeouts

:::python
<Note>
Requires `langgraph>=1.2`.
</Note>

Pass `timeout` to @[`add_node`] to cap how long a single async node attempt may run. Use a number (seconds), a `datetime.timedelta`, or a @[`TimeoutPolicy`] for separate run and idle limits:

<LanggraphGraphApiNodesTimeoutPy />

Node timeouts apply only to **async** nodes. Setting `timeout` on a sync node fails at compile time, because sync Python execution cannot be safely canceled in-process. For separate run and idle limits, pass a @[`TimeoutPolicy`].

When a node exceeds its timeout, LangGraph raises @[`NodeTimeoutError`]. It does **not** subclass built-in `TimeoutError` (an `OSError` subclass), so the default retry policy treats it as retryable when a `retry_policy` is set. The timeout applies to each attempt independently, so the timer resets for every retry. Timed-out attempts do not commit buffered writes.

See [Fault tolerance](/oss/langgraph/fault-tolerance#timeouts) for the full timeout lifecycle, idle-timeout refresh sources, and `runtime.heartbeat()`.
:::

:::js
<Note>
Requires `@langchain/langgraph` v1.4.0 or later.
</Note>

Pass `timeout` to @[`addNode`] to cap how long a single node attempt may run. Use a number (milliseconds) or a @[`TimeoutPolicy`] for separate run and idle limits:

<LanggraphGraphApiNodesTimeoutJs />

When a node exceeds its timeout, LangGraph raises @[`NodeTimeoutError`], clears writes from the failed attempt, and lets the retry policy decide whether to retry. The timeout applies to each attempt independently.

See [Fault tolerance](/oss/langgraph/fault-tolerance#timeouts) for the full timeout lifecycle, idle-timeout refresh sources, and heartbeats.
:::

## Set graph-wide node defaults

:::python
<Note>
Requires `langgraph>=1.2`.
</Note>

Use @[`set_node_defaults`] to set `retry_policy`, `timeout`, `cache_policy`, or `error_handler` once for every node in a graph, instead of repeating them on each @[`add_node`] call. Per-node values always win, and defaults are applied at @[`StateGraph.compile`] time:

<LanggraphGraphApiNodesNodeDefaultsPy />

`retry_policy` and `timeout` defaults apply to every node, including error-handler nodes. `cache_policy` and `error_handler` defaults apply only to regular nodes—handlers never catch themselves, and caching a handler result is unsafe. Defaults are not inherited by subgraphs.

See [Fault tolerance](/oss/langgraph/fault-tolerance#graph-defaults) for the full precedence rules and applicability table.
:::

:::js
<Note>
Requires `@langchain/langgraph` v1.4.0 or later.
</Note>

Use [`setNodeDefaults`](https://reference.langchain.com/javascript/langchain-langgraph/index/StateGraph#member-setNodeDefaults) to set `retryPolicy`, `timeout`, `cachePolicy`, or `errorHandler` once for every node in a graph, instead of repeating them on each `addNode` call. Per-node values always win, and defaults are applied at compile time:

<LanggraphGraphApiNodesNodeDefaultsJs />

`retryPolicy` and `timeout` defaults apply to every node, including error-handler nodes. `cachePolicy` and `errorHandler` defaults apply only to regular nodes. Handlers never catch themselves, and caching a handler result is unsafe. Defaults are not inherited by subgraphs.

See [Fault tolerance](/oss/langgraph/fault-tolerance#graph-defaults) for the full precedence rules and applicability table.

## Access execution info inside a node

:::python
Access execution identity and retry information via `runtime.execution_info`. This surfaces thread, run, and checkpoint identifiers as well as retry state, without reading from `config` directly.

| Attribute | Type | Description |
| --------- | ---- | ----------- |
| `thread_id` | `str \| None` | Thread ID for the current execution. `None` without a checkpointer. |
| `run_id` | `str \| None` | Run ID for the current execution. `None` when not provided in config. |
| `checkpoint_id` | `str` | Checkpoint ID for the current execution. |
| `checkpoint_ns` | `str` | Checkpoint namespace for the current execution. |
| `task_id` | `str` | Task ID for the current execution. |
| `node_attempt` | `int` | Current execution attempt number (1-indexed). `1` on the first try, `2` on the first retry, etc. |
| `node_first_attempt_time` | `float \| None` | Unix timestamp (seconds) of when the first attempt started. Stays the same across retries. |

#### Access thread and run IDs

Use `execution_info` to access the thread ID, run ID, and other identity fields inside a node:

`execution_info` is set once the node task is prepared. Even without a retry policy, `node_attempt` defaults to `1`, and `node_first_attempt_time` is set when the node starts executing.

## Add node caching

Use node caching when a step is expensive and you want to reuse results for the same input.

To enable caching:

1. Pass a cache when you compile the graph (for example, `InMemoryCache`). `SqliteCache` is also available in Python.
2. Attach a @[`CachePolicy`] on the node.

@[`CachePolicy`] options:

:::python
- **`key_func`**: Function that builds a cache key from the node input. Defaults to a hash of the input (via pickle).
- **`ttl`**: Time to live in seconds. When omitted, the cache entry does not expire.
:::

:::js
- **`keyFunc`**: Function that builds a cache key from the node input.
- **`ttl`**: Time to live in seconds. When omitted, the cache entry does not expire.
:::

You can also set `cache_policy` (and other node options) once for the graph with @[`set_node_defaults`]. See [Set graph-wide node defaults](#set-graph-wide-node-defaults).
