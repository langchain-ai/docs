OpenWiki can run inside an existing coding agent instead of launching its own model. The coding agent investigates the repository, plans the wiki, and writes each assigned page with its native repository tools. OpenWiki owns the durable page-job lifecycle, Claims validation and persistence, source-drift handling, and deterministic finalization.

Host-driven runs support only repository [code mode](/oss/openwiki/code-mode) wikis, not [personal mode](/oss/openwiki/personal-mode). They use the coding agent's authenticated model session, so OpenWiki provider credentials are not required. Connector-sourced context, including LangSmith, is not yet supported on this path. Host-driven page authoring is sequential; [parallel page workers](/oss/openwiki/code-mode#parallel-page-workers) apply to the native CLI only.

## Install an integration

Supported hosts are **Codex**, **Claude Code**, **GitHub Copilot**, **OpenCode**, **Cursor**, **IBM Bob** (Bob Shell), **Kiro**, **Oh My Pi** (`omp`), and **Antigravity CLI**. Installations default to user level, so one install works from any Git repository:

```bash
openwiki integrations install codex
openwiki integrations install claude
openwiki integrations install copilot
openwiki integrations install opencode
openwiki integrations install cursor
openwiki integrations install bob
openwiki integrations install kiro
openwiki integrations install omp
openwiki integrations install antigravity
```

Restart the coding agent after installation. Then open the repository and ask:

```txt
Initialize this repository's OpenWiki from the current source and tests.
```

For an existing wiki, ask:

```txt
Update this repository's OpenWiki for changes since its last successful run.
```

Installed integrations also expose [search and read tools](/oss/openwiki/search-and-link) so the host can query an existing wiki without starting a generation run.

### Inspect or uninstall

```bash
openwiki integrations list
openwiki integrations uninstall <codex|claude|copilot|opencode|cursor|bob|kiro|omp|antigravity>
```

Add `--project [path]` to `list`, `install`, or `uninstall` for repository-scoped state. Project paths resolve to the Git repository root.

Host-specific user-level locations:

- **OpenCode**: `~/.config/opencode`
- **IBM Bob / Bob Shell**: `~/.agents/skills` and `~/.bob/settings/mcp.json` (project scope uses `.agents/skills` and `.bob/mcp.json`)
- **Kiro**: `~/.kiro/skills` and `~/.kiro/settings/mcp.json`
- **Oh My Pi**: `~/.omp/agent` for the default profile. Use `--project` for named profiles or a relocated `PI_CODING_AGENT_DIR`
- **Antigravity CLI**: `~/.gemini/antigravity-cli/skills` and `~/.gemini/config/mcp_config.json`

## Pi package

Pi loads OpenWiki's skill, retrieval, and lifecycle tools from the npm package:

```bash
pi install npm:openwiki
```

Use `pi install --local npm:openwiki` for a project-local install. The Pi extension starts OpenWiki's CLI through Node, so `openwiki` need not be on `PATH`. Pi is not a target of `openwiki integrations install`.

## How host-driven runs work

Host-driven runs follow the same resumable page-job lifecycle as native `openwiki --init` and `openwiki --update`. The coding agent drives repository research and page authoring; OpenWiki validates each completion, persists [Grounded Claims](/oss/openwiki/code-mode#grounded-claims), and finalizes metadata through MCP.

On each page, the host submits sparse Claim decisions (confirm, revise, add, or retract). OpenWiki retains unaffected Claims, applies the explicit decisions, and refuses to finish until the final Claims state is durable. The host can call `openwiki_inspect_page_claims` when it needs the complete Claims set for the current page.

### Result capping in openwiki_begin

<Note>
    Result capping requires OpenWiki v0.8.0 or later.
</Note>

Repositories with many changed files or Claim issues can produce large `openwiki_begin` responses. To keep the response within transport limits, OpenWiki caps the returned lists and includes exact totals so the host can recover omitted data.

The response includes the following capping fields:

- **`changedPathCount`** (`number`): Exact number of repository paths changed since the previous run.
- **`changedPathsTruncated`** (`boolean`): Whether `changedPaths` omits entries beyond the 200-path limit. Each `pageUpdateWindows` entry also carries its own `changedPathCount` and `changedPathsTruncated`. Per-window path lists share that budget evenly across windows.
- **`claimIssueCount`** (`number`): Exact number of Claim preflight issues.
- **`claimIssuesTruncated`** (`boolean`): Whether `claimIssues` omits entries beyond the 50-issue limit.
- **`claimIssuePages`** (`string[]`): Every page that has a Claim issue, including pages whose individual issues were omitted from `claimIssues`.

When a `changedPathsTruncated` flag is `true`, recover the full list from Git. Each `pageUpdateWindows` entry carries its own baseline as `baseGitHead`. For every window that has a `baseGitHead` (not a `fullReview` window), list committed changes since that baseline:

```bash
git diff --name-only <baseGitHead>..HEAD
```

For every window, add uncommitted changes to tracked files and untracked files:

```bash
git diff --name-only HEAD
git ls-files --others --exclude-standard
```

Exclude `openwiki/` and `.openwikiignore` paths from the result.

Planning and page jobs read the full run state internally, so capping does not affect correctness. The host uses the truncation fields only when it needs to present the complete list to the user or to make its own routing decisions before calling `openwiki_submit_plan`.

### Defer unplanned Claim issues

<Note>
    `deferUnplannedClaimIssues` requires OpenWiki v0.9.0 or later.
</Note>

By default, `openwiki_submit_plan` on an `update` run automatically adds page jobs for every existing page that has stale or unresolved Claims, even when the host did not include those pages in its plan. To run a focused update that touches only the pages the host explicitly planned, set `deferUnplannedClaimIssues` to `true` in the `openwiki_submit_plan` input:
- **`deferUnplannedClaimIssues`** (optional `boolean`, default `false`): When `true`, OpenWiki skips inserting automatic jobs for unplanned pages with Claim issues. Those pages are recorded as deferred, and the run finishes in an interrupted state until a future full update reconciles them.
When `true`, OpenWiki skips inserting automatic jobs for unplanned pages with Claim issues. Those pages are left untouched, and the run completes but records its update metadata as interrupted until a future full update reconciles them.
This option is valid only on `update` runs. Setting it on an `init` run returns an `invalid_input` error.
