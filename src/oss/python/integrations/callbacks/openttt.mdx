## Overview

`langchain-openttt` provides `TTTPSTimestampCallbackHandlerKPPLive`, a `BaseCallbackHandler` that attaches a cryptographic Proof-of-Time receipt to each LLM generation's `generation_info`, without modifying the generated text. The receipt is produced by [TTTPS](https://datatracker.ietf.org/doc/draft-helmprotocol-tttps/) (proposal draft), a Roughtime-based timestamping scheme.

## Why

When you need to show a third party (a customer, an auditor, a counterparty) when an LLM response was generated and that it hasn't been altered since, plain application logs aren't enough: you control them, so nothing stops you from editing a timestamp after the fact. A TTTPS receipt is produced by an independent service at generation time and can be re-verified later.

This attaches a cryptographic timestamp and integrity hash to the generation. It does **not** certify the correctness of the LLM's output, and it does not certify legal or regulatory compliance (EU AI Act, FDA, etc.) on its own. Treat it as an audit-trail timestamp, not a compliance certification. The backing API's own receipt says as much: it "attests when/order/tamper-evidence, not correctness."

## How it works

1. On `on_llm_end`, the callback hashes each generation's text with SHA-256.
2. It `POST`s the hash to a Proof-of-Time backend, which timestamps and signs it.
3. The response is attached under `generation_info["tttps_receipt"]` on the `Generation` object; the generated text itself is untouched.

Fail-open by design: any failure (timeout, connection error, non-200, exhausted quota, unknown key) degrades to `{"status": "degraded", "reason": ...}` rather than raising, so a backend outage can never break the caller's LLM pipeline.

The package ships two handlers:

| Handler | Backend | Use |
|---|---|---|
| `TTTPSTimestampCallbackHandler` | Internal-only PoT server | Reference implementation; not reachable outside the maintainers' infrastructure |
| `TTTPSTimestampCallbackHandlerKPPLive` | Public self-serve `https://kpp.kenosian.com` Provenance API | What external callers should use |

## Prerequisites

```shell
pip install langchain-openttt
```

Mint a free API key (no card, no approval step):

```shell
curl -X POST https://kpp.kenosian.com/v1/keys \
  -H "Content-Type: application/json" \
  -d '{"email": "you@example.com", "use_case": "langchain callback"}'
```

```shell
export KPP_API_KEY=kpp_prov_...
```

## Example

```python
import os

from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage
from langchain_openttt import TTTPSTimestampCallbackHandlerKPPLive

os.environ["KPP_API_KEY"] = "kpp_prov_..."

llm = ChatOpenAI(model="gpt-4o-mini")

# generation_info is only populated on the LLMResult returned by
# generate()/agenerate(), not on the message returned by invoke().
result = llm.generate(
    [[HumanMessage(content="What is the capital of France?")]],
    callbacks=[TTTPSTimestampCallbackHandlerKPPLive()],
)

receipt = result.generations[0][0].generation_info["tttps_receipt"]
print(receipt)
# {"status": "ok", "content_hash": "sha256:...", "receipt_id": "...",
#  "receipt": "...", "time": "2026-08-04T...Z", "time_source": "roughtime_chain",
#  "backdating_p": "< 2^-128", "verify_url": "/v1/verify?receipt_id=...",
#  "remaining_quota": 999, "overhead_ms": 93.1}
```

The default request timeout is 1000ms; if the backend doesn't respond in time, `receipt` degrades to `{"status": "degraded", "reason": "ReadTimeout", "overhead_ms": ...}` instead.

## Verification

Re-verify a receipt later with the `receipt_id` returned above:

```shell
curl -X POST https://kpp.kenosian.com/v1/verify \
  -H "Content-Type: application/json" \
  -d '{"receipt_id": "..."}'
```
