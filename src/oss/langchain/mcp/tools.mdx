This page covers what is specific to that bridge: identifying MCP tools, controlling their execution, handling their outputs, and responding when a server needs input during a call. For the runnable discovery-and-agent example, see the [MCP quickstart](/oss/langchain/mcp).

## Use MCP tools in an agent

:::python
Discover the server's catalog with @[`MCPAdapter.list_tools`], then give the returned tools to @[`create_agent`]. From the agent's perspective, they behave like LangChain tools: the model chooses a tool, LangChain invokes it, and the resulting @[`ToolMessage`] returns to the model.

<McpUseInAgentPy />
:::

:::js
Discover the server's catalog with @[`MCPAdapter.listTools`], then give the returned tools to @[`createAgent`]. From the agent's perspective, they behave like LangChain tools: the model chooses a tool, LangChain invokes it, and the resulting @[`ToolMessage`] returns to the model.

```typescript
import { createAgent } from "langchain";
import { MCPAdapter } from "@langchain/mcp-adapters";

async function runAgent() {
  const adapter = new MCPAdapter(server);
  const tools = await adapter.listTools();
  const agent = createAgent({ model: "claude-sonnet-5", tools: [tools] });
  
  await agent.invoke({
    messages: [{
      role: "user",
      content: "What is the forecast for Oslo?"
    }]
  });
}
```
:::

For general guidance on defining, binding, and using LangChain tools, see [Tools](/oss/langchain/tools). For several MCP servers and their namespaced tool catalogs, see [Connections](/oss/langchain/mcp/connections#multiple-servers).

## Handle tool outputs

MCP tool results become LangChain-native values: content the model can read, an artifact for structured output, and a @[`ToolMessage`] status that distinguishes a server-reported error from a transport failure.

### Multimodal content

An MCP tool result arrives as LangChain [content blocks](/oss/langchain/messages#standard-content-blocks). Image and file content convert into standardized `image` and `file` blocks alongside `text`, so a tool that returns a screenshot reaches the model as an image block:

:::python
<McpMultimodalToolContentPy />
:::

:::js
```typescript
import { createAgent } from "langchain";
import { MCPAdapter } from "@langchain/mcp-adapters";

const client = new MCPAdapter(...);
const tools = await client.listTools();

const agent = createAgent({ model: "claude-sonnet-5", tools });

const result = await agent.invoke({
  messages: [
    { role: "user", content: "Take a screenshot of the current page" },
  ],
});

// Access multimodal content from tool messages
for (const message of result.messages) {
  if (message.type === "tool") {
    // Raw content in provider-native format
    console.log(`Raw content: ${message.content}`);

    // Standardized content blocks  // [!code highlight]
    for (const block of message.contentBlocks) {
    // [!code highlight]
      if (block.type === "text") {
        // [!code highlight]
        console.log(`Text: ${block.text}`); // [!code highlight]
      } else if (block.type === "image") {
        // [!code highlight]
        console.log(`Image URL: ${block.url}`); // [!code highlight]
        console.log(`Image base64: ${block.base64?.slice(0, 50)}...`); // [!code highlight]
      }
    }
  }
}
```
:::

### Structured content

When a tool returns structured content, the adapter attaches it to the @[`ToolMessage`] as an artifact rather than folding it into the model-visible text. Run the agent, then read the `artifact` from the @[`ToolMessage`] instances in the result:

:::python
<McpStructuredContentPy />

The artifact is an `MCPToolArtifact`, whose `structured_content` field holds the tool result's `structuredContent`. A tool that returns no structured content leaves `artifact` as `None`.
:::

:::js
```typescript
import { MCPAdapter } from "@langchain/mcp-adapters";
import { createAgent, ToolMessage } from "langchain";

const adapter = new MCPAdapter(...);
const tools = await adapter.listTools();
const agent = createAgent({ model: "claude-sonnet-5", tools });
const result = await agent.invoke({
  messages: [{ role: "user", content: "Look up user 42." }],
});

for (const message of result.messages) {
  if (ToolMessage.isInstance(message) && Array.isArray(message.artifact)) {
    const structured = message.artifact.find(
      (entry) => entry.type === "mcp_structured_content"
    );
    if (structured) {
      console.log(`Structured content: ${JSON.stringify(structured.data)}`); // [!code highlight]
    }
  }
}
```

The `artifact` is an array of MCP result entries. Structured content appears in the entry with `type: "mcp_structured_content"`, and its `data` field holds the tool result's `structuredContent`.
:::

### Errors

:::python
An MCP tool result carries an `isError` flag. When a server reports `isError=True`, the adapter converts it into a @[`ToolMessage`] with `status="error"` carrying the server's own message, so the agent can read it and correct itself:

<McpToolErrorsPy />
:::

:::js
An MCP tool result carries an `isError` flag. When a server reports `isError: true`, the adapter converts it into a failed @[`ToolMessage`] carrying the server's own message, so the agent can read it and correct itself:

```typescript
import { MCPAdapter } from "@langchain/mcp-adapters";
import { createAgent, ToolMessage } from "langchain";

const adapter = new MCPAdapter(...);
const tools = await adapter.listTools();
const agent = createAgent({ model: "claude-sonnet-5", tools });
const result = await agent.invoke({
  messages: [{ role: "user", content: "What is 10 divided by 0?" }],
});

// A server error (`isError: true`) reaches the model as a failed
// ToolMessage, so the agent can read the server's message and recover.
// Transport failures still throw because a model cannot act on them.
for (const message of result.messages) {
  if (ToolMessage.isInstance(message) && message.status === "error") {
    console.log(`Tool reported: ${message.text}`); // [!code highlight] 
  }
}
```
:::

A server-reported error reaches the model as a failed tool message, but a transport or session failure raises instead, because a model cannot act on a dropped connection.

## Tool metadata

Each adapted tool may carry its MCP provenance under an `mcp` namespace on the LangChain tool's metadata:

:::python
```python
tool.metadata
# {
#     "mcp": {
#         "tool": {
#             "annotations": {
#                 "destructive_hint": True,
#                 "read_only_hint": False,
#             },
#             "_meta": {"origin": "crm"},
#         },
#         "server": {
#             "name": "crm",
#             "version": "2.1.0",
#         },
#     },
# }
```
:::

:::js
```typescript
tool.metadata;
// {
//   mcp: {
//     tool: {
//       annotations: {
//         destructiveHint: true,
//         readOnlyHint: false,
//       },
//       _meta: { origin: "crm" },
//     },
//     server: {
//       name: "crm",
//       version: "2.1.0",
//     },
//   },
// }
```
:::

Every nested field is optional: a server may provide tool annotations, `_meta`, server identity, any combination of those, or none. `annotations` contains MCP hints such as `read_only_hint` and `destructive_hint`; `_meta` is opaque metadata supplied by the server; and `server` identifies the MCP implementation that advertised the tool.

Read optional metadata defensively, so a missing field returns a default rather than raising:

:::python
<McpToolMetadataPy />
:::
:::js
```typescript
import type { DynamicStructuredTool } from "@langchain/core/tools";

function isDestructive(tool: DynamicStructuredTool): boolean {
  return tool.metadata?.mcp?.tool?.annotations?.destructiveHint ?? false;
}
```
:::

## Human-in-the-loop

Reading annotations lets you gate a tool based on what the server declares about it, rather than hardcoding tool names. The MCP annotation classifies the tool and LangChain's human-in-the-loop middleware enforces the approval policy.

Read the destructive hint from metadata once during tool discovery. Then give the human-in-the-loop configuration a `when` predicate that receives each pending tool call and returns whether the call needs approval:

:::python
<McpDestructiveGatePy />
:::

:::js
```typescript
import { MemorySaver } from "@langchain/langgraph";
import { MCPAdapter } from "@langchain/mcp-adapters";
import {
  createAgent,
  humanInTheLoopMiddleware,
  type InterruptOnConfig,
  type WhenPredicate,
} from "langchain";

async function createGuardedAgent() {
  const adapter = new MCPAdapter(...);
  const tools = await adapter.listTools();

  // Read the hint once, then apply the same predicate to every tool call.
  const destructive = new Set(
    tools
      .filter(
        (tool) =>
          tool.metadata?.mcp?.tool?.annotations?.destructiveHint ?? false
      )
      .map((tool) => tool.name)
  );

  const needsApproval: WhenPredicate = (request) =>
    destructive.has(request.toolCall.name);

  const gate: InterruptOnConfig = {
    allowedDecisions: ["approve", "reject"],
    when: needsApproval,
  };
  const interruptOn = Object.fromEntries(
    tools.map((tool) => [tool.name, gate])
  );

  return createAgent({
    model: "claude-sonnet-5",
    tools,
    middleware: [humanInTheLoopMiddleware({ interruptOn })],
    checkpointer: new MemorySaver(),
  });
}
```
:::

When the agent calls a tool that the predicate gates, the run pauses. Approve the call to run it, or reject it to skip the tool and tell the model:

:::python
```python
from langgraph.types import Command

# Approve the pending destructive call and resume.
resumed = await agent.ainvoke(
    Command(resume={"decisions": [{"type": "approve"}]}), config
)
```
:::

:::js
```typescript
import { Command } from "@langchain/langgraph";

// Approve the pending destructive call and resume.
const resumed = await agent.invoke(
  new Command({ resume: { decisions: [{ type: "approve" }] } }),
  config
);
```
:::

The predicate can also inspect the call's arguments. This lets a tool run freely for safe inputs and pause only for risky ones, such as a `delete_file` call targeting a protected path.

:::python
Access the arguments through `request.tool_call["args"]`.
:::

:::js
Access the arguments through `request.toolCall.args`.
:::

Combine the metadata classification and argument check to gate a tool only when its type and inputs warrant approval. For the full approval workflow, see [Human-in-the-loop](/oss/langchain/human-in-the-loop).

## Server requests during tool execution

Most tools finish without asking the client for anything mid-call. When a server needs input, @[`MCPAdapter`] surfaces [elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation) as a LangGraph @[`interrupt`].

### Elicitation

[Elicitation](https://modelcontextprotocol.io/specification/draft/client/elicitation) is the MCP mechanism for a server to request input in the middle of a tool call. When a server needs input, the request surfaces as a LangGraph interrupt so the person already reviewing the agent's work answers it and the run resumes:

:::python
<McpElicitationPy />
:::

:::js
```typescript
import { Command, MemorySaver, type Interrupt } from "@langchain/langgraph";
import {
  MCPAdapter,
  type MCPElicitationInterrupt,
  type MCPElicitationResume,
} from "@langchain/mcp-adapters";
import { createAgent } from "langchain";

async function bookWithElicitation(serverUrl: string) {
  const adapter = new MCPAdapter({
    servers: { booking: { url: serverUrl } },
  });

  try {
    const agent = createAgent({
      model: "claude-sonnet-5",
      tools: await adapter.listTools(),
      checkpointer: new MemorySaver(),
    });
    const config = { configurable: { thread_id: "booking-1" } };

    const paused = await agent.invoke(
      { messages: [{ role: "user", content: "Book a table for 4." }] },
      config
    );
    const [pending] = paused.__interrupt__;
    const [requestKey] = Object.keys(pending.value!.requests);

    const resume: MCPElicitationResume = {
      [pending.id]: {
        responses: {
          [requestKey]: {
            action: "accept",
            content: { date: "2026-09-14" },
          },
        },
      },
    };

    return await agent.invoke(
      new Command<MCPElicitationResume>({ resume }),
      config
    );
  } finally {
    await adapter.close();
  }
}
```
:::

A few things to note:

- **Elicitation is on by default.** The adapter advertises the capability and drives the interrupt loop. A prebuilt client that already carries its own elicitation handler is honored instead of overridden.
- **Resuming needs persistence.** Attach a [checkpointer](/oss/langchain/short-term-memory) so the interrupted run has somewhere to wait.
- **Answers are keyed by the server's request key.** Each answer's `action` is `accept` (with `content` matching the request's schema), `decline` (answer refused, call continues), or `cancel` (the whole call is abandoned).

:::python
Resume with `Command(resume={"responses": {key: answer}})`. The interrupt payload and answer types live in `langchain.mcp.elicitation`.
:::

:::js
Address the responses to the pending interrupt ID with `MCPElicitationResume`, then resume with `new Command<MCPElicitationResume>({ resume })`. The adapter exports the interrupt and answer types. Set `elicitation: false` on an individual modern server to opt out.
:::

Only elicitation is answered this way. A server that instead asks for [sampling](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling) or [roots](https://modelcontextprotocol.io/specification/2025-06-18/client/roots) raises an error, because the modern, sessionless protocol has no live back-channel for those requests. See [Sampling and roots](/oss/migrate/langchain-mcp-adapters#sampling-and-roots).

<Note>
Interrupt-driven elicitation answers a server that returns its request as an `InputRequiredResult`. A server that only pushes elicitation over a legacy handshake session cannot be answered this way.
</Note>
