Most remote MCP servers require authentication. @[`MCPAdapter`] delegates auth to FastMCP, so any credential a `fastmcp.Client` accepts works: a static [bearer token](#bearer-token), a full [OAuth 2.1](#oauth-authentication) flow, or any [`httpx.Auth`](https://www.python-httpx.org/advanced/authentication/). Pass the credential on a prebuilt client and hand that client to the adapter. When one agent talks to several servers, use [per-server authentication](#per-server-authentication); in a deployment, use [per-user authentication](#per-user-authentication) so each run reaches the server as the caller.
<Note>
The `langchain.mcp` namespace requires `langchain[mcp]>=1.4.0` and is in beta. The API may change.
</Note>

## Bearer token

The simplest case: the server verifies a token you provisioned and adds it in the `Authorization: Bearer <token>` header. There is no discovery, browser, or refresh. Pass the token as the client's `auth`:

<McpAuthBearerPy />

The `auth` argument accepts a bearer-token string, the literal `"oauth"`, or any `httpx.Auth`. In an `MCPConfig` fleet, each server takes the same key.

## OAuth authentication

For a server that issues its own credentials, pass the literal string `"oauth"`. FastMCP runs the full OAuth 2.1 flow: discovery, [dynamic client registration](https://modelcontextprotocol.io/specification/draft/basic/authorization), the browser redirect, and the token exchange. Dynamic client registration means the client registers itself at runtime instead of you pre-provisioning a client ID:

<McpAuthOauthPy />

By default tokens are held in memory, so each run repeats the browser step. Pass a prebuilt `OAuth` provider with a token store to persist them across runs:

```python
from fastmcp.client import Client
from fastmcp.client.auth import OAuth

oauth = OAuth(mcp_url="https://example.com/mcp", token_storage=...)
client = Client("https://example.com/mcp", auth=oauth)
```

FastMCP ships providers for common identity providers (Auth0, WorkOS, Okta, and more); the flow the client runs is identical across them. See [OAuth authentication](https://gofastmcp.com/clients/auth/oauth) in the FastMCP documentation.

When one agent talks to several servers, each server may need its own credential. Give each its own connection with a [`ClientGroup`](/oss/langchain/mcp/connections#independent-connections-with-clientgroup), and set `auth` per client, so every server authenticates independently:

## Per-user authentication

In a deployment, each run should reach the MCP server as the user who initiated it, not with one shared credential. The pattern has two halves:

1. **Authenticate the caller at the LangGraph server.** A [custom auth handler](/langsmith/auth) resolves the incoming request to a user identity, which each run reads off its runtime.
2. **Mint or exchange a credential for that user.** Inside the [graph factory](/oss/langchain/mcp/connections#scale-a-deployment), read the user's identity and build the MCP client with a per-user token, so the connection carries that user's authorization.

<McpAuthPerUserPy />

In production, `token_for` stands in for whatever the deployment already has: an OAuth gateway that exchanges the session for a per-user token, or a `fastmcp.client.auth` provider that runs the authorization-code flow per identity. Isolate any [cached responses](/oss/langchain/mcp/connections#caching) per user, keyed off the verified identity, so one user never sees another's cached tool list.

## Bearer token

For a fixed API key, send a static `Authorization` header. For a token your app issues or rotates, pass an `AuthProvider` (`{ token, onUnauthorized? }`) as `authProvider`:

```typescript
import { MCPAdapter } from "@langchain/mcp-adapters";

const adapter = new MCPAdapter({
  servers: {
    // A fixed API key, sent as a header.
    search: {
      url: "https://search.example.com/mcp",
      headers: { Authorization: `Bearer ${process.env.SEARCH_API_KEY}` },
    },
    // A token your app issues and rotates.
    crm: {
      url: "https://crm.example.com/mcp",
      authProvider: {
        token: async () => tokenStore.current(),
        onUnauthorized: async () => {
          // Throw when no newer token exists: over SSE, the SDK calls this
          // again every time a reconnect is rejected.
          if (!(await tokenStore.refresh())) {
            throw new Error("No newer token for the CRM server");
          }
        },
      },
    },
  },
});
```

- **`token()`**: Runs before every request and returns the current token.
- **`onUnauthorized()`**: Optional. Runs on a 401, before the request is retried once. Over SSE, the SDK calls it again every time a reconnect is rejected, with no cap. Throw from it when you have no newer token.

Without `onUnauthorized`, a 401 fails the connection with the SDK's `UnauthorizedError`. See [Handle authentication errors](#handle-authentication-errors).

The adapter re-exports the `AuthProvider` and `OAuthClientProvider` types, so you can type a provider without importing the SDK.

## OAuth authentication

For a server that uses OAuth 2.1, pass an `OAuthClientProvider` as `authProvider`. The SDK runs discovery, [dynamic client registration](https://modelcontextprotocol.io/specification/draft/basic/authorization), the code exchange, and token refresh. For a walkthrough of each provider method and the redirect, see the MCP TypeScript SDK's [OAuth client guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/clients/oauth.md).

An `OAuthClientProvider` is not the OAuth server. It is storage your app owns, plus a redirect hook. The SDK reads and writes client information, tokens, the PKCE code verifier, and discovery state through its methods. Tokens live wherever your provider stores them, so whether a login survives a restart is your choice. The adapter keeps no token store, has no in-memory default, and has no browser login helper. Your app owns the redirect and the callback.

```typescript
import { MCPAdapter, type OAuthClientProvider } from "@langchain/mcp-adapters";

const callbackUrl = "https://app.example.com/oauth/callback";

// Every method reads or writes your storage for one user. Use durable
// storage to keep the login across restarts.
function oauthProviderFor(userId: string): OAuthClientProvider {
  const store = oauthStore(userId);
  return {
    redirectUrl: callbackUrl,
    clientMetadata: { client_name: "My agent", redirect_uris: [callbackUrl] },
    state: () => store.createPendingState(),
    clientInformation: () => store.load("client"),
    saveClientInformation: (info) => store.save("client", info),
    tokens: () => store.load("tokens"),
    saveTokens: (tokens) => store.save("tokens", tokens),
    codeVerifier: () => store.load("verifier"),
    saveCodeVerifier: (verifier) => store.save("verifier", verifier),
    discoveryState: () => store.load("discovery"),
    saveDiscoveryState: (state) => store.save("discovery", state),
    invalidateCredentials: (scope) => store.invalidate(scope),
    // Send the user to the login page, for example by returning the URL
    // to your frontend.
    redirectToAuthorization: (url) => store.saveLoginUrl(url),
  };
}

const adapter = new MCPAdapter({
  servers: {
    crm: {
      url: "https://crm.example.com/mcp",
      authProvider: oauthProviderFor(userId),
    },
  },
});
```

Beyond the methods the SDK requires, implement these:

- **`state()`**: Returns the OAuth `state` value. Record it as pending so the callback can [consume it once](#complete-the-redirect). The SDK sends `state` only when the provider supplies one, and it does not check it on the way back.
- **`saveClientInformation()`**: Stores the client that dynamic client registration creates. Omit it only for a pre-registered client.
- **`saveDiscoveryState()` and `discoveryState()`**: Persist this state alongside the code verifier. It is required when the authorization server is only discoverable from the 401 challenge. It also lets the SDK check that the callback comes from the authorization server the login started with.
- **`invalidateCredentials()`**: Lets a refresh that the server rejects restart the login instead of failing.

For machine-to-machine access with no user, pass the SDK's `ClientCredentialsProvider`, which implements `OAuthClientProvider` and needs no redirect.

### Complete the redirect

When a connection needs a login, the SDK calls `redirectToAuthorization()`, and the connection attempt fails with an `UnauthorizedError` cause. After the user signs in, the authorization server redirects to your callback URL. Complete the login with the SDK's `transport.finishAuth(params)`. Use a provider that reads and writes the same storage as the provider in the adapter's server config. The adapter has no `finishAuth` of its own.

```typescript
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/client";

// In your OAuth callback route, with the same provider (same storage) the adapter uses:
const params = new URL(req.url).searchParams;
// The SDK doesn't check state. Consume it once: look it up and delete it.
if (!(await deletePendingState(params.get("state"))))
  throw new Error("unknown state");
const transport = new StreamableHTTPClientTransport(new URL(serverUrl), {
  authProvider,
});
await transport.finishAuth(params); // validates iss (RFC 9207), exchanges the code, saves tokens via the provider
await transport.close();
// The next adapter discovery or tool call connects with the saved tokens.
```

Use `SSEClientTransport` instead for a server configured with `transport: "sse"`. The callback route does not need an `MCPAdapter`. Your app needs its own direct dependency on `@modelcontextprotocol/client`, version 2.2 or later, to import it, even though the adapter depends on it.

Follow these rules in the callback:

- **Consume `state` once**: Look up and delete the pending `state` before calling `finishAuth()`, and do not call it for a `state` that is already gone. Otherwise a refresh, a double-invoked handler, or a back-button replay redeems the same code twice. The SDK responds by discarding the tokens the first call saved, which logs the user out.
- **Wait for a pending login**: Do not start another discovery while a login is pending. A new discovery begins a new redirect and invalidates the first callback.
- **Hide SDK error text**: Catch a callback failure and show your own generic message. `IssuerMismatchError` carries the callback's `iss`, which an attacker controls in a mix-up attack. `OAuthError` can carry the authorization server's `error_description`. Both come from `@modelcontextprotocol/client`.

## Handle authentication errors

A connection rejected for credentials throws an `MCPClientError`. Its `cause` tells you what to do next:

- **`UnauthorizedError`**: The SDK cannot recover on its own. An OAuth login is needed, or a token provider has no `onUnauthorized`.
- **An HTTP 401 `SdkHttpError`** (`status: 401`): The server still rejects the credentials after `onUnauthorized` or a token refresh.

```typescript
import { MCPClientError, UnauthorizedError } from "@langchain/mcp-adapters";
import { SdkHttpError } from "@modelcontextprotocol/client";

function authFailure(error: unknown): "login" | "rejected" | undefined {
  if (!MCPClientError.isInstance(error)) return undefined;
  // An OAuth login is needed, or a token provider has no onUnauthorized.
  if (UnauthorizedError.isInstance(error.cause)) return "login";
  // Still rejected after onUnauthorized or a token refresh.
  if (SdkHttpError.isInstance(error.cause) && error.cause.status === 401)
    return "rejected";
  return undefined;
}
```

The adapter re-exports `UnauthorizedError`. Import `SdkHttpError` from `@modelcontextprotocol/client`. An `MCPClientError` message includes the SDK's error text, so log it rather than show it to users.

When a server rejects the credentials during a tool call, the tool fails with a `ToolException` instead. Under `createAgent`, the model sees it as an error message and the run continues.

A server that failed on authentication is retried on the next discovery, even when `onConnectionError` skips failed servers. A later login recovers without recreating the adapter.

## Header precedence

Once a provider has a token, it replaces a configured `Authorization` header. Until then, the header is sent, so a static API key can fall back to OAuth.

The SDK also forwards a static `Authorization` header to the authorization server's discovery, registration, and token endpoints, not only to the MCP server. Do not pair a secret API key with an OAuth provider whose authorization server lives on another origin.

## Per-server authentication

Each named server takes its own `authProvider` and `headers` and opens its own connection, so the servers in one adapter authenticate independently. No grouping construct is needed: the [bearer token example](#bearer-token) gives two servers different credentials.

## Per-user authentication

In a deployment, each run should reach the MCP server as the user who started it, not with one shared credential. Pass `authProvider` or `headers` in the options of `listTools()`, `listToolsets()`, `getClient()`, or the resource methods (`listResources()`, `listResourceTemplates()`, and `readResource()`):

```typescript
import { MCPAdapter, type AuthProvider } from "@langchain/mcp-adapters";

// A single-server adapter, because each user brings a different credential.
const crm = new MCPAdapter({
  servers: { crm: { url: "https://crm.example.com/mcp" } },
});

// Reuse one provider object per user: each object opens its own connection.
const providers = new Map<string, AuthProvider>();

function providerFor(userId: string): AuthProvider {
  let provider = providers.get(userId);
  if (!provider) {
    provider = { token: async () => tokenFor(userId) };
    providers.set(userId, provider);
  }
  return provider;
}

const tools = await crm.listTools(["crm"], {
  authProvider: providerFor(userId),
});
```

The returned tools call the server through that user's connection. Three rules apply to these overrides:

- **Adapter-wide override**: An `authProvider` or `headers` in a method's options applies to every HTTP and SSE server the adapter holds, not only the one you name. Use a single-server adapter when different users need different credentials.
- **One connection per provider object**: Each distinct provider object gets its own connection, kept until `close()`. Reuse one provider object per user rather than creating one per call.
- **Isolated catalogs**: Catalogs are keyed by provider object and headers, so one user never receives another user's cached tool list. Recreate the adapter when the account behind the same provider object changes.

Resolve the user from the incoming request, for example with a [custom auth handler](/langsmith/auth) on a LangGraph server.
